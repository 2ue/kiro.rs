# 与 ZyphrZero/kiro.rs 的对比：空回处理与说明文档所列特性

**更新时间：** 2026-10-29（按最新代码复核过两次，见文末「复核记录」）
**对比对象：** `https://github.com/ZyphrZero/kiro.rs`，提交 `7255d98`（0.9.3，两次复核时远端都没有新提交），本地克隆在 `../kiro.rs-zyphrzero`。
- 实测时，本项目用的是 0.0.222，加上当时还没提交的空回冷却开关。
- 最近一次复核时，本项目是 0.0.224（`c8eb99a3`）；线上 59137 也已升级到这个版本。

**方法：** 三种方式结合：
- 阅读两边代码；
- 用同一批真实账号、同一组请求同时请求两边；
- 空回用对方项目自带的模拟上游测试实测，临时加的探测用例已经撤掉。

**相关文档：** [59137 线上账号频繁冷却与并发分配不均](prod-59137-cooldown-dispatch-imbalance-20261028.md)

## 结论

- **空回处理：本项目明显更强。** 对方的做法：
  - 只有用量统计的回合，直接返回 200、内容为空，按正常结束处理，不重试也不换号；
  - 零帧只报错，不重试；
  - 首输出前不会换号。
- **常规功能：真实账号下两边结果一致。** 差异只在两处：大图片（对方会缩放，我们原样发送），以及缓存用量的上报口径。
- **对方有约 10 处值得借鉴。** 优先级最高的是：
  - 5xx 携带请求格式错误时不重试；
  - ~~模型暂时不可用时返回 503 并带重试间隔~~（看过线上数据后撤回，见[实施计划](zyphrzero-adoption-plan-20261029.md)）；
  - 客户端版本号自动更新；
  - 读取上游时按静默时长判超时，而不是按总时长；
  - 图片缩放。

## 一、空回处理（实测）

对方部分的测法：用对方测试里的模拟上游，一种是它自带的"空响应体"，另一种是我临时补的"只返回用量统计帧"。每种都分别打 `/cc/v1/messages` 和 `/v1/messages`，流式和非流式各一次，只用单账号。

| 场景 | 对方结果 | 本项目结果 |
|---|---|---|
| 只有用量统计，流式 | 返回 200，发出结束事件，停止原因是正常结束，内容为空；上游只调用 1 次；不计失败 | 带续写提示换号重试，次数用完后发错误事件，不发结束事件 |
| 只有用量统计，非流式 | 返回 200，内容是空数组，正常结束；上游调用 1 次 | 换号重试，次数用完后返回 502 |
| 零帧，流式 | 发错误事件，不发结束事件；上游调用 1 次；不计失败 | 换号重试，次数用完后发错误事件 |
| 零帧，非流式 | 返回 502；上游调用 1 次 | 换号重试（本次新增），次数用完后返回 502 |

对方只在一个地方检测空回：联网搜索循环里，工具结果之后如果是空回合，就重试一次，再空就返回 502（`src/anthropic/websearch_loop.rs:251-267`）。

把空内容当作正常结束返回给 Claude Code，会写进它的会话历史，后面几轮会跟着出问题。本项目已经改成按失败返回。

## 二、真实账号对比（本项目 0.0.222 加开关）

- **账号**：从根目录的账号文件里抽了 30 个。其中 6 个被上游临时封停，11 个返回 403，剩下 13 个免费账号可用，两边共用这一批。
- **模型和用例**：Haiku 4.5 和 Sonnet 4.5，10 个用例，流式和非流式各跑一次，共 40 组对照。

两边结果一致、而且都正确的用例：
- 基础问答；
- 开启思考（两边都带签名）；
- 超长工具名的还原；
- 无参工具还原为空对象；
- 孤立的工具结果；
- 历史里未闭合的工具调用；
- 类型标错的图片。

有差异的用例：

| 用例 | 本项目 | 对方 | 说明 |
|---|---|---|---|
| 大图片（2400×1600，约 1.6MB） | 原样发送，上游请求体 1.68MB；Sonnet 非流式有一次等响应头等了 83 秒 | 先缩放再发送，输入 token 少约 700；同一用例耗时 7 秒 | 83 秒只出现过一次，不能断定是图片体积导致的 |
| 缓存第二轮（同一会话） | 输入 11351；读缓存在非流式是 6763，在流式是 11157 | 输入 23，读缓存 11371 | 本项目默认口径下，输入包含了缓存部分；而且同一段前缀在流式和非流式下的读缓存不一致 |
| 图片类请求的写缓存 | 流式有时会报写缓存（4100–5556） | 0 | 这些请求没有加缓存标记 |
| 流式工具调用 | 只有工具块 | 工具块前多一个空文本块 | 两种写法都合法 |

缓存口径可能是有意设计的计量策略。如果对外要按官方口径结算（输入、写缓存、读缓存三项互斥，相加等于总量），需要确认一下。

### 原先列为"对方更好"、复核后撤回的两项

- **非流式下只有思考的回合**：原文说对方会补一个空格文本块、我们不补，两点都不对。用两边的模拟上游实测过：
  - 对方开启思考时，content 里只有思考块，停止原因是正常结束；没开思考时，把思考内容当正文返回。
  - 本项目同样只有思考块（带签名），停止原因是正常结束。
  - 流式两边都会补一个空格文本块。区别是对方把停止原因改成 max_tokens，本项目保持正常结束（`src/anthropic/stream.rs:4274-4287`）。本项目这样做是有意的：改成 max_tokens 会让 Claude Code 把一轮本来能接着做的对话中断掉。
- **联网搜索循环里的空回**：原文说本项目重试一次仍为空时返回 200 加空内容，不准确。本项目会重试一次，但返回的停止原因由有没有工具调用决定，空文本块也不会发出去。这个循环默认关闭（路由特性 `modelDrivenWebSearch`，默认 false）。对方重试一次仍为空时返回 502。两边做法不同，但不能简单说对方更好。

### 本项目更强

| 项目 | 说明 |
|---|---|
| 空回处理与首输出前换号 | 见第一节 |
| 并发控制 | 有全局并发、单号并发和按密钥的准入排队；对方的业务请求没有并发上限 |
| 调度 | 支持多种调度方式、预热、按错误类型分别冷却、会话软失败 |
| 思考强度映射 | 优先使用上游模型目录，并映射到最接近的支持档位 |
| 429 处理 | 容量类 429 换号但不冷却；风控类按凭据开关处理；支持区域轮换 |

### 对方说明文档与代码不一致

说明文档写的是"输出配置只在 Opus 4.6 自适应模式下传递"。实际上代码对 Opus 4.6/4.7/4.8、Sonnet 4.6、5.x 系列和 GPT-5.6 都会下发（`src/anthropic/converter.rs:352-389`）。

## 四、本次已做的改动（提交 `c199812d`，随 0.0.224 发布）

0.0.224 的标签后来移到了 `c8eb99a3`，期间补了两处修复，线上实际跑的就是这个提交：

- **`79dccf7e`**：空回会在当次请求内排除账号。所有本地账号都被排除后，原来的逻辑仍按"本地有可用账号"处理，外部池兜底因此被抑制，客户端拿到 502。现在新增"当次请求已排除全部本地账号"这一类原因，允许转外部池。
- **`c8eb99a3`**：抓取测试改为等写线程把队列写完再读取。原来轮询目录时，可能读到还没写完的临时文件。

- **新增全局开关「空回也让账号冷却」**（`credentialEmptyTurnCooldownEnabled`，默认关闭）。位于运行配置的冷却分组，新旧两个管理页面都加了。
- **空回范围扩大为三种**：只有用量统计、零帧、空响应体。
  - 开关关闭时：只在当次请求内排除该账号并换号，不冷却，也不记会话失败。
  - 开关打开时：按流式错误的规则冷却。
- **非流式零帧和空响应体改为换号重试**：以前直接返回 502，现在换号重试，次数沿用首输出前的重试上限。
- **修复两个原有测试问题**：
  - 请求抓取改为先写临时文件再改名，读取方不会看到写了一半的记录；
  - "响应体超长"的测试夹具实际发出的是空响应体，改为发送长度未知的流。

验证结果：

- 新增用例覆盖三种空回、流式和非流式、开关开和关的所有组合，全部通过。
- 全量测试：
  - 合并远端 0.0.223 前：
    - 默认特性：2691 个通过，0 个失败。
    - 另一种加密后端：2690 个通过，1 个失败。失败的是上游调用层的故障矩阵，在全量并发下超时；单独复跑 3 次都通过。这条路径本次没有改动，后来 `94c675c8` 查明原因并修复：测试在异步运行时里同步构建 HTTP 客户端，加载根证书时阻塞了运行时。
  - 合并后提交前：两种后端各 2699 个通过，0 个失败。
  - **提交后 CI 失败**：本地两遍全部通过，但 CI 挂在外部池兜底的用例上（由 `79dccf7e` 修复）。原因是本地没有设置 `KIRO_RS_TEST_POSTGRES_URL` / `KIRO_RS_TEST_REDIS_URL`，约 22 个依赖存储的集成测试直接跳过、算作通过；CI 设置了 `KIRO_RS_REQUIRE_STORAGE_TESTS=1`，这些测试会真跑。以后改动调度、账号排除或外部池逻辑，要带上这两个变量再跑一遍。
- 格式检查、静态检查（告警数在基线以内）、两个前端的类型检查都通过。
- 在本地实例上通过管理接口保存开关再读回，打开和关闭两个方向都正常。

## 建议的后续顺序

1. 上游 5xx 携带请求格式错误时不重试，直接返回 400。
2. ~~模型暂时不可用时，对外返回 503 并带重试间隔。~~ 已撤回，理由同上。
3. 客户端版本号改为定时拉取，至少先更新默认值；同时检查五套请求头是否一致。
4. 非流式读取改为按静默时长判超时。
5. 流式工具参数在结束时校验，不合法就报错。
6. 图片缩放和历史图片去重（需要引入图片处理依赖）。
7. 自愈加上最小间隔和连续轮数限制。
8. 确认缓存用量的对外口径。
