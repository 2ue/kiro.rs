# 借鉴 ZyphrZero/kiro.rs 的实施计划

**日期：** 2026-10-29
**依据：** [对比文档](zyphrzero-kiro-rs-comparison-20261028.md)，以及线上 59137 最近 7 天的只读数据：用量记录 34.9 万条，覆盖 10-23 至 10-29，外加 24 小时应用日志。
**原则：** 只做线上数据证明有问题、或风险低且收益确定的改动。会改变上游身份、计费口径的项目，先请你决定，不在本轮直接改。

## 一、先用线上数据给对比文档里的建议排个序

| 对比文档里的建议 | 线上 7 天数据 | 结论 |
|---|---|---|
| 5xx 携带请求格式错误时不重试 | 0 次（7 天用量记录和 24 小时日志里都没有出现） | 低价值，但改动小、风险低，作为防御项做 |
| 模型暂时不可用时返回 503 | 59 次，其中 55 次靠换号最终成功 | **不照搬**。对方的做法是遇到就直接返回 503、不重试，套到我们这里会把 55 次成功变成失败。最后真正失败的 4 次，最终原因也不是"模型不可用"，改对外状态码没有收益。对比文档要相应修正 |
| 客户端版本号自动更新 | 线上配置写的是 0.11.107，官方当前版本是 1.4.62 | 这是上游身份指纹，影响所有账号。**需要你决定**，本轮不改 |
| 非流式按静默时长判超时 | 因总时长超时被截断：0 次。"读取响应失败"有 8 次，都是解码错误，不是超时 | 暂不做 |
| 图片缩放 | 没有图片体积超限的失败 | 暂不做。另外要引入图片解码依赖，对不可信输入做解码有 CPU 消耗风险 |
| 流式工具参数在结束时校验 | 流结束时工具参数不完整：20 次（这种情况已经能识别并报错）。工具调用正常结束但参数是非法 JSON 的情况，目前直接原样转发，统计不到 | 本轮只加观测日志，不改行为，用数据决定下一步 |
| 自愈节流 | 7 天自愈 0 次，自动禁用 89 次 | 暂不做 |
| 524 快速失败 | 0 次 | 暂不做 |
| 缓存用量对外口径 | — | 涉及计费，**需要你决定** |

**新发现、两边都没处理的问题：图片数量超限。**

- 10-28 当天有 486 个请求被上游拒绝，原因是 `IMAGE_COUNT_EXCEEDED`（上游报错原文："too many inline media segments: 123 exceeds limit 100"），占当天全部 400 失败的大多数。
- 涉及 16 个会话，都是 `/dfcache/mine-haa`、`claude-opus-5-5`、非流式请求。图片数量从 101 一路涨到 210，说明是会话越长，历史里累积的截图越多。
- 同一个会话最多失败了 132 次，持续两个半小时：客户端拿到 400 后一直用同样的历史重发。
- 目前这类错误被归成笼统的 `bad_request`，对外是一句通用的"请求无效"，用户看不出原因。
- 对方项目只对历史里完全相同的图片去重，没有限制数量，所以也会遇到同样的问题。

## 二、本轮实施内容

### 1. 图片数量上限（P0）

**做法：**
- 在 Kiro 请求体的安全整形环节，统计历史和当前轮的图片总数。
- 总数超过上游上限（100）时，从最早的历史消息开始移除图片，直到总数不超过上限。
- 被移除图片的那条历史消息，正文末尾追加一句说明，沿用现有"历史图片超过 5MB 被省略"的写法。
- 当前轮的图片不动。

**开关：** 跟随「请求体整形」总开关（`payloadShaping.enabled`，线上已开），不复用 `oversizedImageHandling`。
- 原因：线上这个设置是 `reject`，管理页面上的说明也写的是"单图超 5MB 处理"。复用它的话，数量上限在线上永远不会生效，语义也对不上。
- 超出数量的请求，上游一定会拒绝，原样发送没有任何意义，所以不再单独提供"原样发送"的选项。

**统计：**
- 移除的数量写进体积保护报告，复用已有的"移除历史图片"字段。
- 打一条日志，记录移除前后的数量。

**错误分类：**
- 上游返回 `IMAGE_COUNT_EXCEEDED` 时，单独归类为"图片数量超限"。
- 对外返回 400，附明确提示：图片太多，请新开会话或减少截图。同时带 `x-should-retry: false`，避免客户端无限重试。
- 有了上限之后，只有当前轮自己就超过 100 张时才会走到这一步。

**不做：**
- 不对历史图片做去重。线上没有证据显示截图会重复，上限已经足够解决问题。
- 不处理外部池的转发路径。这次的失败都发生在本地 Kiro 路径上。

### 2. 5xx 携带请求格式错误时直接失败（P1，防御项）

**判定（只认精确特征，避免误杀本来可以重试成功的 5xx）：**
- JSON 顶层的 `reason`，或者 `error.reason`，等于 `TOOL_USE_RESULT_MISMATCH` 或 `TOOL_SCHEMA_INVALID`；
- 或者正文里出现 `Expected toolResult blocks`。

**行为：**
- 按现有 400 工具格式错误的路径处理：不重试，不换号，不冷却账号，对外返回 400。
- 其他 5xx（包括"模型暂时不可用"）维持现状，继续换号重试。

### 3. 流式工具参数异常的观测（P1，只加日志）

- 流式工具调用正常结束时，如果累积的参数非空、却不能解析成 JSON，打一条告警日志。
- 日志只记录工具名、字节数和请求编号，不记录参数内容。
- 不改变对外行为，积累一周数据再决定要不要像对方那样整段缓冲、校验后再下发。

## 三、不在本轮做、需要你决定的事

1. **客户端版本号**：是保持 0.11.107，还是改成定时拉取官方版本（目前是 1.4.62）？
   - 改了会同时影响所有账号的五套请求头。
   - 落后太多可能本身就是风险信号；跳到新版本也可能改变上游的行为。
2. **缓存用量对外口径**：输入 token 现在包含缓存部分，是否改成官方的三项互斥口径？这会影响按用量结算的下游。

## 四、验证方案

为了保证改动后功能正常，按下面四步验证：

1. **新增单元测试**：
   - 图片上限：历史超限、当前轮超限、正好 100 张、同一条消息里只移除部分图片、提示文案、报告计数、`oversizedImageHandling=reject` 时仍然生效、请求体整形关闭时不改动；
   - 错误分类：`IMAGE_COUNT_EXCEEDED` 对外返回 400，提示明确，且不重试；
   - 5xx 携带工具配对错误：上游只请求 1 次，账号不冷却，对外 400；5xx 携带"模型暂时不可用"时仍然换号；
   - 流式工具参数非法时打出告警。
2. **全量测试连同存储集成测试一起跑**（吸取上次的教训）：
   - 设置 `KIRO_RS_TEST_POSTGRES_URL`、`KIRO_RS_TEST_REDIS_URL`，指向独立的测试库和专用的 Redis 库；
   - 同时设置 `KIRO_RS_REQUIRE_STORAGE_TESTS=1`，防止这些测试静默跳过；
   - 两种加密后端各跑一遍。
3. **真实账号验证**：
   - 起一个临时实例，导入少量免费账号，用 Sonnet 4.5 发一个历史里带 105 张小图的请求；
   - 先关闭请求体整形，确认上游确实返回 `IMAGE_COUNT_EXCEEDED`，并且对外是明确的 400；
   - 再开启请求体整形，确认请求成功、回复正常；
   - 结束后清理实例和数据。
4. **常规检查**：格式检查、静态检查基线、两个前端的类型检查。这次不改前端，只确认没有被影响。

## 五、实施结果（2026-10-29）

### 改动

| 项目 | 位置 |
|---|---|
| 图片数量上限 | `src/anthropic/payload_guard.rs`：新增常量 `UPSTREAM_MAX_INLINE_IMAGES`，新增函数 `apply_history_image_count_limit` 和 `drop_oldest_history_images_over_count` |
| `IMAGE_COUNT_EXCEEDED` 分类 | `src/kiro/provider.rs` 新增原因 `image_count_exceeded_bad_request`；`src/anthropic/handlers.rs` 对外返回 400 并带 `x-should-retry: false`；提示文案见 `envelope::PUBLIC_IMAGE_COUNT_EXCEEDED_MESSAGE` |
| 5xx 携带请求格式错误时直接失败 | `src/kiro/provider.rs`：新增函数 `is_server_error_client_validation`，主请求循环和思考签名重试两处都加了拦截 |
| 流式工具参数观测 | `src/anthropic/stream.rs`：工具调用正常结束、但参数不是合法 JSON 时打告警日志，不改对外行为 |

### 验证

- **新增单元测试 9 个，全部通过**：
  - 图片上限 3 个：超限时从最早的消息开始移除、正好 100 张时不动、只在被移除图片的消息上加说明，以及开关的跟随关系；
  - 5xx 判定 2 个：精确特征直接失败、只在正文里提到时仍然重试，对流式和非流式各跑 5 轮；
  - 400 分类 1 个、对外映射 1 个、流式日志 1 个、检测规则表 1 个。
- **全量测试**，连同存储集成测试一起跑（设置了 `KIRO_RS_REQUIRE_STORAGE_TESTS=1`，使用一次性测试库和独立的 Redis 容器）：
  - 默认特性：2712 个通过，1 个失败。失败的是 `postgres_migration_compresses_second_rollup_buckets_to_hours`，原因是等写锁超过 5 秒。
  - rustls：2712 个通过，1 个失败。失败的是 `usage_cleanup_lease_renewal_recovers_from_transient_row_lock_for_three_rounds`，原因是续租单次超过 40 毫秒。
  - 这两个用例都在存储和管理模块里，本次没有改动这两个文件。单独复跑：前一个连续 3 次通过；存储模块整体复跑 2 次，每次 157 个全部通过；管理模块在 rustls 下复跑，110 个全部通过。判断是全量并发时本机数据库争用导致的超时，与本次改动无关。
- **真实上游验证**：临时实例，Sonnet 4.5，8 个可用的免费账号，请求历史里带 105 张小图：

  | 请求体整形 | 非流式 | 流式 |
  |---|---|---|
  | 关闭 | 上游拒绝，原因是 `IMAGE_COUNT_EXCEEDED`。对外返回 400，带 `x-should-retry: false`，提示"图片超过 100 张，请新开会话或减少截图" | 同样返回 400，同一句提示 |
  | 开启 | 200，回复"收到"。日志记录：移除前 105 张，移除 5 张，上限 100 | 200，回复"收到" |
- **常规检查**：格式检查通过；静态检查告警 745 个，基线允许 849 个；前后端共用的 218 个类型契约一致。

### 风险与回退

- 图片上限只移除最早的历史截图，当前轮的图片不动。如果模型需要回看很早的截图，它会看到"较早的图片已省略"的说明。
- 关闭「请求体整形」可以同时关掉这项功能，代价是超过 100 张图片的请求会直接被上游拒绝。
- 5xx 判定只认精确的原因字段。其他 5xx 的行为完全不变，包括"模型暂时不可用"。
