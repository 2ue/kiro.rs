# 59137 本地账号错误：两项改进建议与空回复重试次数方案（2026-11-02）

本文只记录建议和方案，没有改代码。数据来自 2026-11-01 22:00 至 2026-11-02 01:10（UTC）59137 本地账号的 usage 记录和日志。线上版本 0.0.228，源码与当前 main 一致，文中行号以 main 为准。

## 背景

近 3 小时本地请求约 4200 条，失败 234 条（5.6%），其中约八成来自 6 个会话。这些会话的共同点：同一个请求换哪个账号都失败，对外返回 502，客户端把它当成临时错误立刻重发。去掉这 6 个会话，错误率只有 0.92%。下面两条建议分别针对其中两类错误。

## 建议一：超大请求被上游 400 拒绝时，让客户端去压缩

现象
- 一个会话的请求体有 34 MB、728 条历史、约 41.7 万 token，上游返回 400 `Improperly formed request`。
- 我们对外返回 502，客户端一直重发，半小时内失败 54 次以上。3 小时内超过 450 KB 的本地请求共 62 条，全部失败。

原因
- 线上 `payloadGuardMode=on_too_long`：发送前不裁剪，只有上游明确报"过长"时才处理。"过长"由 `classify_bad_request_reason` 识别，例如 `CONTENT_LENGTH_EXCEEDS_THRESHOLD`、`input is too long`（`src/kiro/provider.rs:15582`）。
- 这次上游报的是"格式不正确"，被归为 `malformed_request`。所以既不裁剪，也不会按 `payloadTooLongHandling=client_compaction` 返回 `prompt is too long`。

建议
- 同时满足下面两个条件时，按"输入过长"处理：上游 400 被归为 `malformed_request`，且本次请求权重超过 `payloadGuardKiroMaxWeight`（线上 1,300,000）。处理走现有的过长流程，默认返回 400 `prompt is too long`，Claude Code 收到后会自动压缩。上面那个请求的权重约 3500 万。
- 判定只看权重，不看字节数。权重上限是服务端现成的"明显超限"标准，可以避免把真正的格式错误误判成过长。未超过上限的 400 维持现状。成功的请求不受影响。
- 测试覆盖三种情况：
  - 超限且格式错误：返回过长响应；
  - 未超限且格式错误：保持原行为；
  - Claude Code 自己的压缩请求：仍按裁剪重试。

## 建议二：空回复不要一路换满 10 个账号

现象
- "空回复"指上游返回 200，但只有用量和元数据，没有任何内容。同一个请求换号重试后，大多数仍然一直是空回复。
- 近 12 小时日志里，有 840 个请求触发过空回复换号。按最终发出次数统计：

| 共发出几次 | 成功 | 失败 |
|---|---|---|
| 2 | 9 | 25 |
| 3 | 2 | 13 |
| 4~9 | 0 | 191 |
| 10 | 0 | 596 |

另有 4 个请求没找到 usage 记录。能救回来的请求都在第 2、3 次就成功了，从第 4 次起没有一个成功；有 596 个请求发满 10 次，最终仍然失败。

原因
- 空回复重试和其他首输出前重试共用 `kiroUpstreamStreamRetryMaxAttempts`（线上 10，默认 6），同时还受 `inferenceUpstreamMaxAttempts`（线上 10，后台允许 1~10）约束。如果只想少试几次空回复，就得连流读取错误、静默超时等重试一起调小，代价太大。
- 次数用完后，对外返回 502（流式返回 error 事件），客户端当成临时错误继续重发。

建议
- 给空回复单独设一个上限（方案见下一节），线上建议设为 3。
- 次数用完后，要不要把对外状态码改成不可重试的 4xx，需要另外权衡：
  - 好处：4xx 能让客户端停止自动重发；
  - 代价：空回复有时只是偶发，改成 4xx 后用户会直接看到报错。

  建议先只做次数上限，观察一段时间再决定。

## 方案：新增"空回复最多尝试次数"配置项

配置项
- 名称 `kiroUpstreamUsageOnlyRetryMaxAttempts`，后台显示为"空回复最多尝试次数"。
- 含义：同一个请求在首输出前，最多允许出现几次空回复（包含第一次）；达到上限后不再换号，按现有方式失败。
- 取值 0~100，默认 0。0 表示沿用 `kiroUpstreamStreamRetryMaxAttempts`，所以升级后行为不变；1 表示空回复不重试。
- 实际次数同时受三项约束：本项、`kiroUpstreamStreamRetryMaxAttempts`（首输出前重试总次数）、`inferenceUpstreamMaxAttempts`（单个请求的发送硬上限），哪个先到算哪个。
- 本项只影响空回复。流读取错误、静默或首输出超时、2xx 错误事件、EventStream 不完整这几类的重试次数不变。

计数方式
- 现在所有首输出前重试共用一个计数：流式用 `state.attempt_number`，非流式用 `non_stream_status_retry_attempt`，空回复和其他原因混在一起计。
- 新增一个计数，只在空回复时加一。空回复要重试，需要同时满足三个条件：
  - 空回复次数小于本项；
  - 总次数小于 `kiroUpstreamStreamRetryMaxAttempts`；
  - 请求的发送预算还没用完。
- 举例：先读取错误 1 次、再空回复 2 次，本项为 3 时，还能再试一次。

改动位置
- `src/model/config.rs`：新增字段，serde 默认值 0，默认配置里同步加上。
- `src/anthropic/handlers.rs`：
  - 给 `LocalStreamRetryConfig`（146 行起）加上限字段，在 `from_runtime_config`（163 行附近）里把 0 解析成共用上限；
  - 流式：空回复分支（12289 行附近）在调用 `retry_stream_before_downstream_commit`（11452 行）之前检查空回复计数，计数放在流的状态里；
  - 非流式：在 13777~13780 行的重试条件里加上空回复计数；
  - `RequestRuntimeConfig` 的定义、默认值和拷贝处（994、1072、1171 行附近）同步加字段。
- `src/admin/types.rs`、`src/admin/service.rs`：读取、更新和校验（0~100），校验写法参照 `kiroUpstreamStreamRetryMaxAttempts`（`service.rs:6787`）。
- 前端：`ui/src/types/api.ts`、`ui/src/lib/runtime-config-defaults.ts`、`ui/src/features/runtime/runtime-page.tsx`，输入框放在"首输出前最多尝试"旁边。旧后台 `admin-ui` 的对应位置一起加上；如果确认已经废弃，就跳过。
- 不需要数据迁移：运行配置以 JSON 存在 PG 里，缺这个字段时取默认值 0。

测试
- 配置：缺这个字段时反序列化为 0；后台写入 101 时被拒绝。
- 非流式：
  - 本项为 2、上游一直空回复：共发 2 次后失败；
  - 本项为 0：和现在一样，发满共用上限。
- 流式：同样测上面两种情况；再加一个混合场景，读取错误 1 次后出现空回复，两个计数各自生效。
- 本项大于共用上限时，以共用上限为准。

上线步骤
1. 发版后本项默认为 0，行为不变。
2. 在后台改成 3，热加载生效，不用重启。
3. 对比改动前后的三项数据：空回复导致的失败条数、每个失败请求的平均发送次数、本地错误率。预期失败条数基本不变（第 3 次之后本来也救不回来），账号调用次数明显下降。
