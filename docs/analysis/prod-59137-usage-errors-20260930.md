## 1. 上游 5xx 后的重试 100% 变成 400（疑似程序问题，未修）

现象：
- 首次尝试上游返回 500（"Encountered an unexpected error…"），耗时 10～120 秒；随后换号重试，第二次尝试 **全部** 返回 400 `Improperly formed request`，耗时约 0.5 秒。
- 统计：第一次尝试为 500 的请求 137 条，第二次尝试结果 129 条 `malformed_request`、8 条 `reasoning_malformed_request`，**没有一条成功**。504 后重试同样变成 400。
- 对照：首次尝试为 400（签名）、402、403 的请求换号或同号重试，第二次尝试基本都成功（8322 + 312 + 25 + 5 条）。
- 模型以 `claude-opus-5-5` 为主（87 / 137），idc 与 social 账号都有，与账号类型无关；非 500 场景下这些账号对同模型的成功率正常。

分析：
- 重试请求体与首次完全一致：`conversationState.agentContinuationId` 在转换时生成一次（`src/anthropic/converter.rs:461`），`conversationId` 也不变，重试不会重新生成。
- 400/402/403 重试成功说明"同一标识重发"本身不被拒绝；只有上游已经开始处理（5xx/超时）之后重发才被判为格式错误。推断 Kiro 在 5xx 后把这组会话/延续标识标记为已占用，同标识重发被拒。
- 这是推断，尚未用受控实验证实。

建议（待确认后再改）：5xx / 超时后的换号重试重新生成 `agentContinuationId`（必要时也换 `conversationId`，但会影响粘性与缓存命中），并用一次受控实验确认。

## 2. 首输出前静默约 180 秒后客户端断开（程序行为 + 上游慢，未修）

现象：
- `client_dropped` 共 1009 条，其中 **669 条在任何输出之前断开**，持续时间集中在 180～210 秒（均值 185 秒，p90 188 秒），全部为流式请求。
- 这些请求的上游响应头均已返回 200（`response_headers_received`），但上游约 180 秒内没有产生任何内容；其中 159 条先经历了一次同号签名重试。
- 以 `claude-opus-5-5` 为主（594 / 669），路由分布与流量分布一致（minea 535、cc 51、ha 37、v1 35）。

分析：
- 开启"首输出前流式换号"时，代理在向客户端发出第一个 SSE 字节前不发送 message_start，也不发送保活（`src/anthropic/handlers.rs` 保活分支 `!downstream_committed && retry_plan.is_some()` 直接跳过），目的是保留换号重试的机会。0.0.179 的心跳改动没有改变这一点。
- 上游长时间无输出时，客户端或中间代理在约 180 秒处因收不到任何字节而断开。
- 上游侧：opus-5.5 首输出前静默 180 秒本身异常。0.0.179 已对 opus-5 家族停止注入"可见 thinking"策略（该策略在本地实测会让 opus-5.5 只返回 usage 即结束），可能改善，但现网未部署，无法确认。

建议（需决策）：首输出前等待超过一定时间（如 20～30 秒）仍无输出时，放弃首输出前重试并开始下发 message_start 与保活；或把该阈值做成配置。

## 附：第 2 项方案（待确认，未实现）

目标：请求尽量成功；上游长时间无输出时尽早释放连接和账号并发，不无限占用。

现状：开启首输出前换号时，首个上游内容事件之前代理不向客户端写任何字节（不发 message_start，也不发保活），唯一的上限是流式静默超时 180 秒。由于没有写入，客户端断开也探测不到，上游连接和账号并发会一直占到 180 秒。

方案（两个新运行配置，所有路由一致，页面可配）：

1. `streamPreOutputHoldSecs`（首输出前静默保留窗口，默认 15 秒，0–60）
   - 窗口内保持现状：不写字节，上游失败可以无感换号重试。
   - 超过窗口仍无输出：提交下游，发出 message_start，并按 `streamKeepaliveIntervalSecs` 发保活。之后不再做首输出前换号（与现在"已提交"的语义一致）。
   - 作用：客户端和中间代理不再因零字节而断开；开始写入后，客户端断开能在下一次保活时被发现，随即取消上游并释放并发。
2. `streamFirstOutputTimeoutSecs`（首个内容事件等待上限，默认 90 秒，0 表示关闭，回落到静默超时）
   - 从上游响应头到首个内容事件（文本、thinking、工具调用）超过该值：主动断开上游并释放账号并发。
   - 尚未提交下游：按现有首输出前重试预算换号重试一次。
   - 已提交下游：以 SSE `overloaded_error` 结束，Claude Code 会自行重试。
   - usage 记为 upstream_timeout，终止原因 first_output_timeout，便于统计。
3. 非流式请求同样适用第 2 条（非流式无法保活，只做首事件上限 + 首输出前换号）。
4. 已有输出之后的静默仍由现有 `kiroUpstreamStreamIdleTimeoutSecs` 控制，不变。

效果预估（按现网 669 条样本）：客户端最多等 15 秒就能看到 message_start 和保活，不再在 180 秒时断开；上游若 90 秒仍无内容，连接在 90 秒而不是 180 秒释放，并有一次换号机会。

## 附：`invalid image data for media_type: image/jpeg` 分析

- 这是本地转换阶段的拒绝，请求没有发到 Kiro（`src/anthropic/converter/content.rs`）。
- 本地做了两步校验：
  1. 解码 base64 后按文件头识别格式，只认 PNG、JPEG、GIF、WebP 四种（与 Anthropic 官方支持范围一致）；声明类型与文件头不一致时按文件头修正。
  2. 轻量结构校验：JPEG 必须以 `FF D8` 开头且**以 `FF D9` 结尾**；PNG 必须含 IEND；GIF 必须以 `;` 结尾；WebP 检查 RIFF 长度。
- 现网 3 条均报 image/jpeg。usage 不保存图片内容，无法确认是哪一步失败。可能原因：
  - 图片确实损坏或被截断（base64 不完整）；
  - JPEG 在 EOI 之后带了尾部数据（部分手机、截图或编辑工具会追加元数据或填充字节），本地"必须以 FF D9 结尾"会误判为非法，但这类图片通常能被正常解码；
  - 实际是 HEIC、AVIF、BMP 等格式却标成 image/jpeg——这类 Kiro 也不支持，属于真实的格式问题。
- 格式种类并不算少：四种格式就是官方支持范围，扩展格式没有意义，上游同样会拒绝。
- 是否保留本地校验：
  - 文件头识别有价值：能修正错误的 media_type，让本来可用的图片正常发送，建议保留。
  - 结构校验（尾部标记）收益小、有误判风险：Kiro 自己会判断，对损坏图片返回 400 `Could not process image`（现网已有 4 条 IMAGE_FORMAT_UNSUPPORTED），错误同样能到达客户端，代价只是一次快速的上游调用。
  - 建议：保留文件头识别与 media_type 修正，去掉结构校验（或只记日志不拒绝），交给 Kiro 判断。

## 附：JSON 读取报错核对

逐条检索了现网 usage 的错误文本、错误详情和近 24 小时服务日志，没有发现代理解析 JSON 失败（serde、parse、expected value 等）的记录。可能被看成"JSON 读取报错"的有两类：

- `content_type=json`：这是上游错误响应体的类型标记，意思是"上游返回了一个 JSON 格式的错误"，例如 `reason=malformed_request`，不是解析失败。
- `读取响应失败: error decoding response body` / `upstream stream read error: error decoding response body`（共 147 条）：这是 HTTP 响应体传输中断（连接被重置、分块传输未完成），发生在读取网络数据阶段，与 JSON 无关，归为上游 / 网络问题。
