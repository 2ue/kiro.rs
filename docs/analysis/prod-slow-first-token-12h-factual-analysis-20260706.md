## 十四、不同慢首字情况说明

### 情况一：等上游响应头之前最长

- 要判断单条请求是否包含重试，必须看调用链路里的尝试次数和每次尝试结果。

### 情况二：响应头已经到了，但首个流包很晚

数量：`703` 条为该类等待最大；另有 `630` 条请求的“响应头后到首包”超过 10 秒。

首次输出接近首个流包

- 这类请求里，上游 HTTP 响应头已经返回，但响应体第一段流式数据没有马上到。

## 十六、可能原因分析

本节开始是基于上面事实链和本地代码结构做出的原因判断。这里不再只描述现象，而是说明哪些原因被当前证据支持、支持到什么程度、还缺什么证据。

### 原因一：容量控制按“请求条数”而不是“请求重量”工作

判断：高概率。

证据：

- 最近 12 小时单分钟成功流请求最高 `220`，单分钟 token 体量最高约 `7,713 万`。
- 慢首字请求中，token 体量 `>=300k` 的记录有 `10,498` 条，占慢首字请求的大多数。
- 最近 12 小时估算在途流请求最高 `199`。
- 本地凭据全局并发未限制。
- 外部池只有一个启用，单池并发 `300`，外部池全局并发未限制。
- 本地代码里，本地凭据调度主要按账号 in-flight 条数、错误率、延迟、选择压力等评分；外部池选择主要按池 in-flight 和并发上限判断。当前没有把本次请求的输入、缓存读取、缓存写入、工具数量、请求体大小作为容量权重。

原因解释：

当前调度里，一个很轻的请求和一个超大上下文请求都基本只占一个并发槽。但从现网数据看，很多慢首字请求携带几十万 token 体量。这样会出现页面看起来只是几十到几百 RPM，但真实上游负载已经很高的情况。

这不是单纯“RPM 高不高”的问题，而是“每个请求有多重”的问题。

直接后果：

- 轻请求和重请求互相竞争同一批账号/外部池容量。
- 大量长流式请求同时在途时，后续请求即使 RPM 不夸张，也会排到较长等待。
- 外部池和本地凭据都会出现这个问题，因为两边都按请求条数做容量控制。

### 原因二：外部池 fallback 在高峰时集中打到单个启用外部池

判断：高概率。

证据：

- 当前未删除外部池 `8` 个，但启用外部池只有 `1` 个。
- 唯一启用外部池单池并发 `300`，外部池全局并发上限为 `0`，即不限制。
- 外部池容量模式为 wait，最大派发等待 `300s`。
- 11:15-11:30 高在途窗口，成功流请求 `1,914` 条，首字超过 10 秒 `1,675` 条。
- 11:15-11:30 高在途窗口主要走外部池，其中 Opus 4.8 外部池 `1,184` 条成功流请求里 `1,046` 条首字超过 10 秒。
- 该窗口日志里同时出现 `427` 次 429、`80` 次 timeout、`59` 次 Redis 调度热路径、`6,820` 次 Postgres 连接池等待。

原因解释：

11:15-11:30 的高峰并不是本地凭据为主，而是外部池为主；当前外部池只有一个启用，配置允许非常高的单池并发，并且全局不限制。这个组合会让外部池成为单点承压位置。

现有数据不能证明外部池上游本身一定慢，但可以证明这个窗口的慢首字主要集中在外部池路线，并且外部池配置允许大量请求堆到唯一启用池上。

直接后果：

- fallback 流量容易集中到单个外部池。
- 外部池进入慢状态时，没有足够的池间分散能力。
- 外部池排队等待上限为 300 秒，容易把请求挂很久，而不是快速失败或限流。

### 原因三：本地凭据和外部池的并发上限都偏宽

判断：高概率。

证据：

- 本地凭据全局并发上限为 `0`，表示不限制。
- 当前启用本地账号 10 个，其中 3 个并发 `50`、4 个并发 `20`、3 个并发 `15`。
- 外部池全局并发上限为 `0`，表示不限制。
- 唯一启用外部池单池并发为 `300`。
- 最近 12 小时估算在途流请求最高 `199`，95 分位 `78`。

原因解释：

流式请求会长期占用上游连接和模型处理资源。并发上限如果只按连接数设置，而不考虑每条请求的上下文体量，就会允许大量重请求同时进入上游。现网里已经出现最高 `199` 条在途流请求。

直接后果：

- 请求没有在网关侧形成有效背压。
- 慢首字会向后续请求扩散。
- 上游已经慢时，系统仍可能继续放入大量新请求。

### 原因四：重试策略会放大高峰压力

判断：高概率。

证据：

- 本地凭据最大重试次数为 `100`。
- 慢首字请求中，记录到多次尝试的有 `715` 条。
- 慢首字尝试链里出现 `787` 次 429。
- 慢首字尝试链里出现 `54` 次 500 后重试，平均单次尝试耗时约 `70.35s`。
- 慢首字尝试链里出现 `339` 次 400 请求无效。
- 多次尝试会计入页面上的总耗时和首字等待。

原因解释：

429、500、timeout 出现时，系统继续尝试其他账号或外部池。这对可恢复故障是必要的，但在高峰时会增加新一轮上游请求。尤其本地凭据最大重试次数为 `100`，即使实际未必打满，也说明配置上限非常宽。

直接后果：

- 已经失败或被限流的请求会增加额外上游调用。
- 页面上的“上游响应头前等待”可能包含失败尝试、换号、最终成功尝试的累计时间。
- 高峰时重试可能把压力继续推给其他账号或外部池。

### 原因五：部分时段存在本地基础设施慢路径，但它不是所有慢首字的统一原因

判断：中高概率，按时段成立。

证据：

- 11:15-11:30 高在途窗口日志里，Postgres 连接池等待命中 `6,820` 次。
- 同一窗口有 `59` 次 Redis 调度热路径命中。
- 19:00 和 20:00 小时段 usage 写入慢日志分别为 `132` 和 `220`。
- 20:41 机器快照中 app 容器 CPU 为 `182.15%`。
- 当前资源快照未显示内存耗尽或磁盘满。

原因解释：

这些日志证明某些时间段存在本地 Redis、Postgres、usage 写入、CPU 压力信号。它们可能增加请求前置等待、调度等待、记录写入压力或后台负载。但从 12 小时慢首字拆解看，最大等待多数出现在“拿到上游响应头之前”，而当前记录无法进一步拆分其中到底有多少是本地调度、多少是上游网关、多少是模型排队。

直接后果：

- 当前数据能证明本地慢路径存在，不能证明所有慢首字都由本地慢路径导致。
- 后续必须增加更细的阶段记录，才能把“本地等待”和“上游等待”拆开。

### 原因六：不同模型的慢点不同，不能用同一套限流策略处理

判断：高概率。

证据：

- Opus 4.8 是慢首字数量最大来源，慢首字 `13,574` 条。
- Sonnet 5 慢首字 `1,752` 条。
- Opus 4.8 的响应头 95 分位约 `55.37s`。
- Sonnet 5 的响应头后到首包 95 分位约 `48.95s`。
- `/ha` + Sonnet 5 的响应头后到首包 95 分位约 `64.45s`。

原因解释：

Opus 4.8 的慢更集中在响应头前；Sonnet 5 的慢更明显体现在响应头已经返回后，首个流包迟迟不到。两者表现不同，说明模型维度、路径维度需要分别治理。

直接后果：

- 只用全局 RPM 或全局并发无法精细控制。
- 同一账号池或外部池同时承载不同模型，会让慢模型影响快模型。

### 原因七：Payload guard 不是 10 秒级慢首字主因，但会贡献 CPU 和后台压力

判断：中高概率。

证据：

- 慢首字请求中，Payload 处理超过 100ms 的只有 `220` 条，占慢首字请求 `1.3%`。
- 请求体 `>=1MB` 的慢首字请求中，Payload 平均处理约 `52.1ms`，95 分位约 `114.6ms`。
- 多个小时 Payload guard 日志大量出现。
- app 容器 CPU 快照较高。

原因解释：

Payload guard 的单次耗时通常不是秒级，因此不能解释大量 10 秒、30 秒、60 秒首字慢。但 Payload guard 日志大量出现，说明它在高峰时会频繁运行，可能贡献 CPU 消耗、JSON 处理压力和后台诊断写入压力。

直接后果：

- 不应把首字慢的直接原因简单归为 Payload guard。
- 但仍需要优化 Payload guard 的开关、轻量模式和大 body 处理策略，避免高峰 CPU 放大。

### 原因八：当前观测字段不足，无法把“响应头前等待”继续拆开

判断：确定存在。

证据：

- 页面现有字段能看到总耗时、Payload 处理、上游响应头、首个流包、首次输出。
- 当前“上游响应头”是累计时间，里面可能包含本地调度、等待并发槽、重试失败尝试、连接上游、上游网关排队、模型预处理等。
- 当前 usage 记录有尝试链，但没有把最终成功尝试的内部阶段独立拆出来。

原因解释：

现网最大类慢首字是“响应头前等待最大”，但这个阶段太粗。没有更细的阶段记录时，只能判断“这段时间最大”，不能直接判断具体卡在本地调度还是上游处理。

直接后果：

- 下一次定位会继续卡在“响应头前等待”这个黑盒。
- 必须补充阶段耗时，才能精确归因。

## 十七、解决方案

解决方案分三层：立即可配置止血、短期代码修复、长期根治。

### A. 立即可配置止血

这些方案不需要改代码，但需要在低峰期逐项调整并观察。调整前应记录当前配置，调整后观察 30-60 分钟。

1. 给本地凭据设置全局并发上限。

当前本地凭据全局并发为不限制。建议设置一个明确上限，避免所有账号的并发简单相加后形成过高在途请求。上限具体值要按业务承受能力灰度；可以先从保守值开始，再结合首字 95 分位、429 数、排队数观察。

预期效果：

- 网关侧形成背压。
- 降低同时进入上游的流式请求数量。
- 可能增加排队或 503，需要配合队列上限和等待时间。

2. 降低高并发账号的单账号并发。

当前仍有 3 个启用账号单账号并发为 `50`。建议优先把这类账号降到和其他账号同一量级，避免单账号承受过多重请求。

预期效果：

- 降低单账号被打爆或触发 429 的概率。
- 慢请求不会过度集中到某个账号。

3. 给外部池设置全局并发上限，并降低唯一启用池的单池并发。

当前只有一个外部池启用，单池并发 `300`，外部池全局并发不限制。建议先给外部池全局设置明确上限，再调低单池并发。

预期效果：

- 防止 fallback 流量全部堆到唯一外部池。
- 降低 11:15-11:30 这类外部池高在途窗口再次出现的概率。

4. 缩短外部池最大派发等待。

当前外部池最大派发等待为 `300s`。高峰时这会让请求长时间挂起。建议降低等待上限，让系统更早返回容量不足或进入本地救援逻辑。

预期效果：

- 减少客户端长时间无首字等待。
- 暴露真实容量不足，而不是把请求挂在队列里。

5. 降低本地凭据最大重试次数。

当前本地凭据最大重试次数为 `100`。建议将普通请求的最大重试降到很小的值，例如 `2-3` 级别，并区分错误类型：

- 429：进入冷却，不做大量横向重试。
- 400 输入过长：只允许 payload guard 确认缩减后重试一次。
- 403/额度/风控：快速排除或冷却，不连续打。
- 500/timeout：有限重试，并记录重试累计耗时。

预期效果：

- 降低错误高峰时的放大效应。
- 减少一次用户请求产生多次上游请求的情况。

6. 对 Opus 4.8 和 Sonnet 5 分别限流。

现网证据显示两者慢点不同。建议不要只用全局限流，而要按模型设置不同的并发/RPM。

预期效果：

- 慢模型不拖垮其他模型。
- Sonnet 5 这种 header 后首包慢的情况可以单独观察。

### B. 短期代码修复

1. 增加“请求重量”估算，并写入 usage。

每个请求进入调度前，计算一个轻量的重量分：

- 输入 token。
- 缓存读取 token。
- 缓存写入 token。
- 请求体字节数。
- 工具数量。
- 工具 schema 字节数。
- 图片数量和图片估算 token。
- 请求是否流式。
- max_tokens。

这个重量分先不一定参与调度，第一步先记录到 usage 和日志中。这样下一次能直接按“轻/中/重/超重请求”分组看慢首字。

2. 本地凭据和外部池统一使用加权并发。

当前一个请求占一个并发槽。改为：

```text
轻请求占 1 个权重槽
中请求占 2-3 个权重槽
重请求占 5-10 个权重槽
超重请求进入专门队列
```

本地凭据和外部池都使用同一套重量计算，只是容量后端不同。

预期效果：

- 轻请求不会被重请求完全挤压。
- 长上下文请求不会以“1 个并发”的成本大量进入上游。

3. 增加模型级和路径级容量池。

建议增加：

- Opus 4.8 独立容量。
- Sonnet 5 独立容量。
- `/cc` 独立容量。
- `/ha` 独立容量。
- 外部池 fallback 独立容量。
- 外部池 direct 独立容量。

预期效果：

- `/cc` + Opus 4.8 不会挤压所有请求。
- `/ha` + Sonnet 5 的首包慢可以单独限流和熔断。

4. 重试策略按错误类型改为硬规则。

建议规则：

- 429：账号或池进入冷却；同一请求最多换号一次或两次。
- 400 输入过长：不横向换号；只做一次缩减后重试。
- 403 风控/额度：标记账号状态，不继续多次尝试。
- 500/timeout：有限重试，且重试前检查全局和模型容量。
- 单请求重试累计耗时超过阈值后停止。

5. 外部池 fallback 前做容量判断。

当本地池不可用要 fallback 外部池时，先检查外部池全局和单池当前压力。如果外部池已经高压，不应继续把本地失败流量推过去。

6. Payload guard 做轻量模式和完整模式分离。

建议保留两种模式：

- 轻量模式：只做字节统计、图片轻量识别、必要协议修复，不深度裁剪。
- 完整模式：只在输入过长、超阈值、明确需要裁剪时执行。

预期效果：

- 降低高峰 CPU 和 JSON 处理压力。
- 不把所有请求都拖进复杂处理。

### C. 长期根治

1. 建立“调度成本模型”。

调度不能只看请求数，必须看请求重量。建议最终形成：

```text
实际调度压力 = 基础请求成本 + token 成本 + cache 成本 + tool 成本 + image 成本 + 流式占用成本 + 重试惩罚
```

每个账号、每个外部池、每个模型都有自己的压力上限。

2. 建立自适应熔断。

按模型、路径、账号、外部池记录最近窗口：

- 首字 95 分位。
- 响应头前等待 95 分位。
- 响应头后到首包 95 分位。
- 首包后到有效输出 95 分位。
- 429 数。
- timeout 数。
- 输入过长数。
- 平均请求重量。

超过阈值时自动降权、冷却或降低并发。

3. 建立轻重请求分离队列。

至少分三类：

- 轻请求队列。
- 普通请求队列。
- 重上下文请求队列。

重请求不能无限占用普通请求容量。

4. 增加外部池多池健康评分。

外部池不能只有 enabled/disabled 和并发。需要记录：

- 近 1 分钟首字。
- 近 5 分钟 429。
- 近 5 分钟 timeout。
- 上游响应头等待。
- 首包等待。
- 错误率。
- 当前权重在途。

根据健康评分选择池，而不是只按优先级和 in-flight。

## 十九、建议实施顺序

### 第一步：配置止血

目标：先降低高峰时在途请求和重试放大。

建议顺序：

1. 设置本地凭据全局并发上限。
2. 降低单账号并发 `50` 的账号。
3. 设置外部池全局并发上限。
4. 降低唯一启用外部池单池并发。
5. 降低本地凭据最大重试次数。
6. 缩短外部池最大派发等待。

验收指标：

```text
首字超过 10 秒比例下降
首字 95 分位下降
429 不继续升高
在途流请求下降
token/min 峰值更平滑
外部池 fallback 高峰不再单池堆积
```

### 第二步：观测补齐

目标：把“响应头前等待”拆开。

优先实现：

1. 请求级阶段差值。
2. 每次 attempt 的上游响应头、首包、首次输出。
3. 调度快照。
4. 请求重量。

验收指标：

```text
任意慢请求能直接看出卡在本地调度、重试、最终上游、首包还是有效输出
```

### 第三步：加权调度

目标：让重请求占更多容量。

优先实现：

1. 请求重量计算。
2. 本地凭据加权并发。
3. 外部池加权并发。
4. 模型级容量池。
5. 重请求队列。

验收指标：

```text
轻请求 p95 首字不被重请求拖垮
重请求在途数受控
token/min 峰值受控
429 和 timeout 下降
```

### 第四步：自适应治理

目标：系统自动对慢模型、慢账号、慢外部池降权。

优先实现：

1. 模型+账号健康评分。
2. 模型+外部池健康评分。
3. header 前等待、首包等待、有效输出等待分别统计。
4. 自动降权、冷却、恢复。

验收指标：

```text
某个模型或池进入慢状态后，新请求自动减少进入该通道
恢复后自动逐步放量
```

## 二十、当前数据不能证明的内容

以下内容不能从本次只读数据直接证明：

- 不能证明每一条慢首字都是上游模型本身导致。
- 不能证明每一条慢首字都是本地调度导致。
- 不能证明请求体越大一定越慢。
- 不能证明工具数量越多一定越慢。
- 不能用 20:41 的机器资源快照代表最近 12 小时所有时间点。
- 不能仅凭日志关键词命中数等同于唯一慢请求数量。
- 不能仅凭当前字段拆出“响应头前等待”中本地调度和最终上游等待各占多少。
- 不能仅凭请求体大小或工具数量单独决定慢首字原因。

## 二十一、页面展示口径说明

当前页面上的几个耗时不是同一种口径：

| 页面名称 | 实际含义 | 是否可直接相加 |
| --- | --- | --- |
| 总耗时 | 从本条 usage 记录开始到记录完成的累计时间 | 不可和下面几项相加 |
| 请求检查 | 实际更接近 Payload guard / body 保护处理耗时 | 可以单独看 |
| 上游响应头 | 从请求开始到拿到上游 HTTP 响应头的累计时间 | 是累计时间点 |
| 首个流分片 | 从请求开始到第一次读到上游响应体 bytes 的累计时间 | 是累计时间点 |
| 首次输出 | 从请求开始到第一次识别到有效输出的累计时间 | 是累计时间点 |
| 分片到输出 | 首个流分片到首次有效输出之间的差值 | 是阶段差值 |
| 输出前分片 | 首次输出前已经读到多少个无有效输出的流包 | 是计数 |
| 输出前事件 | 首次输出前已经解析到多少个无有效输出的事件 | 是计数 |

更容易理解的展示方式应该是：

```text
Payload 处理
响应头前等待
响应头到首包
首包到首输
首输到结束
重试/换号累计
```

其中“响应头前等待”应进一步结合调用链路拆成：

```text
本地调度/等待
失败尝试累计
最终成功尝试等待响应头
```

当前页面还没有把这些阶段完全拆开。
