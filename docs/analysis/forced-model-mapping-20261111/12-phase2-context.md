# 12 第二阶段：上下文方案（摘要检查点）

## 1. 现状问题

| # | 问题 | 后果 |
|---|---|---|
| C1 | 预留输出取 `min(max_tokens, 64K)`。Claude Code 对 5.x 模型发 `max_tokens: 128000`，于是预留 64K，输入预算只剩 (200K − 64K) × 95% ≈ 129K | 实际能用的窗口只有 65%。Kiro 不接收 `max_tokens`，实际输出极少超过 32K |
| C2 | 超出预算时按"清理旧工具结果 → 删最早的轮次 → 截断大块"处理 | 删掉的轮次彻底丢失。长任务后期会忘记早期的约定、决策和改过的文件 |
| C3 | 退避只在普通路径生效，搜索路径绕过 | 见 11 篇 E3 |
| C4 | 上游仍判超长时只重试一次，字节上限还被误封到 180KB | 见 11 篇 E7 |
| C5 | 客户端不知道真实窗口是 200K（对外 input 按客户端原始量报，D4） | 客户端要到 967K 才自己压缩。200K–967K 之间全靠服务端处理 |

C5 是有意的设计：如果报真实的上游 input，客户端看到的上下文百分比和压缩时机都会暴露 200K。所以服务端必须在 200K 内把会话长期保持下去，而且不能丢信息。

## 2. 方案：摘要检查点

思路和 Claude Code 自己的压缩相同（"把早期对话浓缩成一段工作记录，后面接着做"），只是放在服务端完成，对客户端不可见。

```
客户端发来：  [m1 用户任务] [m2] [m3] … [mB] … [mN 当前轮]
发给上游：    [m1 用户任务 + 早期记录(摘要 m2..mB-1)] [mB] … [mN]
  └─ mB 一定是 assistant 消息
```

- **保留 m1 原文**：Claude Code 把 CLAUDE.md、skills 列表、用户的原始任务都放在首条用户消息里，这些不能被摘要。m1 超过预算的 25% 时，截取头尾。
- **切点 B 一定落在 assistant 消息上**：这样 `[用户：m1 + 摘要] → [assistant mB] → [用户 mB+1] …` 的角色交替天然正确。tool_use / tool_result 的配对也不会被切开（mB 里的 tool_use 对应的结果在 mB+1）。
- **摘要的形态**：在 m1 末尾追加一个文本块，用 `<system-reminder>` 包裹，与现有注入一致：

  ```
  <system-reminder>
  Earlier in this conversation (condensed record of the turns that are no longer shown):
  …摘要正文…
  </system-reminder>
  ```

### 2.1 检查点与缓存稳定

- 对每条消息算一个累积哈希：h_i = sha256(h_{i−1} ‖ canon(m_i))。canon 只取角色、文本、tool_use 的 id/name/input、tool_result 的 tool_use_id；不取 tool_result 的内容、thinking、图片、cache_control。这样客户端事后改写旧内容（Claude Code 的 microcompact 会把旧工具结果换成占位文字、cache_control 每轮挪位置）都不会让检查点失效。
- 检查点 = (h_B → 切点 B、摘要正文、覆盖的 token 数)。存在进程内的有界表里（按条数和字节数双上限，LRU 淘汰）。
- 查找：从后往前找第一个命中的 h_i，就是这段对话最近的检查点。
- 同一个检查点会一直复用到尾部再次长满。期间发给上游的前缀（m1 + 摘要 + mB…）逐字不变，prompt cache 照常命中。

### 2.2 阈值（滞回）

```
预算 B        = (目标窗口 − 预留输出) × (1 − 安全余量)
预留输出      = clamp(max_tokens, 8K, 32K)        ← C1：上限由 64K 改为 32K（可配置）
预压缩线      = 预算 × 0.75     超过就在后台生成下一个检查点，本次请求照常发送
压缩后目标    = 预算 × 0.45     新检查点要让 [m1 + 摘要 + 尾部] 落到这条线以下
```

200K 窗口下：预算约 160K，预压缩线约 120K，压缩后目标约 72K。从一次压缩到下一次之间，可以再增长约 50K。

### 2.3 流程（每个强制模式请求）

1. 用客户端原始消息算出累积哈希，找最近的检查点 c，按 c 拼出请求。没有检查点时就是原请求。
2. 估算 token：
   - **≤ 预压缩线**：直接发送。
   - **预压缩线 < 估算 ≤ 预算**：直接发送；同时在后台为这段对话生成下一个检查点（同一个 h_B 只会有一个任务在跑）。
   - **> 预算**：
     a. 后台任务正在生成或已经生成好下一个检查点 → 最多等摘要超时时间（默认 120 秒），拿到后按新检查点重新拼；
     b. 没有 → 同步生成（同样受超时限制）；
     c. 超时或失败 → 本次走硬裁剪兜底（现有 L2/L4/L5），摘要任务不取消，继续在后台完成，下一轮就能用上。
3. 拼完仍超出预算（尾部本身太大，比如单个工具结果有 150K）→ 在尾部上执行硬裁剪（L2 清旧工具结果 → L5 截断最大块）。m1 和摘要不动。

### 2.4 选择切点 B

从最后一条消息往前累加 token，直到尾部达到 `压缩后目标 − m1 − 摘要预留(8K)`。B 取这个位置及之后的第一条 assistant 消息，并且要求 B > c.B（检查点只向后推进）。找不到满足条件的 B（例如尾部只有一条巨大的用户消息）时，直接走硬裁剪。

### 2.5 生成摘要

- **输入**：上一份摘要（如果有），加上 m_{c.B} … m_{B−1} 渲染成的文字记录：
  - 用户文字原文；`<system-reminder>` 块每块截到 600 字符；
  - assistant 文字原文；
  - tool_use 写成 `[assistant -> tool 名字] 入参（截到 1.5K 字符）`；
  - tool_result 截取头尾共 2K 字符。被截掉中间的长结果另附 `[notable lines]`：最多 12 句带 error / cause / note / must 等标记的句子，合计不超过 1.5K 字符。明确的发现（`NOTE:`、`root cause`、`caused by`、`decided` 等）优先入选，其余按原文顺序，避免普通代码里大量的 `error`、`must` 把文件末尾的一行结论挤掉；
  - 图片写成 `[image]`。
- **分段**：按渲染后的文字记录计算 token，超过 100K tokens 时按顺序分段滚动处理：s1 = 摘要(旧摘要 + 第 1 段)，s2 = 摘要(s1 + 第 2 段) ……
- **提示词要求的内容**：用户的目标与原话要求（关键指令原文引用）、已做出的决策和约束、涉及的文件/函数/关键代码、遇到的错误和修复、工具输出里的发现（根因、备注、取值、名字，标识符原样）、当前进度、待办和下一步。与用户使用同一种语言；只写事实；控制在约 2500 词以内。
- **原文附录**：摘要写完后，把这一段工具输出里的明确发现（同上的强标记）原文附在末尾 `## Notes from tool output (verbatim)` 之下，最多 12 条，每条 300 字符以内，摘要里已经原文引用的不重复。实测 300K 场景下，摘要模型会把长文件末尾一行 `NOTE: The root cause … cache_evict worker` 当成无关内容略去，加上附录后三档长度都能答出根因。
- **改写**：摘要文字经过身份过滤（强制规则），里面提到实际服务型号的自述改成外显型号，提到服务通道的句子删除。
- **模型**：请求的目标模型（与主请求同一个账号池），不开启思考。上游拒答（CONTENT_FILTERED 一类）按失败处理。
- **账号与预算**：走现有的调度和准入；用独立的 inference attempt 预算，不占主请求的尝试次数。
- **成本**：只记日志和内部指标，不计入用户 usage（P2-D4）。
- **失败处理**：60 秒内同一个 h_B 不再重试（负缓存），避免上游故障时每个请求都去摘要。

### 2.6 Claude Code 自己的压缩请求

`/compact` 或客户端在约 967K 时自动压缩时，会发出带完整历史的请求，末尾附上"写摘要"的指令。这类请求同样按检查点拼装：模型看到的是"m1 + 服务端摘要 + 尾部 + 压缩指令"，能够写出完整的摘要。压缩完成后，客户端的历史变成 [摘要, …]，累积哈希从头开始，旧检查点自然失效。

### 2.7 与 context_management、compaction 协议的关系

- `clear_tool_uses_*` / `clear_thinking_*`：按官方参数执行（11 篇 S5），在拼装检查点之前执行。
- `compact_20260112`（阈值压缩）：服务端检查点已经透明地完成了压缩，不向客户端返回 compaction 块；客户端继续发完整历史即可。
- 顶层 `compaction`（按需压缩，beta）：直接调用摘要引擎，对整个 messages 做一次摘要，返回 `{"type":"compaction","content":摘要}`，`stop_reason: "compaction"`，usage 为 0。
- 请求历史里带着 `compaction` 块（客户端从官方 API 切过来）：丢弃它之前的消息，把它的 `content` 当作摘要（同 2.1 的形态）。

## 3. 上游仍拒绝时

上游报上下文超长时只重试一次，不管 payload guard 怎么配置都执行：

- 目标为目标模型窗口的 75%（本地估算偏低时留出余量；第一次发出的请求已经按预算裁过）；
- 丢弃历史 thinking，截断历史和当前轮的工具结果，必要时把当前轮也裁进预算；
- 历史中的 tool_use / tool_result 转成文字，同时排除结构问题；
- 字节上限沿用 payload guard 的配置；没有配置时按窗口 × 4。

重试仍失败才返回错误。

## 4. 配置（`contextBackoff` 新增字段）

| 字段 | 默认值 | 说明 |
|---|---|---|
| `maxReservedOutputTokens` | 32000 | 预留输出上限（C1） |
| `summaryEnabled` | true | 摘要检查点开关；关闭后只用硬裁剪 |
| `summaryPrecompactRatio` | 0.75 | 预压缩线 |
| `summaryTargetRatio` | 0.45 | 压缩后目标 |
| `summaryTimeoutSecs` | 120 | 同步等待摘要的上限（5–300） |

## 5. 验收

| 编号 | 场景 | 通过标准 |
|---|---|---|
| X1 | 构造 300K / 600K / 1M token 的多轮工具会话，在第 5–10 轮埋入 3 个事实（约定的变量名、用户要求的风格、某个错误的根因），最后一轮提问 | 全部返回 200；三个事实答对的比例明显高于纯硬裁剪的对照组 |
| X2 | 同一会话连续 20 轮，每轮追加约 5K | 检查点只在越过预压缩线时推进；两次推进之间，发给上游的前缀逐字相同 |
| X3 | 摘要调用失败（注入上游错误） | 回退硬裁剪，返回 200；下一轮重新尝试生成摘要 |
| X4 | Claude Code 真实长会话（触发服务端压缩），以及 `/compact` | 无报错，任务连续；`/compact` 成功 |
| X5 | 单个工具结果 150K | 走尾部硬裁剪，返回 200 |
