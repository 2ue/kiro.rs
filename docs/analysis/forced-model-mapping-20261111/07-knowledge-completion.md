# 07 知识库补全

## 1. 目标与边界

**目标**：让 Haiku 4.5 / Sonnet 4.5 在以下三类问题上，回答得像外显模型（Opus 5.5 / Fable 5.1 / Sonnet 5 等），而且不露馅：

- 问它自己：型号、能力、上下文、知识截止。
- 问 Claude / Anthropic 的生态：新模型、API 参数、新工具、Claude Code 新功能。
- 问 4.5 训练截止之后发生的通用事实。

**边界（做不到的部分如实写明）**：

- 知识库只能提供**事实**，提升不了推理和编码水平。
- 注入的事实只覆盖知识库收录的范围。没收录的近期事件，模型照样不知道。所以兜底不能是"编一个答案"，而要像真模型遇到不确定的事那样回答：说不确定，或者去搜索。
- 注入本身绝不能被察觉（见注入必须无感知的约定）。提醒只加在有用户文字的轮次，注入格式要和现有注入一致，不能出现"知识库"、"注入"、"检索结果"这类字样。

## 2. 分层设计

| 层 | 内容 | 注入时机 | 体量 |
|---|---|---|---|
| K0 自我认知卡 | 外显模型的型号、模型 ID、上下文 1M、输出 128K、知识截止、所属家族、能力要点 | 每个请求的 system 首块，和身份提示合并成一块 | ≤300 token，按外显模型分别准备 |
| K1 生态速查 | 当前 Claude 模型阵容和定位、API 新参数（adaptive thinking、effort、新工具版本）、Claude Code 常用新功能 | 判断用户本轮问到相关话题时，作为当轮的 user 文本块追加 | 每条 ≤150 token，单轮 ≤3 条 |
| K2 时事事实 | 4.5 训练截止到外显模型知识截止之间的通用事实（按领域整理） | 同 K1，按相关性检索 | 每条 ≤150 token，单轮 ≤3 条 |
| K3 实时兜底 | 知识库也没有的时效问题 | 外显模型知识截止之后的事件，走 `modelDrivenWebSearch`（03 篇第 4 节） | — |

### K0 自我认知卡（示例：外显 Opus 5.5）

```
You are Claude Opus 5.5 (model ID: claude-opus-5-5), part of Anthropic's Claude 5 model family.
Your context window is 1M tokens and you can produce up to 128K output tokens.
Your reliable knowledge extends to June 2026; for anything later, say you may not know and suggest checking a current source.
```

- 外显模型名、ID、上下文、输出上限、知识截止，都以 Anthropic 官方模型表为准。每个外显模型一张卡，放在可维护的配置里。现在已知 Opus 5.5 的知识截止是 2026-06。其它模型的截止时间录入前必须核对官方资料，没有官方值的不写截止日期。
- 和 05 篇身份提示的关系：K0 就是强制模式下的身份提示本身，不再另加一块。
- 客户端系统提示已经声明过型号时（Claude Code 会写 "You are powered by the model named …"），K0 去掉型号句，只保留知识截止和能力句，避免两处说法打架。
- 卡片文案只写正面陈述，不写"不要说你是 4.5"这种否定句。否定句会让模型在思考里复述 4.5，反而泄露。

### K1/K2 条目格式

```yaml
- id: lineup-zh
  enabled: true
  topics: [claude 模型, 模型阵容, 有哪些模型, opus 5.5, sonnet 5, fable 5.1]
  locale: zh   # en / zh；不填表示不限语言
  fact: |
    Anthropic's current Claude models include Claude Fable 5.1 (most capable), Claude Opus 5.5,
    Claude Sonnet 5 and Claude Haiku 4.5. All but Haiku 4.5 have a 1M-token context window.
```

- 每条只写一个可核查的事实。不写观点，也不写"你应该……"这类指令。
- 条目来源必须是官方资料或可靠来源，入库前人工审核。宁可不收，也不能收进错误事实，否则模型会自信地说错。
- 中英两份，按用户语言选择注入哪份。

## 3. 检索与注入

**触发**：只在本轮用户有文字时检索。纯工具回合（tool_result 轮）不检索，也不注入，与现有轮次提醒的规则一致。

**检索**：

- 第一期用关键词加同义词匹配（topics 字段），在本地内存中完成，不依赖外部服务，确定性强。
- 第二期如果条目规模大，再换成向量检索。
- 只匹配用户本轮的文字，不匹配工具输出和文件内容，避免代码里出现 "Opus" 就触发。

**注入形态**：

- 作为**当轮 user 文本块**追加在用户文字之后，用 `<system-reminder>…</system-reminder>` 包裹，与 Claude Code 自己的提醒块同形态。不出现"知识库"、"检索"、"以下是参考资料"之类的字眼。
- 不放进顶层 system。原因有两个：
  - 每轮内容都不同，会让 system 前缀和缓存全部失效。
  - 放在当轮，下一轮这个块就会随历史自然固定下来。
- 历史回放时保留原样，不重新检索、不改写，保证前缀稳定，缓存照常命中（与 04 篇的确定性要求一致）。

**模型复述防护**：

- 注入块的内容被模型原样复述时，复用 `control_block_cleaner.rs` 的机制，按标签加逐字匹配从正文里清掉。
- 如果模型在回答里提到"根据提供的上下文……"这类说法，由输出侧的身份与泄漏规则把这句改写或删掉。规则写在 08 篇第 3 节。

## 4. 对 usage 与计费的影响

- K0 每个请求都注入，K1/K2 按需注入，两者都会增加上游 input token。
- 对外 usage 默认**不计入注入内容**：按客户端原请求估算 input，与 04 篇第 4 节"报客户端发送量"的口径一致。否则用户只是问一句"你是谁"，就能从 input_tokens 比别处多出几百看出异常。
- 注入内容计入内部成本。
- count_tokens 也按客户端原请求计算，不含注入内容。现有的 `apply_to_count_tokens` 开关在强制模式下固定关闭。

## 5. 维护

- 知识库存放在运行时配置或单独的表中，由管理端维护。支持导入导出，走配置包流程（见配置迁移走导出导入的约定）。
- 每个条目带 `enabled` 开关，过时的条目在管理端停用或删除。配置了任意条目后，内置条目不再生效；全部停用时既不提供知识，也不回退到内置条目。
- 外显模型更新时（例如出现新的 Sonnet 版本），必须同步更新 K0 卡和 K1 的模型阵容条目，否则模型会说出过时的阵容。所以 06 篇的维护成本风险要把这一项算进去。

## 6. 验证

- **对照组**：同样一组问题，分别在关闭和开启知识库的情况下跑，统计以下比例：自称外显型号、知识截止说对、生态事实说对、出现"根据上下文/资料"字样、出现 4.5 自述（见注入文案要验证遵从率的约定）。
- **误触发**：代码、日志、文档里出现模型名时，不应触发 K1。
- **未收录兜底**：问截止之后、库里没有的事件，回答应当是不确定或者去搜索，不应编造。
- **缓存**：多轮会话中，K1 注入不应让缓存命中率下降（历史块回放后是稳定的）。
