# 借鉴实施计划（第二轮）

**日期：** 2026-10-29
**依据：** [对比文档](zyphrzero-kiro-rs-comparison-20261028.md)、[第一轮实施计划](zyphrzero-adoption-plan-20261029.md)，以及用户 10-29 的确认。
**原则：** 凡是会改变上游身份的改动都做成开关，默认关闭；默认配置下的行为必须与现在完全一致。

## 本轮清单

| 序号 | 项目 | 做法 | 默认 |
|---|---|---|---|
| 1 | 客户端版本号同步 | 新增开关「自动同步 Kiro 客户端版本」 | 关闭 |
| 2 | 上游域名切换 | 新增开关「对话改走 Kiro 新域名」 | 关闭 |
| 3 | 非流式读取超时 | 按静默时长判超时，不再按总时长 | 直接生效 |
| 4 | 图片压缩 | 新增开关，打开后才缩放和重新编码 | 关闭 |
| 5 | 没标缓存却报写缓存 | 流式请求也按官方规则判断要不要模拟缓存 | 直接生效 |
| 6 | OpenAI 接口 | 新增 `/v1/chat/completions` 和 `/v1/responses` | 新路由 |
| 7 | 流式工具参数 | 工具调用结束时校验参数，不合法就按失败处理 | 直接生效 |

缓存用量的对外统计口径不动（用户确认这是与其他系统同步的处理策略）。

## 1. 客户端版本号同步

- **新增运行配置** `kiroVersionAutoSyncEnabled`，默认关闭。
- **打开后的行为：**
  - 后台每 12 小时从官方元数据地址拉一次 `currentRelease`：`https://prod.download.desktop.kiro.dev/stable/metadata-linux-x64-stable.json`。
  - 版本号必须形如 `数字.数字.数字`，否则丢弃，防止把异常内容写进请求头。
  - 拉取失败时继续使用配置里的 `kiroVersion`。
- **关闭时：** 继续用配置里的 `kiroVersion`，和现在完全一样。
- **生效范围：** 统一走一个"当前生效版本"函数，覆盖全部五处请求头，避免只改一处：
  - IDE 端点；
  - 命令行端点；
  - 模型列表；
  - token 刷新；
  - 用量查询。
- **管理页面：** 显示开关，以及最近一次拉到的版本号。

## 2. 上游域名切换

- **新增运行配置** `kiroRuntimeDomainEnabled`，默认关闭。
- **打开后：** IDE 端点的对话和联网搜索请求从 `q.{region}.amazonaws.com` 改到 `runtime.{region}.kiro.dev`。
- **不受影响：**
  - IDE 端点的模型列表、用量查询、token 刷新，这些仍走原来的地址；
  - 命令行端点本来就走新域名，不受影响；
  - 测试用的上游地址覆盖仍然优先。

## 3. 非流式读取超时

- **问题：** 原来非流式读取响应体用的是 `kiroUpstreamResponseTimeoutSecs`，这是总时长限制（线上设为 600 秒），超长回答会被截断。
- **改为：**
  - 静默超时改用流式同一个 `kiroUpstreamStreamIdleTimeoutSecs`，每收到一段数据就重新计时；
  - 首输出超时保持不变；
  - `kiroUpstreamResponseTimeoutSecs` 只管等待响应头，与它原本的配置说明一致。
- **影响到的入口：** 主路径和模型驱动的联网搜索循环。

## 4. 图片压缩（开关）

- **新增配置：** 在 `imageProcessing` 下新增以下几项，`resizeEnabled` 默认关闭：

  | 配置项 | 默认值 |
  |---|---|
  | `resizeEnabled` | 关闭 |
  | `resizeMaxLongSide` | 1568 |
  | `resizeMaxBytes` | 400000（按 base64 长度计） |
  | `resizeJpegQuality` | 85 |

- **处理时机和范围：** 在请求体预处理阶段执行，这一步本地账号和外部池共用。只处理 base64 编码的 PNG、JPEG、WebP；GIF 不动，以免破坏动画。
- **何时处理：** 体积超过上限，或者长边超过上限。
- **怎么处理：**
  - 先等比缩放，再编码成 JPEG；透明背景铺成白色。
  - 仍然超过体积上限时，逐步降低画质，最低到 35；还不够就继续缩小尺寸。
- **安全措施：**
  - 解码前限制图片尺寸和内存占用，防止解压炸弹；
  - 失败时保留原图，只打日志；
  - 结果不比原图小就不替换；
  - 计算放在阻塞线程里做，不占异步线程。
- **依赖：** 新增 `image` 库，固定版本，只开 png/jpeg/webp 三种格式。

## 5. 没标缓存却报写缓存

- **问题：** 0.0.222 起，非流式请求只有带缓存标记、并且断点前的内容达到模型最小可缓存长度时，才模拟缓存。流式请求没有这条规则，所以没加标记的流式请求也会报写缓存。
- **改为：** 流式请求套用同一条规则。本地账号、外部池、联网搜索三条路径保持一致。
- **注意：** 这会改变"没加缓存标记的流式请求"上报的用量。
  - Claude Code 总会带缓存标记，不受影响。
  - OpenAI 接口那边，翻译时会自动加上顶层缓存标记，模拟 OpenAI 自身的自动缓存行为。

## 6. OpenAI 接口

- **做法：** 在 HTTP 层把 OpenAI 请求翻译成 Anthropic 请求体，再交给现有的消息处理入口。这样鉴权、准入、调度、提示词注入、用量记录、外部池兜底都能直接复用。拿到响应后，再逐个事件翻译回 OpenAI 格式。
- **用量记录：** 端点记作 `{前缀}/v1/chat/completions`，后台可以单独区分；路由策略按前缀生效（`/cc`、`/ha`、`/na`、`/dfcache/{名}` 下都有同名路径）。
- **请求翻译：**
  - system/developer 消息提到 system；tool 消息转成 user 轮的 tool_result，相邻同角色合并。
  - `max_completion_tokens`/`max_tokens` 缺省时补运行配置里的默认值。
  - `reasoning_effort`：4.6 及以上模型用 adaptive + 档位（minimal 记作 low），旧模型换算成思考预算；`none` 关闭思考。
  - `tools`、`tool_choice`（required→any）、`parallel_tool_calls=false`、`stop`、`response_format.json_schema` 都映射；图片支持 http(s) 和 data URL，文件按 PDF 处理。
  - `temperature` 等采样参数不转发；多候选、音频、旧版 functions 直接 400。
  - 顶层加缓存标记，模拟 OpenAI 自身的自动缓存。
- **响应翻译：**
  - 思考内容放 `reasoning_content`；联网搜索的服务端块不输出。
  - 流式 tool_calls 的 `index` 按工具调用出现顺序编号；`include_usage` 时最后单独发一个用量 chunk。
  - 用量：`prompt_tokens` 含缓存读写，命中数放 `cached_tokens`。
  - 出错时以一个错误 chunk 结束，不发 `[DONE]`；错误响应换成 OpenAI 信封，529 改为 503。
- **已知限制：** 鉴权、准入这两层在进入处理函数前就返回，错误体仍是 Anthropic 信封，但 `error.type`/`error.message` 字段一致，OpenAI SDK 能正常读出。

## 7. 流式工具参数

- **问题：** 现在工具调用结束时，参数就算不是合法 JSON 也照样转发。Claude Code 收到的是一个无法执行的工具调用，白白浪费一轮。
- **改为：** 工具调用结束时校验完整参数，空参数视为 `{}`。不合法时：
  - 不发这个工具块的结束事件；
  - 本轮按上游协议错误处理：还没向客户端输出过内容时，换号重试；已经输出过时，以错误事件结束。这和现在"参数没收完就断流"的处理一致。
- **对外行为不变的部分：** 参数仍然边收边发，长参数（例如写大文件）的显示进度不受影响。
- **实施时的调整（用户 10-29 确认）：**
  - 参数问题出在本轮输出，不是账号故障：不冷却账号、不记会话失败，只释放占用。
  - 能安全清洗的直接清洗：顶层对象闭合后的多余右括号、逗号，以及同一份参数的完整或截断重复，去掉后客户端无感。流式在转发时就截掉这些尾巴，非流式在解析时清洗；OpenAI 接口收到的历史工具参数也按同一规则清洗。
  - 真正截断或格式错误的参数无法修复，本轮以错误结束。工具块的开始事件一收到就会发给客户端（AskUserQuestion 也一样，它只是把参数攒到完整再发），之后就不能再无感换号，所以实际都是以错误事件结束，由客户端重发。代码里保留了"还没向客户端输出时"的换号路径：这种情况下换号重试，并且本请求内不再选回原账号。

## 验证方案

1. **单元测试：** 每一项都要覆盖默认行为和开关打开后的行为。
2. **全量测试：** 带存储集成测试，两种加密后端各跑一遍。
3. **真实账号：**
   - 版本同步开关打开后，确认请求成功，并且请求头里的版本号已更新；
   - 域名开关打开后，确认对话请求成功；
   - 图片开关打开后，用大图验证体积确实变小；
   - OpenAI 接口：Chat 的流式、非流式和工具调用。
4. **常规检查：** 格式检查、静态检查基线、前端类型检查和前后端契约检查。
