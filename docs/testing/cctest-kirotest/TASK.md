## 3. 硬性约束

- **C1 不影响生产**：59138 服务及本机其他在运行的服务，进程、配置、数据库、日志一律不改、不重启；从中取数据只能只读（读配置 / 只读导出），不能写回。
- **C2 资源受控**：
  - 编译前检查可用内存、CPU 负载；不足时等待，不抢资源。
  - 编译限制并发和资源（如 `cargo build -j <N>`、docker `--memory` / `--cpus`）。
  - 编译和检测期间持续监控内存、CPU、swap，以及生产服务的响应状态；超过阈值立即暂停编译，恢复后再继续。阈值在执行前定好并写进记录。
- **C3 不关 usage**：开发实例完整沿用 `tune-ss6-99` 的参数，usage 统计保持开启；不允许靠关闭 usage、伪造或硬编码 usage 来通过“Token 用量审计”。
- **C4 账号与代理一致**：开发实例用的每个账号，必须搭配它在 59138 上绑定的同一个代理，不能错配；也不能修改生产侧账号的状态（禁用、优先级、配额等）。开发实例直接和 59138 共用这些账号，用户已确认 token 刷新不会影响生产，不需要额外隔离。
- **C5 caddy 只增不改**：只新增 `kirotest` 站点；改之前备份 Caddyfile，`caddy validate` 通过后用 `reload`（不用 `restart`），确认 `kiro2` 抓包服务和其他站点正常。
- **C6 开发实例隔离**：使用未占用的独立端口，独立的数据目录 / 数据库副本，不和生产共享任何可写存储。
- **C7 密钥与抓包数据**：API Key、账号凭证不进入仓库和文档；抓包文件里含凭证和对话内容，存放在仓库外或 `.gitignore` 覆盖的目录，文档里只引用脱敏片段。证据未固定前不得实时清理；证据固定后，只允许清理已登记、可由保留归档恢复的重复展开副本或零事件空会话。唯一 `events.jsonl`、`capture.zip`、`manifest.json`、签名/EOF/重试/opaque 字段来源必须保留。59138 生产原始抓包永久只读保留。
- **C8 git**：未经用户明确要求不提交、不推送。

## 4. 环境准备（一次性）

0. **存档基线**：按 cctest 文档用 API 或页面拉取基线结果，保存原始 JSON 和可读摘要到 `docs/testing/cctest-kirotest/results/baseline-9afa06c2.*`。
1. **读取参数**：只读获取 59138 上 `tune-ss6-99` 路由的完整参数，存为开发实例配置（脱敏后的副本归档备查）。
2. **取账号和代理**：只读导出 59138 上测试要用的账号及各自绑定的代理，写入开发实例独立的数据存储，逐条核对对应关系。
3. **启动开发实例**：资源受控编译（遵守 C2），用开发方式启动在独立端口，本机 curl 冒烟（非流式 + 流式各一次）。
4. **配置 caddy 抓包链路**：参照 `kiro2.okmcode.com` 的抓包实现，新增 `kirotest.okmcode.com → 抓包层 → 开发端口`。确认 HTTPS 证书和 Cloudflare 代理模式下可以从公网访问，抓包能完整记录请求、响应和流式分片。
5. **打通 cctest**：阅读接口文档，确认触发检测、轮询状态、拉取结果的调用方式，写成可复用的脚本；跑一轮完整检测，结果应和基线基本一致，证明链路正常。

## 4.5 摸底阶段（改代码之前）

先不动代码，把问题和评分规则摸清楚：

1. **多轮检测**：用未修改的代码完整检测至少 3 轮，抓包全部保留。
2. **问题清单**：逐项、逐个请求把抓包里看到的问题详细记下来，写进 `analysis/issues.md`，内容包括：
   - 属于哪个检测项、哪一轮、哪个请求（时间用北京时间，并注明抓包文件位置）
   - cctest 发出的请求内容摘要（脱敏）
   - 本服务的实际响应（流式要逐个事件列出），以及它和官方规范的具体差异
   - 这个问题是每次都出现，还是偶发（统计出现次数 / 轮数）
3. **评分规则分析**：根据抓包反推 cctest 每个检测项怎么评分，写进 `analysis/scoring.md`：
   - 每项发了哪些请求、各请求的参数特征（stream、tools、thinking、web_search 等）
   - 检查了响应的哪些内容（字段、事件顺序、签名格式、usage 数值等），通过 / 失败的判定条件
   - 采样项（x/10）怎么抽样、怎么计分，失败的那几次和通过的那几次差在哪里
   - 每条推断注明证据（抓包位置）；只是推测、还没证实的要单独标出来
4. 这两份文档在后面的调优循环中持续更新；第 5 节的修改要以它们为依据。

## 5. 调优循环

每一轮按以下顺序执行，直到达到第 1 节的目标：

1. **检测**：通过脚本触发 cctest 完整检测，保存结果。
2. **关联抓包**：按时间窗口找到本轮所有请求和响应，逐个对应到检测项。
3. **定位**：对每个失败或不稳定项，对比本服务输出和官方 Anthropic API 的规范行为（事件顺序、字段、签名、tool_use / server_tool_use 结构、usage 字段等），找出差异。
4. **查资料**：只用第 5.1 节允许的来源；结论要有出处或抓包证据，不靠猜。
5. **修改代码**：最小化改动，只针对已证实的差异。
6. **编译与重启**：资源受控编译，只重启开发实例。
7. **复测**：回到第 1 步；对 5/10 这类概率性失败，要多跑几次确认已经稳定。

### 5.1 参考资料范围

只允许以下三类，按优先级从高到低：

1. **官方资料**：只限 Kiro 和 Claude（Anthropic）两家的官方文档、官方 API 参考、官方 SDK 源码和官方博客。两者冲突时，对外协议以 Claude 官方为准，上游行为以 Kiro 官方为准。
2. **开源社区的同类项目**：必须有参考价值，同时满足：
   - 做的是同类事情（Kiro 或 Claude API 的代理、转换、兼容层），并且实现了要参考的那部分功能；
   - 仍在维护，近期有提交，相关代码不是已废弃的分支；
   - 能指到具体的文件或提交，不只引用 README 里的说法。
3. **社区文章**：必须确认有效，同时满足：
   - 写明了发布时间，内容没有被后来的官方变更推翻；
   - 关键结论能用官方资料或本项目抓包复现验证，没验证的只能作为线索，不能作为改代码的依据。

不在以上范围的来源（转载、AI 生成的摘要、没有出处的论坛帖子等）一律不用。cctest 文档只用来调用接口、理解各检测项在测什么，不作为实现依据。

每条用到的资料都记进当轮记录，包括：链接、访问时间（北京时间）、所属类别、得出的结论、怎么验证的。官方资料如果和抓包结果不一致，以抓包里的实际行为为准，并在记录里标出这个差异。

**每轮记录** `docs/testing/cctest-kirotest/rounds/round-XX.md`，内容包括：

- 时间（北京时间）、代码版本 / diff 摘要
- 12 项结果，以及和上一轮的对比
- 抓包证据（脱敏片段）、根因分析、结论
- 参考资料清单（按 5.1 节格式）
- 资源监控峰值（内存、CPU），是否触发过暂停

**停滞处理**：同一项同一思路连续两轮无改善，就停止微调，回到抓包和上游资料重新分析根因，换思路。

## 5.2 开发模式热更新

调优期间使用 debug 增量开发循环，不要求每轮执行 release 冻结编译。Rust 代码变更后自动编译；成功后原子替换开发二进制并只重启 59139，编译失败则保留旧进程。开发循环、资源门禁和操作方式见 [`dev-loop.md`](dev-loop.md)。

该循环只读探测 59138 的 `/healthz`，不得对 59138 执行构建、重启、配置写入、数据库写入或账号状态修改。满分后的 release 编译和完整门禁仍按第 6 节执行。

## 6. 收尾验证

满分达标后：

1. 统一完整编译（release），运行 `cargo fmt --check`、`cargo clippy`、`cargo test`；有前端的话一并构建。
2. 功能回归：普通对话、流式 / 非流式、工具调用、图片 / 文档、usage 记录写入、错误处理；确认改动对其他路由配置（包括 59138 上的默认路由）没有副作用。
3. 再跑一轮 cctest，确认满分。
4. 收尾：清理临时文件（抓包数据不算临时文件，全部保留）；停止开发实例；`kirotest` 的 caddy 站点和抓包服务保持运行，不停用。

## 8. 已确认的决定（2026-11-05）

1. **账号共享**：开发实例和 59138 直接共用账号；用户确认 token 刷新不会影响生产，不需要额外隔离。
2. **生效范围**：修复默认全局生效，不做路由级开关。所以第 6 节的回归必须覆盖其他路由配置（包括 59138 上的默认路由）。
3. **达标标准**：同一份代码连续 3 次完整检测满分。
4. **资源阈值**：参考并复用已有 cctest 调优用的暂停 / 恢复阈值，执行前写进记录。
5. **收尾**：
   - 开发实例：停止；
   - `kirotest` caddy 站点和抓包服务：保持运行；
   - 抓包数据：全程保留不删；摸底阶段（第 4.5 节）先多测几轮，把抓包里的问题详细记录下来，并分析 cctest 怎么评分。
