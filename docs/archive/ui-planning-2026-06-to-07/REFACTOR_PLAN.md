# kiro.rs 控制台 — 前端完全重构方案

> Archive status: Historical, partially landed frontend plan; not current authority.
>
> Original path: `ui/REFACTOR_PLAN.md`. Current disposition and authority: [operator UI planning archive](README.md).

> 目标:重新设计信息架构(IA)与视觉语言,数据层尽量复用、必要时重组,**后端 API 与业务逻辑一律不动**。

## ✅ 已确认决策(2026-06-25)

1. **IA**:方向 A — 四域导航(总览 / 资源 / 分析 / 设置)
2. **视觉**:融合风格 — 密集高效型的信息密度与表格力 + 清爽卡片型的层次与指标表达
3. **深色模式**:亮色 + 暗色双主题,可切换并持久化
4. **图表库**:引入 recharts(支持 hover / tooltip / 多系列)
5. **实施粒度**:先做垂直切片验收 —— 设计系统 + 骨架 + 数据层基建,再把「总览 + 账号」做到高完成度交付确认,风格对齐后再铺开其余页面

---


## 一、为什么要重构(现状诊断)

当前 `ui/` 是旧 daisy 版的 1:1 移植:`api/`、`hooks/`、`types/api.ts`、`lib/` 逐字照搬,9 个页面与旧 Panel 一一对应,只换了组件库和路由。问题:

1. **IA 是"按后端模块罗列",不是"按用户任务组织"**。9 个平铺 tab(总览/账号/校验/代理/外部池/用量/价格/审计/配置)里,"账号/校验/外部池/代理"职责重叠,新用户难分辨;"用量/价格/总览"其实是同一件事(分析)的不同切面。
2. **信息密度与后台场景不匹配**。账号卡片展开态 20+ 字段、6-8 个 badge,视觉噪音大;用量表格强制横向滚动;配置 13 个等权 tab,优先级不清。
3. **数据层贴着后端 50+ 种响应类型**,组件直接消费原始结构,缺乏面向任务的高层抽象(如"资源池"统一视图)。

---

## 二、能力域 → 任务域的重新映射

后端 11 个能力域,按**用户实际在做什么**重新归并为 4 个任务域:

| 后端能力域 | 归入任务域 |
|---|---|
| 凭据管理、账号信息/额度、校验、代理资源、外部账号池 | **资源(Resources)** |
| 用量记录、用量仪表盘、模型价格目录、审计日志 | **分析(Analytics)** |
| 凭据 summary 实时态、external-pool status、writer-stats | **总览(Overview)** |
| 运行配置、负载均衡、模型能力、安全密钥 | **设置(Settings)** |

核心判断:
- **校验/代理不该是独立一级页**——它们是"管理资源"过程中的动作和子资源,应内聚进资源域。
- **价格/审计不该是独立一级页**——它们是分析/排查的辅助数据,归入分析域。
- **总览**保留为独立入口,但重新定位成"实时健康 + 待办",而非现在的"用量仪表盘搬运"。

## 三、信息架构(两个候选方向)

### 方向 A:四域导航(推荐)

```
总览 Overview         实时健康、关键指标、异常待办、快捷操作
─────────────────────────────────────────────
资源 Resources
  ├─ 账号 Credentials   主列表(筛选/批量/导入导出/卡片详情)
  ├─ 外部池 External    外部 API 池
  └─ 代理 Proxies       代理资源(也可作为账号筛选维度)
─────────────────────────────────────────────
分析 Analytics
  ├─ 用量 Usage         仪表盘 + 请求明细(同页两视图)
  ├─ 成本 Cost          计费链路、外部池盈亏、模型价格
  └─ 审计 Audit         操作日志
─────────────────────────────────────────────
设置 Settings
  ├─ 运行 Runtime       调度/限流/冷却/缓存/兼容(分组折叠)
  ├─ 模型 Models        能力 + 价格目录、同步
  └─ 安全 Security      Admin Key、Request Keys、客户端接入
```

- 一级导航 4 项,二级在各域内分组。导航清爽,职责清晰。
- "校验"不再是页面,而是资源域里账号/外部池上的**动作**(选中 → 校验 → 结果分组展示)。

### 方向 B:扁平 + 智能默认

```
总览 · 账号 · 外部池 · 代理 · 用量 · 配置
```
- 6 个一级页(比现在少 3 个:校验并入账号、价格并入用量、审计并入用量)。
- 改动较小、迁移快,但没彻底解决"按模块罗列"的根问题。

> **建议方向 A**:真正按任务组织,符合"完全重构"目标。下文均以 A 为准。

## 四、视觉与交互语言(候选)

管理后台的设计取向,给三个风格锚点,二选一或融合:

### 风格 1:密集高效型(参考 Linear / Stripe Dashboard)
- 紧凑信息密度,表格优先,大量数据一屏可览
- 中性灰底 + 单一强调色,克制用色,语义色只用于状态
- 微动效(hover、行展开、乐观更新的瞬时反馈),无大面积动画
- 适合:重度运维,每天盯着看的人

### 风格 2:清爽卡片型(参考 Vercel / Resend)
- 留白舒适,卡片化,圆角柔和
- 关键指标用大字号 + 迷你图,次要信息弱化
- 状态用色块/徽章,层次分明
- 适合:偶尔查看,看重一眼抓重点

### 风格 3:仪表盘驱动型(参考 Grafana / Datadog 简化版)
- 总览即仪表盘,实时图表占主导,深色友好
- 信息以"卡片矩阵 + 时序图"为主
- 适合:强监控诉求

**横切设计决策(无论选哪种):**
- 信息密度:比现在更紧凑(尤其账号卡片、用量表)
- 数据可视化:替换现在的纯 CSS bar,用轻量图表库支持 hover/tooltip(后端 series 数据已具备)
- 状态语义色系统化:可用=success / 冷却=warning / 故障=error / 限流=info,全局一致
- 危险操作:依据能力域调研的"危险清单",分级二次确认(高危要求输入文字确认)
- 实时数据:summary/runtime/status 独立轮询,与静态配置分离,带"数据新鲜度"指示(尤其额度快照的 checkedAt)

## 五、数据层策略(复用为主,必要重组)

**保留不动:**
- `types/api.ts`(后端契约,1322 行)
- `api/*.ts`(请求函数)
- `lib/*`(format、credential-import、kam-import、runtime-config-defaults 等纯逻辑)

**重组/新建:**
- **react-query key 体系**:统一规范(`['credentials','list',filters]` 等),明确各 query 的 staleTime/轮询策略(实时态轮询、配置类长缓存)。
- **面向任务的高层 hooks**:
  - `useCredentialList`:合并 list + runtime + usage-summary + account-info,按 id 聚合,运行态独立轮询。
  - `useResourceOverview`:总览页聚合 summary + external status + writer-stats。
  - 统一的乐观更新 + 失效策略(禁用/优先级/并发等写操作后精准失效)。
- **统一错误处理**:401 全局拦截登出(保留)、写操作 toast、危险操作确认收口到一处。
- **类型收敛**:组件消费"视图模型"(如 `CredentialRow`),不直接吃后端 6 种凭据响应的并集,降低耦合。

**保留的关键机制(调研标记不能丢):**
- localStorage 存 admin key + 启动静默校验 + 失败清除
- 401 全局事件 → 强制登出
- 自动刷新开关持久化(usage/dashboard)
- 导入三入口(批量/KAM/单条)、导入去重、默认参数回填、验证进度可取消
- 客户端 Key 新增后一次性明文展示
- 用量详情的 4 层成本链路 + 重试链路表格
- 模型映射"生成默认规则"、外部池映射预设按钮

## 七、实施路线(建议,待确认后细化)

1. 设计系统层:配色/字号/间距/组件规范 + 核心原子组件
2. 应用骨架:四域导航、布局、路由、auth、数据层基建(query keys + 高层 hooks)
3. 垂直切片验收:**总览 + 账号** 两个页面做到完成度,给你确认风格与交互
4. 铺开其余:外部池/代理 → 用量/成本/审计 → 设置(运行/模型/安全)
5. 整体验证:类型检查、构建、headless 实测路由与关键流
