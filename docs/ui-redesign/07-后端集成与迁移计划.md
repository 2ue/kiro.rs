# 07 后端集成与迁移计划

## 1. 挂载与构建

新目录是 `console/`，挂载在 `/console`，与 `/ui`、`/admin` 并行运行。

| 位置 | 修改 |
|---|---|
| `console/vite.config.ts` | `base: '/console/'`；dev 端口 9027（strictPort）；`/api` 代理到 `VITE_API_PROXY_TARGET`，默认 `http://127.0.0.1:9022` |
| `src/admin_ui/router.rs` | 新增 `#[folder = "console/dist"]` 的 Embed struct 和 `UiAsset` 实现；新增 `create_console_router`，环境变量前缀为 `KIRO_CONSOLE_UI_*`（MODE/DIR/DEV_SERVER/EXTERNAL_URL）；补上 base path 测试 |
| `src/main.rs`（约 684-688 行） | 增加 `.nest("/console", ...)`，`/console/` 301 跳转，加启动日志 |
| `Dockerfile` | frontend-builder 阶段构建 `console`；COPY `console/dist` |
| `.github/workflows/*.yaml` | pnpm cache 路径，install 和 build 步骤 |
| README | 构建前置步骤 |

注意：release 编译时，`console/dist` 目录必须已经存在，否则 rust-embed 会编译失败。可以提交一个只包含 `.gitkeep` 的占位目录，或者在 `build.rs` 里做检查。

切换方案：验收通过后，有两种做法。
- 方案 A：把 `/ui` 的嵌入目录改为 `console/dist`，同时把 base 改为 `/ui/`，用户的书签继续可用。
- 方案 B：保留 `/console`，把 `/ui` 301 到 `/console`。

推荐方案 B。新旧版本可以并行回滚，旧 UI 再保留一个版本后，删除 `admin-ui/` 和 `ui/`。

## 2. 接口策略

第一阶段完全使用现有接口。下面这些现有但还没用上的接口会被启用：

- `POST /credentials/import`：导入向导一次性提交。
- `/credentials-paged`：账号表的服务端分页、筛选、排序。
- `/usage-dashboard/*`：总览和成本页使用聚合数据。
- `supported-models/sync`：同步支持的模型。
- `PATCH /credentials/{id}/auth`：修改认证信息。

第二阶段建议做以下后端增强。每一项都单独提交，并保持向后兼容：

| 优先级 | 增强 | 原因 |
|---|---|---|
| 高 | `PATCH /config/runtime`，按字段局部更新，并带 `version` 做乐观锁 | 从根本上解决整份 PUT 互相覆盖的问题；在此之前，前端用三方合并兜底 |
| 高 | `/credentials-paged` 支持 `disabledReason` 筛选 | 按原因处置时需要拿到全量数据，而不只是当前页 |
| 中 | `/audit-logs` 支持 actor/action/objectType/success/时间筛选 | 现在筛选只作用于当前页 |
| 中 | usage 记录支持游标分页 | 大量明细时翻页稳定，配合虚拟滚动使用 |
| 低 | `/usage-dashboard/series` 增加错误率和 p95 序列 | 总览的趋势图需要这两项 |

上述增强都不涉及 usage 的计算口径，只调整查询和展示，符合"不改 usage 计算"的约束。

## 3. 分阶段交付

| 阶段 | 内容 | 完成标准 |
|---|---|---|
| M0 骨架 | 初始化 Vite、shadcn、Router；token、AppShell、登录、Cmd+K、刷新控制；后端挂载 `/console`；CI 构建 | `/console` 能登录并完成导航；release 二进制包含 dist |
| M1 账号 | 账号表、状态模型、详情 Sheet、批量操作、导入向导、体检 | 覆盖 `ui/` 中账号页和校验页的全部能力；状态单测覆盖 9 种禁用原因 |
| M2 监控 | 总览、请求（虚拟滚动和详情）、调度器 | 行动队列可以跳转；1 万条明细滚动流畅 |
| M3 资源与成本 | 外部池（含策略）、代理、成本与额度 | 外部池策略只有这一个入口；盈亏数字与现有 UI 对账一致 |
| M4 系统 | 配置（草稿、diff、三方合并）、模型、访问控制、审计 | 配置覆盖 RuntimeConfig 全部 104 个顶层字段；未保存时离开页面会被拦截 |
| M5 切换 | E2E、性能、移动端走查；`/ui` 跳转；下线旧 UI | 并行运行 1 个版本，期间没有阻断性问题 |

每个阶段作为一个独立功能提交，不推送。

## 4. 验收矩阵（摘要）

- **功能对等**：以 [01](01-现状诊断.md) 列出的 `ui/` 能力为清单，逐项勾选，确认新 UI 都有对应入口。
- **正确性**：
  - 已禁用的账号不显示"可调度"。
  - 草稿不会被远端更新静默覆盖。
  - 所有危险操作都需要确认。
- **数据口径**：同一时间窗口内，费用和请求数与现有 UI 显示一致，只改展示，不改计算。
- **性能**：首屏 JS 小于 200KB（gzip）；2000 个账号、1 万条明细时滚动流畅；暂停刷新后没有任何轮询请求。
- **安全**：
  - Admin Key 默认存在 sessionStorage。
  - Key 在界面上一律脱敏显示。
  - 接入示例里的 Key 使用占位符。
  - 管理 API 的鉴权行为保持不变。

## 5. 风险

| 风险 | 应对 |
|---|---|
| 三套 UI 并存，维护成本上升 | `ui/` 和 `admin-ui/` 冻结，只修阻断性 bug；M5 结束后删除 |
| React 19、Vite 8 和部分 shadcn 组件兼容性 | M0 阶段先跑通全部组件的示例页 |
| RuntimeConfig 字段多，配置分组可能遗漏字段 | 用脚本比对 `RuntimeConfig` 的类型键和 settings 字段注册表，未注册的字段在 CI 中报错 |
| 后端如果真的迁移到 Go | `api/schema` 作为契约层，可以对照新后端做 contract test |
