# 风险、决策与待确认项

## 已作出的设计决策

### 决策 A：统一渠道/账号概念

产品和新 API 使用 channel/account/providerType；旧 `credentials`、`external_pools` 仅作为兼容来源和迁移别名。这样可以增加 Cursor/OpenAI，而不把“外部池”继续固化成特殊业务域。

### 决策 B：Provider 私有协议处理

Kiro converter、Kiro endpoint、EventStream、token/quota 属于 Kiro Provider；Claude Code Base URL+Key 只做 Anthropic/Claude Code passthrough 和 usage projection。共享的是 contract、调度语义和缓存接口，不是具体协议代码。

### 决策 C：先单体模块化，再考虑进程插件

第一阶段使用 Go 进程内 Provider registry。动态插件会引入 ABI、版本和部署风险；只有当第三方 Provider 需要独立发布/隔离时，才定义进程间 Provider protocol。

### 决策 D：缓存算法先冻结再优化

先把当前 Rust 算法转成 golden fixtures 和跨语言 contract，再做写法优化。任何公式、默认值、scope、提交时机变化都必须有显式版本和迁移说明。

### 决策 E：技术栈已固定

后端采用 Go，负责 gateway、Provider、调度、缓存、配置、Admin API 和持久化；前端采用 React + TypeScript + Tailwind CSS，负责 Web 管理台。后续只需要锁定具体版本、构建工具和镜像基线，不再保留 Go 前端或 React 后端的替代分支。

## 主要风险与应对

| 风险 | 后果 | 应对 |
| --- | --- | --- |
| 把通用调度和 Kiro token manager 直接合并 | 外部账号被迫接受 Kiro 状态/字段，未来 provider 扩展困难 | scheduler 只依赖 Candidate/Quota/Lease/Attempt contract；Kiro 实现独立 adapter |
| RuntimeConfig 拆分时丢默认值或覆盖优先级 | 线上路由、缓存、协议行为变化 | schema version、effective preview、golden merge tests、ETag 和旧 API adapter |
| external passthrough 误走 Kiro converter | 第三方协议失败、tool/thinking/body 被改写 | capability gate + provider isolation tests + package dependency lint |
| 缓存 tracker 在失败请求后提交 | 虚假 cache read、成本与 usage 错误 | calculator 与 commit 分离；只由 kernel 在成功 terminal outcome 调用 commit |
| 双 Redis authority 混用 | 调度与观测故障相互影响 | 连接配置硬隔离、启动校验、禁止 fallback 复用、故障测试 |
| 双 UI 持续漂移 | 字段丢失、API 行为不一致 | `ui/` 单一基线，共享 schema/client/design-system，admin-ui 只读兼容 |
| Go 重写时遗漏 Rust 隐含行为 | 边界错误难以发现 | 先 characterization、shadow decision、双运行对照和真实 CLI |
| secret 迁移/日志泄露 | 外部 key 或 Kiro token 暴露 | secretRef、加密列/KMS、mask、redaction、密钥轮换与审计 |
| 大规模新表迁移锁表 | 生产停顿 | 分批 backfill、索引 concurrently、可暂停 job、旧表只读回滚 |

## 开工前必须确认

1. **切换方式**：是同一域名下 Go/Rust 双进程灰度，还是先在 staging 完成再一次切换？这决定路由层和数据双写复杂度。
2. **secret 存储**：第一阶段是否允许 PostgreSQL 加密列，还是必须接 KMS/Vault？需要确定密钥轮换和灾备责任。
3. **租户边界**：当前系统看起来是单租户/单管理员；目标是否需要多租户？如果需要，channel/account/config/cache scope 必须从第一版带 tenant id。
4. **OpenAI 入站范围**：本期只预留 provider contract，还是需要同时开放 `/v1/chat/completions` 或 Responses API？不能把“预留”误实现成半成品协议。
5. **缓存持久化范围**：当前 tracker 以进程内状态为主。是否继续接受重启清空 tracker，还是要把 tracker 持久化到 Redis？如果改变，必须单独定义一致性和成本。
6. **旧 admin-ui 生命周期**：是否允许一个版本周期后删除 `/admin`？若必须长期保留，需要共享 package 和兼容测试预算。

## 方案边界

本方案是重构计划和执行指导，不是立即修改 Rust/Go/React 生产代码的授权，也不包含发布、切流或删除旧数据。实现阶段必须以本目录文档、确认后的技术栈和验收矩阵为入口；任何偏离都要先补充决策记录。
