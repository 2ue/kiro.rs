# 缓存模块与缓存重建规则

缓存是本次重构的行为保护重点。重构允许改变代码组织和实现语言，不允许改变当前缓存计算、整形、提交时机和隔离语义，除非先增加兼容开关并完成对照验证。

## 1. 独立模块职责

缓存模块拆成六个组件：

1. `PolicyResolver`：按 path、protocol、provider capability 和覆盖链返回不可变 `ResolvedCachePolicy`。
2. `ProfileBuilder`：从请求稳定前缀生成 profile/fingerprint；不把动态 cache_control、位置字段或 billing header 混入稳定 fingerprint。
3. `Tracker`：保存 scope → fingerprint → entry 的 TTL、last-used、cached token 状态，负责 per-account/global/bytes bounds 和淘汰。
4. `Calculator`：根据 profile、已有 tracker entry、target read ratio、token scale、cap jitter 计算模拟 cache usage。
5. `CreationController`：执行 creation 频控、成功请求间隔、时间窗预算和 scope 规则。
6. `UsageProjector`：把真实上游 usage 与本地模拟结果合并为 raw/shaped/reported 三层，不改变真实 metadata 的优先级。

Provider 只提供 `UsageFacts` 和成功/失败/stream terminal 状态；Provider 不直接写 tracker。

## 2. 当前默认策略

以当前仓库 v0.0.169 的 README/config 为准：

| 路径 | 默认策略 | tracker namespace |
| --- | --- | --- |
| `/v1` | `current_high_cache` | 路径覆盖决定；默认可共享基础 namespace |
| `/cc` | `current_high_cache` | 与 `/v1` 使用同一底层模拟，但可由 route namespace 覆盖 |
| `/ha` | `current_high_cache` | 与 `/v1` 使用同一底层模拟 |
| `/na` | `no_cache` | 无 tracker state |
| 自定义 defined route | 只有显式配置才生效 | 由 `routeNamespace` 决定 |

现有 `CachePolicyConfig` 的 `default`、`currentHighCache`、`kiroRsTool` 和 `pathOverrides` 必须迁移为同等能力的策略模板与路径覆盖，不得把旧字段简单扁平化后丢失继承关系。

## 3. 计算顺序

每个消息请求必须严格按以下顺序处理：

```text
1. Resolve path policy
2. Derive stable conversation_id
   metadata.user_id 优先；否则由 system + tools + first user 等稳定部分 SHA-256 派生
3. Bind/acquire target account
4. Build profile blocks
   prelude(model/tool_choice) → tools → system → messages
5. Count tokens and build cumulative fingerprint points
6. Lookup tracker under scope=(account, conversation, model, route namespace)
7. Compute simulated creation/read usage
8. Send upstream request
9. Extract real upstream metadata
10. Merge raw usage (real metadata wins)
11. Apply shaping and reported usage policy
12. Only after successful terminal completion, update tracker
```

如果请求失败、上游返回错误、SSE 在首语义输出前或后中断、lease 丢失或 response 无法完成，步骤 12 不执行。首请求不得因为目标 read ratio 而伪造 cache read；已有稳定前缀命中后才允许 read。

Profile 的 block 顺序必须固定为 `prelude(model/tool_choice) → tools → system → messages`。fingerprint 只使用会改变稳定前缀语义的 canonical 内容：

- 忽略 JSON 对象键顺序、非语义空白、`cache_control` 和位置字段；
- 不把 `x-anthropic-billing-header` 等计费标记混入稳定前缀；
- system、tools、messages 的结构和文本顺序必须保留；
- model 使用 cache model 的规范化值，不直接使用未解析的别名；
- route namespace 只有在策略要求隔离时才进入 scope。

conversation id 的优先级必须保持：请求 metadata 中稳定的 `user_id` 优先；没有时使用稳定 system/tools/首个 user 内容派生 SHA-256。不能用 request id、随机数或账号 secret 生成 conversation id。

## 4. 现有参数与公式语义

以下参数和边界要在新 schema 中保留：

- `targetReadRatio` 默认 `0.98`，有效范围 `0..0.99`。
- `tokenScale` 默认 `1.6`，有效范围 `1..3`。
- `maxSimulatedInputTokens` 默认 `300000`。
- `capJitterMinTokens`/`capJitterMaxTokens` 默认 `12000..24000`，必须满足 min ≤ max。
- `scaleMinInputTokens` 默认 `20000`。
- entry TTL、per-account entries、global entries 和 estimated bytes limit 保持当前默认/上限。
- 默认 ephemeral TTL 为 5 分钟；显式 1h 保留为 1h，但不能超过全局 entry TTL。
- 模型最小可缓存 token 门槛继续按当前模型能力表执行（例如 extended 模型 4096、旧 Haiku 2048 等）。

实现时不要在文档中重新发明公式；应把 Rust `PromptCacheTracker`、`CacheUsage`、`ReportedCacheUsagePolicy` 和 `resolve_cache_policy_for_path` 的现有测试转成 Go characterization tests，再替换内部实现。新算法只有在 golden case、随机对照和线上 shadow 结果一致后才能启用。

## 4.1 Usage 整形的不可变公式

所有 token 字段先做非负归一化；cache creation 的 5m/1h breakdown 之和不能超过总 creation。内部总输入保持：

```text
totalInput = inputTokens + cacheReadInputTokens + cacheCreationInputTokens
billableInput = inputTokens + cacheCreationInputTokens
```

`ReportedUsagePolicy` 的应用顺序固定为：

1. 读取 field base policy：input/output/cacheRead 使用 raw 或 shaped 基值。
2. 如果 cache creation policy 是 raw，保留真实 5m/1h breakdown；否则按确定性 seed 做目标范围采样并 cap。
3. 执行 output post-processing、cache-read sampling、cache-creation sampling。
4. 当 input 被压低且策略允许时，把 input delta 转入 cache read；只有存在 cache-read evidence 或已有 read token 时才允许这样做。
5. 应用最终 standard cache guards，重新计算 `totalInput`。

任何实现都不能先把 reported usage 写回 tracker，也不能用 reported cache read 反推真实上游 metadata。seed 必须由稳定 request/profile/usage 值派生，不能使用不可复现的全局随机数。

## 4.2 Kiro-RS-Tool 与 high-cache 的关系

`current_high_cache` 是基于稳定前缀和 tracker 的本地模拟策略；`kiro_rs_tool` 是另一种策略，默认关闭普通 simulation 和 creation control，依赖 Kiro-specific cache point plan。两者共用 `ResolvedCachePolicy`、bounds、reported usage 和成功提交接口，但内部计算不可互换。`no_cache` 必须关闭 simulation、creation control、cache point 和 reported local cache fields。

## 5. raw/shaped/reported 三层

```text
RawUsage
  = upstream metadata 或 provider 明确的 uncached usage

ShapedUsage
  = raw usage 与本地 tracker simulation 合并后的内部事实
  （真实 cache_read/cache_creation 优先；本地 simulation 只在真实字段无证据时补足）

ReportedUsage
  = 按 path/channel/account 的报告策略做 cap、sample、input delta 转 cache_read、
    creation breakdown 和最终标准字段整形后的下游 usage
```

usage record 和成本计算要同时保存 raw/shaped/reported 的可审计字段。reported usage 的改变不能回写 tracker，也不能改变真实上游请求。

## 6. Provider 与缓存的关系

- Kiro provider 仍可把 cache point、Kiro-RS-Tool 计划和 Kiro protocol conversion 作为 provider-local preparation，但最终 usage 必须转成通用 `UsageFacts`。
- Claude Code upstream provider 不执行 Kiro cache point 或 Kiro-RS-Tool converter；它可以使用同一个通用 route cache policy 和 tracker，但 body 只按 Anthropic/Claude Code passthrough 规则处理。
- OpenAI provider 将来可以声明 `cacheSemantics` 能力；若不支持 Anthropic cache metadata，应使用 `no_cache` 或显式 usage projection，而不能套用 Kiro 模拟。

## 7. 独立缓存页面

缓存页面必须支持：

- 路径策略表：path prefix、strategy、namespace、enabled。
- 模板编辑：default/current_high_cache/kiro_rs_tool。
- simulation、creation control、reported usage、bounds、cache point 的分组表单。
- 继承预览：显示 global → route → channel → account 的最终生效值。
- 影响分析：哪些 provider/channel/route 会使用该策略；修改前显示差异。
- 版本、保存冲突和回滚。

页面不能把 Kiro-only 字段显示给 Claude Code channel；缓存策略是通用域，但 Kiro cache point 是 capability-gated 的扩展。
