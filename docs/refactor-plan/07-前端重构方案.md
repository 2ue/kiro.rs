# 前端重构方案

## 1. 现状与选择

仓库目前同时有 `ui/` 和 `admin-ui/` 两套 React/Vite 工程。`ui/` 已经有路由、AppShell、React Query、较完整的资源页面和 Tailwind 4；`admin-ui/` 使用另一套 Tailwind 3、旧版 dashboard 单体组件和重复 API。重构以 `ui/` 为基线，先冻结 API contract，再将 `admin-ui/` 变为只读兼容入口，最终下线重复实现。

## 2. 推荐技术基线

**技术栈已经确定：Go 负责后端网关和管理 API，React + TypeScript + Tailwind CSS 负责 Web 管理前端。** 本方案后续所有模块、接口、部署和验收均以此为准。

建议在开工时锁定经 CI 验证的成熟版本，不在计划中虚构未来 patch 号：

| 层 | 基线 |
| --- | --- |
| Runtime | Node 22 LTS、pnpm 11、Go 当前受支持稳定版本（记录到 `go.mod`/toolchain） |
| UI | React 19、TypeScript 5.x、Vite 6/7 中与 Node 22 兼容的稳定版 |
| Styling | Tailwind CSS 4.x，单一版本；禁止 Tailwind 3/4 并存 |
| Components | shadcn/ui 风格封装 + Radix UI primitives，图标使用 Lucide；表格/日期/图表使用经过维护的开源包 |
| Data | TanStack Query 5、React Router 7 或已验证的 Router 6 兼容基线、Zod 3/4（按最终生态兼容性锁定） |

第一阶段建议沿用当前 `ui/` 已验证的稳定基线，减少“换语言 + 换框架 + 升级大版本”同时发生的风险：React 18.3.1、TypeScript 5.7.x、Vite 5.4.x、Tailwind 4.0.6、TanStack Query 5.x、Node 22.x、pnpm 11.x；Go 后端使用开工时 CI 验证通过的稳定版本，并在 `go.mod` 的 `toolchain` 中固定。React 19、Vite 新主版本或 Tailwind 新主版本只能作为独立升级，不得和 Provider 迁移混在同一个切换批次中。

成熟组件库的约束解释为：业务页面只能使用统一 design-system 组件（Button、Input、Select、Dialog、Table、Tabs、Toast、Form、DataGrid 等），不得直接写 `<button>`、`<input>`、`<select>`、`<textarea>`、原生 modal 或未经包装的 table 控件。底层组件为了可访问性仍可渲染 HTML DOM，这不违反“业务层禁止原生组件”的目标。

## 3. 页面信息架构

```text
总览
渠道与账号
  ├─ All channels
  ├─ Kiro accounts
  ├─ Claude Code upstream accounts
  └─ Validation / import / proxy bindings
路由与调度
  ├─ Route policies
  ├─ Fallback matrix
  └─ Scheduler health
缓存
  ├─ Cache policy overview
  ├─ Route strategy editor
  ├─ Creation control
  └─ Effective config preview
用量与审计
模型与能力
系统设置
  ├─ Global config
  ├─ Security
  ├─ Redis/Postgres/observability
  └─ Feature flags / migration status
```

缓存必须有独立导航项和独立保存动作；路由策略不得继续埋在一个 1800 行以上的 runtime 页面中。账号表单根据 `providerType` 动态渲染 capability sections，Kiro 专属字段与 Claude Code Base URL+Key 字段完全分离。

## 4. API 与表单模型

- 使用 OpenAPI/JSON Schema 生成 TypeScript types 和 query/mutation client，避免 `ui/` 与 `admin-ui/` 各自维护接口类型。
- 表单使用 Zod schema 与后端 schema 同步校验；未知字段保留在 `unknownFields`，提交 patch 时不丢失。
- 查询区分 list、summary、runtime status、effective config，禁止为了兼容旧卡片一次拉取 500 条全部账号。
- React Query 的 query key 按 domain/version/scope 组织，mutation 成功后只 invalidate 受影响的 keys。
- 所有异步状态必须有 loading/empty/error/stale/permission state；危险操作使用统一 confirm pattern。

## 5. 设计系统与质量门禁

建立 `web/src/components/ui` 和 `web/src/components/patterns` 两层：前者是可访问基础组件，后者是分页表格、异步 data state、section card、form field、diff preview 等业务模式。Feature 目录禁止 import 原生控件和直接拼接 Radix primitive。

加入 ESLint rule 或自定义 lint 检查：

- 禁止 feature 文件中出现 JSX intrinsic controls。
- 禁止 feature 直接 import `@radix-ui/*`，只能从 design-system 导入。
- 禁止绕过 API client 直接使用 axios/fetch。
- 禁止把 secret/API key 写入 React Query cache、URL 或 localStorage。

验证包括键盘导航、焦点管理、ARIA、暗色主题、窄屏、5000+账号分页性能和视觉回归。

## 6. 迁移顺序

1. 建立共享 `api-client`、schema、tokens 和组件包。
2. 将 `ui/` 的 credentials/external-pools 页面改为统一 channels/accounts 适配层。
3. 拆分 runtime 页面为 global/dispatch/routes/cache/provider sections。
4. 新增独立缓存页面和 effective config preview。
5. 迁移 usage/audit/models/security。
6. 把 `admin-ui/` 指向同一 API 和 design-system，进入 legacy read-only，最后删除。
