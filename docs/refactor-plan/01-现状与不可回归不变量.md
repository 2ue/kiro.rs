# 现状与不可回归不变量

## 1. 当前请求路径的真实结构

当前服务是一个 Rust/Axum 单体。`src/anthropic/router.rs` 创建 Anthropic 路由时，同时注入 `KiroProvider`、`ExternalPoolManager`、usage recorder、prompt cache tracker、cache creation controller、模型能力和定价目录。`src/anthropic/handlers/request_entry.rs` 是实际的入口编排器：它先对原始 JSON 做探测、缺省 `max_tokens` 补齐、reasoning 校正、历史 transcript 检查，然后根据请求是否仍可 raw passthrough 决定是否尝试外部渠道。

当前大致流程如下：

```text
客户端 Anthropic/Claude Code 请求
        │
        ├─ API key / admission / raw body probe / 安全校验
        ├─ missing max_tokens、reasoning、transcript 检查
        ├─ 若请求未被要求规范化：外部渠道 raw direct / preflight
        ├─ 解析 MessagesRequest
        ├─ 路由策略与本地/外部可用性判断
        ├─ 本地路径：Anthropic body → Kiro conversation state → Kiro endpoint
        │              Kiro EventStream → Anthropic SSE/JSON
        └─ 外部路径：原始或受控 normalized Anthropic body → Base URL+Key
                       SSE/JSON 透传与 usage projection
```

这说明“入口协议处理”和“账号调度”已经被放在同一条热路径上，但两类账号实际需要的协议处理不同。重构应保留入口的安全与兼容行为，却把 provider-specific preparation/execution 从入口编排器中抽出。

## 2. 当前模块职责与耦合点

| 当前位置 | 已承载的业务职责 | 重构判断 |
| --- | --- | --- |
| `src/anthropic/handlers/*` | Anthropic 请求校验、路径路由、body 预处理、缓存解析、调用本地或外部、响应整形 | 拆为 transport、route planner、protocol pipeline、execution kernel；不得让 handler 直接知道 Kiro 细节 |
| `src/anthropic/cache.rs`、`prompt_cache.rs` | raw/shaped/reported usage、fingerprint、scope、TTL、tracker、缓存策略计算 | 提升为独立 cache domain，保持算法与字段语义 |
| `src/kiro/provider.rs` | Kiro 凭据选择、token/lease、endpoint、重试、失败归因、流式完成 | Kiro Provider 插件私有实现；其内部算法不下沉为“所有账号通用实现” |
| `src/kiro/token_manager/*` | 账号池、RPM、并发、sticky、cooldown、Redis 协调、容量状态、refresh | 抽取通用 scheduler contract；Kiro 额度和 token 生命周期作为 Kiro quota/credential adapter |
| `src/kiro/endpoint/*`、`parser/*`、`protocol.rs` | Kiro 协议 URL、请求/事件帧和 EventStream 解码 | 仅属于 Kiro protocol adapter |
| `src/external_pool.rs` 及子模块 | Base URL+Key、header/wire profile、raw/normalized body、池 lease、队列、质量评分、重试、usage projection | 变成 Claude Code upstream Provider；保留外部特殊能力，但不得依赖 Kiro converter |
| `src/model/config.rs` | 全局配置、Kiro 调度、外部池调度、协议转换、缓存、reported usage 全部混合 | 拆成有 owner 的 versioned config schemas |
| `src/storage/postgres.rs` | runtime_config、credentials、external pools、usage、proxy、migration | 数据域分表保留；引入 channel/account 通用表时必须提供可回滚映射 |
| `src/storage/redis_cache.rs` | Kiro sticky/cooldown/lease 与外部池协调/质量/容量 | Redis key namespace 按 scheduler domain + provider/channel 分隔，保留业务 Redis 与观测 Redis 故障域 |
| `ui/`、`admin-ui/` | 两套重复后台；缓存藏在 runtime 页面 | 以 `ui/` 为功能基线，统一设计系统，`admin-ui` 只做兼容入口并逐步下线 |

最需要解除的耦合有三处：

1. `AnthropicRouterDependencies` 同时持有 Kiro 和外部池具体管理器，导致入口层承担 provider 选择细节。
2. `ExternalPoolManager` 直接引用 `anthropic::cache`、`prompt_cache`、`model_processing`，并通过 Kiro 模块的 storage task 写关键状态；这些应改成共享 domain contract 或外部 provider 自己的实现。
3. 当前 `RuntimeConfig` 既保存 Kiro body conversion，又保存外部池 route、cache policy 和 reported usage；UI 只能整体保存，容易误改无关字段。

## 3. 必须保持的外部行为

### 路由与入口

- 继续支持 `/v1/messages`、`/cc/v1/messages`、`/ha/v1/messages`、`/na/v1/messages` 以及相应 models/count_tokens 入口。
- `/v1`、`/cc`、`/ha` 默认使用 high-cache 策略，`/na` 默认 no-cache；自定义 defined cache route 仍需显式配置。
- 继续支持 `x-api-key` 与 Bearer 认证、request admission、payload guard、缺省 `max_tokens` 处理、reasoning 边界修复、transcript 污染检查和错误信封。
- raw external direct/preflight 只能在入口规范化没有改变 body 时使用；一旦发生必须的规范化，外部请求走 parsed/normalized pipeline。

### 渠道和 fallback

- 本地 Kiro 账号可以按配置 fallback 到第三方 Claude Code Base URL+Key 渠道。
- external 直连、本地优先、local rescue、维护期 direct、unsupported model、容量不足、Redis degraded、无可用账号和 transient exhausted 等现有开关语义必须逐项保留。
- 路由规则继续支持 allow-all、allow-list、deny-list，且同时可限制 local targets 和 external targets；池/账号自身也可有独立 route rules。
- sticky 绑定不能越过 disabled、cooldown、capacity、model incompatibility；Redis feedback 必须在下一次选择前可见。

### 协议边界

- Kiro 路径继续负责 Anthropic/Claude Code → Kiro conversation state，以及 Kiro EventStream → Anthropic response 的完整转换。
- 外部 Base URL+Key 路径不执行 Kiro conversation converter、Kiro tool cache point、Kiro machine id、Kiro EventStream parser 或 Kiro token refresh。
- 外部路径只做必要的 Anthropic/Claude Code passthrough、model mapping、header/wire profile、SSE framing、错误分类和 usage projection。

### 缓存与 usage

- 真实上游 cache metadata 优先；只有真实 metadata 读写均为 0 时，才使用本地模拟数据补足 cache 字段。
- 首次没有已有前缀时可以报告 creation，但不能凭空报告 read；已有前缀命中后才报告 read。
- 只有成功完成的请求才更新 tracker；失败、上游错误、流式中断不得提交缓存状态。
- scope 至少隔离账号、conversation、model、route namespace；账号删除/禁用应清理其缓存，进程重启清空进程内 tracker 的语义保持不变。
- `rawUsage`、`shapedUsage`、`reportedUsage` 和计费输入必须可追踪，外部渠道也不能跳过这三层。

## 4. 当前版本与运行约束

- Rust package 当前为 `kiro-rs 0.0.169`，edition 2024；依赖包含 Axum 0.8、Tokio 1、Reqwest 0.12、SQLx 0.8、Redis 0.27。
- 生产依赖 PostgreSQL 和业务 Redis；可选 observability Redis 必须与业务 Redis 处于不同 authority，不能因为连接失败回退复用业务 Redis。
- 当前 Docker/CI 固定 Rust 1.92.0、Node 22.23.0、pnpm 11.11.0，并构建两套 React 前端再嵌入 Rust 二进制。Go 重构必须定义 Go 后端、Node/React 前端、pnpm、数据库和 Redis 的锁定版本矩阵。
- 当前 `runtime_config` 以 JSON 持久化并递增 version；重构不能直接删除旧 JSON，必须先做读取迁移和双向回滚映射。

## 5. 当前管理面 API 基线

当前 Admin API 仍按旧概念分域，重构时必须有兼容适配：

- `/credentials` 及其分页、summary、runtime、account-info、usage-summary、batch/import/export、disabled/priority/concurrency/RPM/warmup/refresh/test/proxy 等操作：本地 Kiro 账号管理。
- `/external-pools`、`/external-pools/status` 及 CRUD、enabled、supported-models、test、cooldown/auto-disabled：第三方 Base URL+Key 管理。
- `/config/load-balancing` 与 `/config/runtime`：当前整体调度/运行配置入口；其中混合 cache、protocol、Kiro、external pool 字段。
- `/usage-records*`、`/usage-dashboard*`、`/audit-logs`：usage、成本、质量和审计。
- `/proxy-resources`、`/model-pricing`、`/model-capabilities`、`/security/*`：代理、模型目录和密钥。

兼容期要同时验证“旧 endpoint 读到的结果”和“新 channel/account endpoint 的结果”一致；旧 endpoint 不得因为概念重命名而把外部账号当成 Kiro credential 返回。
