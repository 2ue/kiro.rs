# 目标架构与模块边界

## 1. 目标系统

目标系统是一个可扩展的多渠道 AI gateway。当前交付范围只有两种 Provider：

1. `kiro`：本地 Kiro 账号池，负责 Kiro 认证、token refresh、额度、endpoint、协议互转和 Kiro 特有调度指标。
2. `claude-code-upstream`：第三方 Claude Code 协议的 `baseURL + apiKey` 账号/渠道，负责 Anthropic/Claude Code 请求透传和外部上游错误、流式、usage 处理。

未来可以增加 `openai-compatible`、官方 OpenAI、Cursor 或其他渠道，但新增 Provider 不应修改通用请求入口、缓存引擎和调度状态机的核心代码。

逻辑分层如下：

```text
┌───────────────────────────────────────────────────────────────┐
│ Control plane: Admin API / React UI / config schema / audit   │
├───────────────────────────────────────────────────────────────┤
│ Request plane: Auth → Request facts → Route planner → Kernel  │
├───────────────────────────────────────────────────────────────┤
│ Shared domains: Scheduler / Cache / Usage / Retry / Errors    │
├───────────────────────┬───────────────────────┬───────────────┤
│ Kiro Provider          │ Claude Code Provider  │ future plugin │
│ Kiro protocol         │ Anthropic passthrough │ OpenAI/Cursor │
│ Kiro quota/credential │ BaseURL+Key account  │ own adapter   │
├───────────────────────┴───────────────────────┴───────────────┤
│ Infrastructure: PostgreSQL / business Redis / observability   │
└───────────────────────────────────────────────────────────────┘
```

## 2. 推荐代码仓结构

后端采用 Go module；模块边界按业务所有权而不是当前 Rust 文件一比一搬运：

```text
backend/
  cmd/gateway/                 # 进程启动、依赖组装、优雅关闭
  internal/transport/http/     # Anthropic/OpenAI 入站、SSE、认证、中间件
  internal/controlplane/       # Admin API、schema、ETag、审计
  internal/domain/channel/     # Channel/Account/ProviderRef 领域模型
  internal/domain/dispatch/    # RoutePlan、Attempt、Lease、fallback 状态机
  internal/domain/cache/       # Cache policy、fingerprint、tracker、usage shaping
  internal/domain/usage/       # raw/shaped/reported、计费、usage record
  internal/domain/config/      # global/route/channel/account 合并与校验
  internal/domain/model/       # 模型能力、别名、映射、定价
  internal/provider/           # Provider SPI、registry、capability registry
  internal/provider/kiro/      # Kiro credentials、protocol、quota、transport
  internal/provider/claudecode/# Base URL+Key、Anthropic passthrough、SSE/usage
  internal/scheduler/          # 通用候选筛选、优先级、容量 lease、队列
  internal/storage/postgres/  # repository、migration、旧数据导入
  internal/storage/redis/      # lease/sticky/cooldown/quality keyspace
  internal/observability/      # logs、metrics、traces、redaction
  migrations/                  # versioned SQL
  api/openapi/                 # versioned public schemas
web/
  src/app/                     # shell、router、providers
  src/features/channels/       # 统一渠道/账号
  src/features/routes/         # 路由与 fallback
  src/features/cache/          # 独立缓存策略页面
  src/features/usage/          # usage/成本/审计
  src/features/settings/       # 全局配置、模型、安全
  src/components/ui/           # 唯一 design system
  src/lib/api/                 # generated client + query hooks
```

Go package 应遵守依赖方向：`transport → application/domain`，Provider 实现依赖 domain contract，domain 不依赖具体 HTTP、PostgreSQL 或 React。禁止 `provider/kiro` import `provider/claudecode`，禁止 generic scheduler import Kiro types。

## 3. 请求处理内核

请求内核分成六个稳定步骤：

1. **Ingress facts**：读取路径、协议 profile、模型、stream、conversation hint、原始 body hash，并完成认证、body size、JSON duplicate key、reasoning 和安全检查。
2. **Route policy resolution**：将请求路径映射到 `RoutePolicy`，合并 cache policy、protocol profile、允许的 provider types 和 fallback edges。
3. **Dispatch plan**：根据 route policy 生成有序 target groups，例如 `local:kiro → external:claude-code`，并为每个 group 建立 attempt budget。
4. **Acquire**：通用 scheduler 向 provider registry 查询候选，按 provider 的 `Eligibility`、通用容量和 provider quota 指标申请 lease。
5. **Execute**：把 `ProviderRequest` 交给具体 Provider。Provider 负责自己的 body preparation、transport、stream decoder、usage extraction 和 completion report。
6. **Finalize**：将 provider raw usage 与 cache result 合并，形成 shaped/reported usage；成功才提交 cache tracker；写 usage/audit/metrics；释放 lease。

内核只识别 typed result，例如 `ProviderErrorClass`、`AttemptOutcome`、`UsageFacts` 和 `StreamTerminalState`，不检查错误字符串，也不调用 Kiro 专有方法。

## 4. Provider 插件机制

第一阶段使用进程内静态 registry，避免 Go `plugin` 动态加载的 ABI 和部署风险；后续如有强插件需求，再增加独立进程 Provider protocol。每个 Provider 实现：

```go
type Provider interface {
    Type() ProviderType
    Capabilities(ctx context.Context) CapabilitySet
    ListCandidates(ctx context.Context, query DispatchQuery) ([]Candidate, error)
    Acquire(ctx context.Context, candidate Candidate, req AcquireRequest) (Lease, error)
    Execute(ctx context.Context, lease Lease, req ProviderRequest) (ProviderResult, error)
    Release(ctx context.Context, lease Lease, outcome AttemptOutcome) error
    ValidateAccount(ctx context.Context, input AccountInput) (ValidationResult, error)
}
```

`Capabilities` 用于让 UI 和 route planner 判断能力；例如 Kiro 声明 `kiroProtocolConversion=true`，Claude Code upstream 声明 `anthropicPassthrough=true`、`kiroProtocolConversion=false`。能力声明只能扩大可用路径，不能让外部账号误用 Kiro 设置。

## 5. 可靠性原则

- PostgreSQL 是配置、账号、渠道、usage 的持久权威；Redis 只保存短期调度状态和跨实例 lease/sticky/cooldown/quality。
- 每个 lease 都有 owner、generation、expiry、heartbeat 和幂等 release；丢失 lease 时 Provider 必须停止继续向上游发送或把结果标记为不可提交。
- 任何跨 provider retry 都必须经过 `RetrySafety` 判定：只有尚未产生下游语义输出，或请求被明确标记可重放时，才允许换目标。
- 外部 provider 的 secret 只在 server side 使用；Admin response 只能返回 masked value；日志、usage、audit 统一执行 redaction。
- 运行配置更新使用 optimistic concurrency（ETag/version）；保存局部 patch 时未知字段必须保留。

## 6. Go 依赖选择原则

后端不需要引入一个“大而全”的 Web framework。建议使用 Go 标准库 `net/http` 作为 HTTP 基础，配合经过维护的轻量组件，并在开工时由 CI 锁定确切版本：

| 能力 | 建议 | 选择理由 |
| --- | --- | --- |
| HTTP routing/middleware | `chi` v5 或等价稳定 router | 基于标准 `net/http`，便于 SSE、优雅关闭和中间件测试 |
| PostgreSQL | `pgx` v5；查询用 `sqlc` 生成 | 类型安全、连接池明确、避免 ORM 隐式 SQL |
| Redis | `go-redis` v9 | 支持 context、超时、pipeline、Lua/锁语义 |
| Migration | `goose` 或等价 SQL-first 工具 | migration 可审计、可回滚、可在 CI verify |
| Config/schema | `encoding/json` + `jsonschema`/OpenAPI generator | 版本化 JSON、局部 patch 和前端类型共享 |
| Logging | `log/slog` 或 `zap` | 结构化日志和 secret redaction |
| Observability | OpenTelemetry Go SDK + Prometheus exporter | trace/metric 与 provider、route、cache 维度关联 |
| Test | 标准 testing + `testify`/property testing | 单测、竞态、fuzz、Redis/Postgres integration 可分层运行 |

不在设计阶段写死未经验证的 patch 号；开工时提交 `go.mod`、toolchain、依赖 checksum 和 SBOM，升级只通过依赖更新 PR。任何包必须有维护状态、许可证、CVE 检查和替代方案。
