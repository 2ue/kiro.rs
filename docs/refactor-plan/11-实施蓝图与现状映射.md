# 实施蓝图与现状映射

这份文档把前面的目标设计落到当前仓库的具体模块、数据和请求步骤上。实施者应先按本表建立新工程骨架，再逐个迁移行为；禁止直接把 Rust 文件翻译成同名 Go 文件。

## 1. 当前模块到目标模块的映射

| 当前实现 | 当前真实职责 | Go 目标模块 | 迁移顺序 |
| --- | --- | --- | --- |
| `src/anthropic/handlers/request_entry.rs` | 原始 body 探测、缺省 max tokens、reasoning 校正、transcript 检查、raw external preflight | `internal/transport/http/anthropic/entry` + `internal/application/requestfacts` | 先提取 fixtures，再实现纯函数；最后接入 HTTP |
| `src/anthropic/handlers/local_body_pipeline.rs` | Anthropic → Kiro body、tool mapping、thinking、cache point、payload guard | `internal/provider/kiro/protocol/inbound` | Kiro Provider 内部迁移，不能进入 generic handler |
| `src/anthropic/handlers/parsed_body_pipeline.rs` | 通用 parsed body 的 thinking/multimodal 准备 | `internal/application/requestprepare` + Provider capability hook | 先抽 capability contract |
| `src/anthropic/prompt_cache.rs` | profile、fingerprint、tracker、TTL、bounds、success commit | `internal/domain/cache` | 先 golden test，后实现 |
| `src/anthropic/cache.rs` | CacheUsage、raw/reported usage 整形、creation/read policy | `internal/domain/usage` + `internal/domain/cache/projection` | 与 prompt cache 同一组 fixture 对照 |
| `src/anthropic/usage.rs` | usage record、route kind/subtype、attempt、错误和 latency | `internal/domain/usage` + `internal/observability` | 先定义 versioned record schema |
| `src/kiro/provider.rs` | Kiro 账号获取、retry、stream、endpoint、completion、失败归因 | `internal/provider/kiro` | 依赖 scheduler SPI，不反向依赖 generic handler |
| `src/kiro/token_manager/*` | Kiro token refresh、RPM、并发、sticky、cooldown、Redis 状态 | `internal/provider/kiro/account` + `internal/scheduler/state` | 先迁移状态契约，再迁移算法 |
| `src/kiro/endpoint/*`, `parser/*` | Kiro URL、请求转换、EventStream 解码 | `internal/provider/kiro/protocol` | 只允许 Kiro package import |

| `src/model/config.rs` | 所有配置、默认值、normalize、validate、cache route resolve | `internal/domain/config`、`internal/domain/cache/policy`、`internal/domain/dispatch/policy` | 每个字段有迁移表后再拆 |
| `src/storage/postgres.rs` | runtime JSON、credentials、external pool、usage、proxy、migration | `internal/storage/postgres` repositories + `migrations` | 新旧表双读、双写、校验 |
| `src/storage/redis_cache.rs` | scheduler、sticky、lease、quality、coordination | `internal/storage/redis` 按 namespace 拆 repository | 先定义 key/version/TTL |
| `src/admin/*` | Admin route、DTO、校验、service、审计 | `internal/controlplane/http` + `internal/controlplane/service` | v2 先读，再局部 patch |

## 2. 目标请求时序

```text
HTTP handler
  1. authenticate + admission + body limits
  2. probe(raw body) → RequestFacts
  3. validate/normalize entry facts
  4. resolve RoutePolicy + CachePolicy + EffectiveConfig
  5. planner.build(target groups, attempt budget)
  6. for each target group:
       scheduler.select(provider capabilities, account state)
       scheduler.acquire(lease)
       provider.prepare(request, effective config)
       provider.execute(stream/non-stream)
       provider.classify(outcome, usage facts, replay safety)
       scheduler.complete/release
       if retry/fallback allowed: continue
  7. cache.project(raw/shaped/reported)
  8. if terminal success: cache.commit(scope, profile)
  9. usage.record + metrics + response
```

关键边界：`provider.prepare` 发生在 lease 之后，因为 cache scope 和 usage attribution 需要实际账号；`cache.commit` 发生在完整成功之后；`scheduler.release` 必须在 response stream 被消费完或明确终止之后执行。

## 3. 必须定义的 Go 接口

```go
type RequestFacts struct {
    Path, Protocol, Model string
    Stream bool
    RawBody []byte
    BodyHash [32]byte
    ConversationHint string
}

type RoutePlanner interface {
    Plan(context.Context, RequestFacts, EffectiveConfig) (DispatchPlan, error)
}

type Scheduler interface {
    Select(context.Context, TargetQuery) (Candidate, error)
    Acquire(context.Context, Candidate, AcquireOptions) (Lease, error)
    Complete(context.Context, Lease, AttemptOutcome) error
    Release(context.Context, Lease, ReleaseReason) error
}

type CacheEngine interface {
    ResolvePolicy(RouteContext, EffectiveConfig) (ResolvedPolicy, error)
    Prepare(CacheInput) (CachePlan, error)
    Project(CachePlan, ProviderUsage, ReportPolicy) (UsageProjection, error)
    CommitSuccess(context.Context, CachePlan, CommitEvidence) error
}

type Provider interface {
    Type() ProviderType
    Capabilities() CapabilitySet
    Candidates(context.Context, TargetQuery) ([]Candidate, error)
    Prepare(context.Context, Lease, ProviderRequest) (PreparedRequest, error)
    Execute(context.Context, PreparedRequest) (ProviderResult, error)
    Classify(error, ProviderResult) AttemptOutcome
}
```

这些接口只是稳定边界；具体 Provider 可以使用更细的内部接口。尤其不能把 `KiroRequest`、`KiroCredentials`、`ExternalPool` 或 `reqwest.Response` 暴露到 domain 层。

## 4. 旧字段到新配置的映射

| 旧字段/结构 | 新位置 | 迁移规则 |
| --- | --- | --- |
| `credentials` row | `channels(providerType=kiro)` + `accounts` | 一个旧凭据对应一个 account；共享 endpoint/region 的默认值写 channel config，账号显式值写 account override |
| `external_pools` row | `channels(providerType=claude_code_upstream)` + `accounts` | base URL、header/TLS、model mapping 写 channel；api key 写 account secret；supported models/priority/concurrency 保留在 account |
| `external_pools.external_pool_route_mode/rules` | `RoutePolicy.targets[providerType=claude_code_upstream]` | 保留 allow_all/list/deny_list 语义和路径归一化 |
| `external_pools.local_pool_route_mode/rules` | `RoutePolicy.targets[providerType=kiro]` | 同上，禁止合并成一个无来源的 allow-list |
| `fallback_on_*` | `RoutePolicy.fallback.triggers[]` | 一项一项映射：capacity、redis_degraded、no_candidate、transient、unsupported_model |
| `external_pool_local_rescue_*` | `RoutePolicy.rescue` | 保留触发错误类别、最大等待和“一次性”限制 |
| `external_pool_quality_*` | `QualitySchedulingConfig` | 迁移所有权重、EWMA、TTL、topK、probation、probe share、recovery ramp |
| `promptCache*` | `CacheConfig.templates.currentHighCache.simulation` | 数值和校验范围原样迁移 |
| `cachePolicy.pathOverrides` | `CacheConfig.routes[]` | 路径 canonicalization、最长前缀匹配和空 patch 过滤原样迁移 |
| `reportedUsage.pathOverrides` | `CacheConfig.templates/reports` | 保留 raw/shaped/reported 层和每路径 override |
| `bodyConversion` | `ProviderConfig.kiro.protocolConversion` | 外部 provider 不生成该字段 |
| `external_pool_usage_projection_*` | `ProviderConfig.claudeCode.usageProjection` | 只影响外部上游 usage projection，不改变 cache tracker |

迁移程序必须输出 `migration_report.json`：记录旧行数、新行数、每个旧 id 对应的新 id、配置字段差异、被拒绝字段和 secret fingerprint。任何一对多或多对一转换都要有人工可读原因。

## 5. 每个阶段的交付物和停止条件

| 阶段 | 交付物 | 进入下一阶段的硬条件 |
| --- | --- | --- |
| A 行为冻结 | fixtures、错误分类表、cache golden、旧配置快照 | fixture 可重复运行，覆盖成功/失败/流式/回退 |
| B Go 读路径 | Go service、旧表 repository、v2 read API、projection report | 新旧列表、effective config、secret fingerprint 一致 |
| C 通用 kernel | route planner、scheduler、lease、attempt state machine | scheduler contract、双实例 lease 和 fallback tests 全通过 |
| D Claude Code Provider | raw/normalized、SSE、usage、重试、外部 channel API | 真实 loopback/CLI fixture 与旧外部路径一致 |
| E Kiro Provider | converter、endpoint、token/quota、stream | Kiro CLI/IDE、tool/thinking/MCP/image tests 全通过 |
| F Cache engine | policy resolver、tracker、projection、独立缓存 API/UI | Rust/Go golden diff 为零或每项有签收记录 |
| G 灰度切换 | shadow diff、双写、回滚开关、dashboard | 连续观察窗口无 P0/P1 回归，回滚演练成功 |
