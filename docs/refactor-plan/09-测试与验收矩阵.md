# 测试与验收矩阵

## 1. Contract 和 characterization

所有当前行为先固化为 provider-independent fixtures。每个 fixture 包含 request body、path、model、runtime config、账号/channel 状态、上游响应/SSE、预期 route decision、usage 和 cache state。黄金结果不得包含 secret、机器时间或随机值；随机 jitter 使用确定性 seed。

| 领域 | 必须验证 |
| --- | --- |
| 入口 | `/v1`、`/cc`、`/ha`、`/na` 的 messages/models/count_tokens；x-api-key/Bearer；duplicate key、body limit、missing max_tokens、reasoning 边界 |
| Kiro 协议 | CLI/IDE endpoint、token refresh、EventStream 帧、thinking、tool use/result、MCP、image/document、model mapping、错误 envelope |

## 3. 真实 Claude Code CLI 验证

至少覆盖：单轮、多轮、长会话、tool loop、thinking、image/document、stream/non-stream、模型别名、首输出前故障和首输出后故障。验证事件顺序、tool id、usage、终止事件、错误状态和 transcript 不泄漏。测试必须区分 mock upstream、loopback integration 和真实 CLI；不能把单元测试描述成真实 CLI 验证。

## 4. 缓存对照验收

对每个 cache strategy 和 provider 运行 Rust/Go 双执行：

```text
same request + same account/session/model/path
→ same conversation id
→ same profile fingerprint
→ same cache usage before upstream
→ same raw/shaped/reported usage
→ same tracker update/no-update decision
```

允许时间戳、日志 request id 和内部 map 顺序不同；不允许 token 数、cache read/create 语义、scope、成功提交时机不同。对 46/46 类成功样本、首次 miss、同 session hit、混合流式/同步、失败和进程重启样本做回归。

## 5. 性能与资源门禁

- P50/P95/P99 首 token 延迟和完整响应延迟不得超过当前基线的约定预算。
- 账号规模 1k/10k、并发 100/1k、route 规则 200 条、缓存 entry 上限和大 body 下不出现线性失控。
- Redis/DB 操作必须有 timeout、retry ceiling 和 degraded behavior；缓存 tracker RSS、FD、goroutine 在长时间混合流量后稳定。
- 质量采样、usage materialization、debug capture 不得阻塞主请求。

## 6. 通过标准

只有当 contract、真实 CLI、双实例调度、缓存对照、迁移回滚、前端 E2E 和 release smoke 全部有可追踪报告时，才允许把阶段标记为完成。任何“行为基本一致”都必须附 fixture diff 或指标证据。
