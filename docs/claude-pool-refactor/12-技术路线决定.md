# 12 技术路线决定

## 决定

**在现有 Rust 代码库上原地改造**（分支 `claude-main`），不采用 Go 重写。`../ccgate` 停止推进，其 `docs/design/` 仅作需求对照参考。

## 依据

1. 本次改造的核心资产是 usage 整形算法与它的测试。这部分在 Rust 代码里是协议无关的纯逻辑，约 1.3 万行实现加 2.2 万行测试，原地改造可以零改动保留；重写则需要逐算法做等价证明，而 ccgate 在这一步已经偏离（其 13 章承认 `kiro_rs_tool_plus`、`bounded_high_cache` 仍是近似映射）。
2. 外部池调度器已经是完整、独立、经过现网验证的实现；重写等于重新经历一遍现网调过的所有边界（首输出前换号、early_commit、Redis 降级、revision 校验、质量评分避让）。
3. 删代码比写代码可控。本次工作的主体是删除约 60% 的代码并改名，每一步都有编译器和现有测试兜底；重写没有这层兜底。
4. 运维连续性：PostgreSQL、Redis、多实例协调、配置包导入导出、诊断采集、压测工具、控制台组件库全部复用，部署方式不变。
5. 时间：原地改造的 8 个阶段中，真正写新代码的只有阶段 3（BodyPatch 与路由功能化）和阶段 4（路由收口）；其余是删除、搬运、改名。

## 代价与应对

| 代价 | 应对 |
|---|---|
| 保留了一部分历史包袱（`handlers.rs` 结构、`config.rs` 体量） | 阶段 2 把 `handlers.rs` 删到约 2000 行；`config.rs` 顶层字段从 167 个减到约 60 个；文件按第 11 章目录结构拆分 |
| 旧的 `current_high_cache` 成本下限可突破 input 上限的行为被保留 | 这是用户已确认的决定：旧策略行为不动，需要绝对上下限的路由挂 `bounded_high_cache` |
| 多实例 Redis 协调继续存在，复杂度高于单实例 | 保留的是已验证的实现；C5 要求的降级路径已存在，本次只放宽触发条件 |

## 对 ccgate 的处置

- 不再提交代码，仓库保留只读。
- 其 `00-requirements.md` 中 R1–R25、C1–C14 已全部映射进本文档的 [00](00-需求与范围.md)；`08-usage-shaping.md` 的不变量表（U1–U10）作为 `bounded_high_cache` 策略的行为参照，在阶段 0 的 golden 用例中覆盖。
- 本地 39900 端口的 ccgate 预览服务可以停止。
