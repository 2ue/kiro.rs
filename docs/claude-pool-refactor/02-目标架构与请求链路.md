# 02 目标架构与请求链路

## 1. 目标架构

```
下游（Claude Code / 任何 Anthropic SDK）
        │  POST /{route}/v1/messages
        ▼
┌──────────────────────────────────────────────────────────────┐
│ anthropic/   入口层（协议无关）                                 │
│   middleware  鉴权 → 准入（RPM/并发/队列）→ 密钥额度             │
│   entry       raw body 探测、路由解析、路由功能定点改写           │
│   usage       usage 记录、计费、密钥额度累加                      │
├──────────────────────────────────────────────────────────────┤
│ account/     账号池（原 external_pool）                          │
│   manager     账号快照、候选过滤、选择、lease、排队、重试          │
│   transport   URL/头部组装、原字节转发、SSE 透传、错误分类         │
│   usage       usage 投影（调用 shaping 模块）、原地改写 usage 字段 │
├──────────────────────────────────────────────────────────────┤
│ shaping/     usage 整形纯逻辑（原 anthropic/cache.rs 等）         │
│   tracker     前缀追踪（PromptCacheTracker）                     │
│   simulation  缓存模拟（CacheSimulation）                        │
│   reported    字段整形（ReportedUsagePolicy）                    │
│   creation    写入频次控制                                       │
│   bounded / plus  两种最终收口算法                               │
├──────────────────────────────────────────────────────────────┤
│ model/       配置与模型（Config、RuntimeConfigStore、目录、映射）  │
│ storage/     PostgreSQL、Redis                                   │
│ admin/       管理 API                                            │
│ ui/          控制台                                              │
└──────────────────────────────────────────────────────────────┘
```

与现状相比只有两个结构性变化：

1. **运行时配置独立为 `model::runtime::RuntimeConfigStore`**。它负责从 PostgreSQL 加载、保存并递增版本、监听 Redis `events:runtime_config_changed` 热加载、向各模块提供带代次号的快照。现在这些职责分散在 `kiro/token_manager/manager.rs:2864-3410`、`main.rs:1566-1660`、`anthropic/handlers.rs:1626-1673`。
2. **入口层直接调用账号池**。删除 `ExternalFallbackContext` 及其周边的本地/外部分流（`handlers.rs:2055-3110`、`9065-9460`），`handle_messages_endpoint` 完成入口处理后直接 `AccountManager::forward_with_failover`。

其余模块保持现有实现，只做删除和改名。

## 2. 请求链路

下面是 `POST /{route}/v1/messages` 的完整阶段。每一步都标注它是**必要处理**（实现本系统功能所必需）、**路由功能**（默认关闭，由路由挂载决定）还是**透传**。

| # | 阶段 | 性质 | 现有代码 | 说明 |
|---|---|---|---|---|
| 1 | 鉴权：`x-api-key` 或 `Authorization: Bearer` | 必要 | `middleware.rs:571-607`、`common/auth.rs` | 不变 |
| 2 | 准入：密钥额度（Redis）、进程内 RPM/并发/排队 | 必要 | `request_admission.rs:1232-1298`、`request_key_limits.rs` | 不变 |
| 3 | 路由解析：由路径前缀得到 `RouteContext`（路由 id、缓存策略、注入项、路由功能、允许的账号规则） | 必要 | `config.rs:3850-3904`、`7019-7027`、`prompt_injection/mod.rs:420-458`、`730-757` | 一次解析，后续阶段只读；匹配规则沿用最长前缀 |
| 4 | raw body 探测：读取 `model`、`stream`、`max_tokens`、`thinking`、`metadata.user_id`、估算输入 token | 必要 | `request_entry.rs:47-260`、`request_facts.rs` | **只读不写**。现有的缺省 `max_tokens` 补齐、reasoning 别名归一、thinking budget 修复、助手历史清洗全部降级为路由功能（第 4 节） |
| 5 | 路由功能定点改写（如有开启） | 路由功能 | 见第 4 节 | 在 `serde_json::Value` 上做最小修改，再序列化回字节；没有任何功能开启时跳过本步，原字节直达第 7 步 |
| 6 | 模型限制：请求模型是否被路由/账号允许 | 必要 | `external_pool.rs:12052-12290` | 作为候选过滤条件，不改 body |
| 7 | 账号选择与 lease | 必要 | `external_pool.rs:6355-7108`、`8095-9075` | 见 [04](04-调度.md) |
| 8 | 模型映射：按账号的映射规则改写顶层 `model` | 必要 | `external_pool/model_pipeline.rs`、`body_pipeline.rs:499-553` | 只改顶层 `model` 一个字段，沿用现有 raw 模式的 `rewrite_top_level` 实现；未命中且不要求命中时原样 |
| 9 | URL 与请求头组装 | 必要 | `external_pool.rs:11852-12033` | 见第 3.2 节 |
| 10 | 发送、首输出前缓冲、失败换号 | 必要 | `external_pool.rs:6865-7056`、`retry_pipeline.rs`、`early_commit.rs` | 不变 |
| 11 | 响应透传：SSE 逐事件转发或整包转发 | 透传 | `external_pool.rs:15363-15412`、`7806-7957` | 只有三类事件会被触碰：`error` 事件脱敏、`usage` 字段按路由策略改写、`message_start`/`message_delta` 在换号后的去重 |
| 12 | usage 整形：按路由挂载的缓存策略 | 必要（策略可为 no_cache） | `usage_projection.rs`、`external_pool.rs:15818-16445` | 见 [05](05-usage整形与缓存策略.md) |
| 13 | 响应头：白名单放行，`request-id` 换成本系统 id | 必要 | `external_pool.rs:12806`、`12950-12974` | 见第 3.3 节 |
| 14 | usage 记录、计费、密钥额度累加、缓存状态提交 | 必要 | `usage.rs:2756-2827`、`usage_projection.rs:522-575` | 只有成功完成的请求提交缓存状态 |

`count_tokens` 和 `models` 端点见 [06](06-模型目录映射与限制.md)。

## 3. 透传原则与必要处理清单

R10 的要求是"除必要处理外一律透传"。这一节把"必要"定义清楚，任何不在清单上的改写都不允许存在于默认链路。

### 3.1 请求体

**默认：原始字节透传。** 现有外部池的 `request_body_mode` 有 `normalized` 和 `raw_passthrough` 两种（`external_pool.rs:609`），`normalized` 会把类型化 `MessagesRequest` 覆盖回原 JSON，过程中会做字段重排、占位替换、budget 删除等十几处改动（`body_pipeline.rs:134-257`、`external_pool.rs:12540`）。新系统删除 `normalized` 模式和这个账号字段，统一按 raw 处理。

允许改写请求体的情况只有两类：

| 类别 | 改写 | 触发条件 |
|---|---|---|
| 必要 | 顶层 `model` | 账号模型映射命中，或账号开启 `normalizeModelVersionDots` |
| 必要 | 删除 `context_management` | 账号头部画像是 `anthropic_passthrough` 且请求的 `anthropic-beta` 里没有 context-management（`external_pool.rs:12736-12798`）。这是因为上游会拒绝带该字段却没有对应 beta 的请求，属于 C6 兼容 |
| 路由功能 | 第 4 节列出的各项 | 路由显式开启 |

实现方式：第 5 步和第 8 步共用一个 `BodyPatch` 列表，每个 patch 是 JSON Pointer 加新值；没有 patch 时跳过解析，直接转发原字节；有 patch 时解析为 `serde_json::Value`、应用、再序列化。`serde_json` 默认使用 `preserve_order`（Cargo 已启用 `unbounded_depth`，需要再加 `preserve_order` feature），保证字段顺序不变。

### 3.2 请求头

沿用现有三种头部画像（`external_pool.rs:250-286`、`11921-12033`）：

| 画像 | 行为 |
|---|---|
| `generic`（默认） | 透传下游全部请求头，去掉 hop-by-hop 头、下游鉴权头（`x-api-key`、`authorization`）、`host`、`content-length` |
| `anthropic_passthrough` | 只透传白名单头（`anthropic-version`、`anthropic-beta`、`x-claude-code-session-id` 等） |
| `claude_code_mimic` | 使用固定的 claude-cli 头集合 |

三种画像之后统一做：补 `anthropic-version: 2023-06-01`（下游没带时）、写入账号 key（按 `authType` 决定 `x-api-key` 或 `Authorization: Bearer`）、应用账号的 `headerOverrides`（保留现有黑名单，`external_pool.rs:12562-12658`）、可选追加 `?beta=true`。

### 3.3 响应

- **状态码与响应头**：透传状态码；响应头按白名单放行（`content-type`、`retry-after`、`anthropic-ratelimit-*`、`anthropic-organization-id` 等），`request-id` 和 `x-request-id` 换成本系统生成的 id，流式加 `x-accel-buffering: no`、`cache-control: no-cache`。
- **非 2xx 响应体**：不透传上游错误信封。按 [11 第 3.10 节](11-实施说明与关键逻辑契约.md#310-错误分类与对外映射) 映射为固定公开文案，附 `x-error-id`；上游原始错误体写入日志与 usage 记录供排查。
- **对外模型名**：返回给调用方的 `model` 一律是调用方请求体里的原值。账号模型映射、版本号规范化，以及上游自己换了模型返回，都不会漏给调用方：流式改 `message_start` 的 `message.model`，非流式改响应体顶层 `model`，上游缺这个字段时补上。上游实际返回的模型（流式取本次尝试第一个 `message_start`，非流式取响应体顶层）记在用量记录的 `upstreamResponseModel`，控制台在它与发出的模型不一致时提示。
- **流式**：SSE 逐事件原样转发，只触碰：`message_start` 的模型名（见上）、`error` 事件（脱敏后转发）、带 `usage` 的事件（按策略改写）、换号后重复的 `message_start`（丢弃）。现有的 `ToolTranscriptSanitizer`（`external_pool.rs:15363-15412`）和 thinking 块整体缓冲降级为路由功能。
- **非流式**：整包读取（上限 16MB），`usage` 按策略改写、`model` 换回调用方原值后转发；200 但内容是 HTML、SSE 或错误信封的情况仍按协议错误换号（`external_pool.rs:7806-7957`）。

### 3.4 明确不再做的处理

以下都是为补偿 Kiro 能力缺失而存在的改写，删除：工具名映射与 schema 键清洗、tool_choice 引导前缀、合成 thinking 签名、tool 配对修复、历史占位工具、structured output 转内部工具、stop sequence 模拟、整数输出约束、空轮次 nudge、thinking XML 提取、渠道泄露过滤、代码执行、WebSearch 模板与模型驱动搜索、payload 加权裁剪、cachePoint 注入。

## 4. 可选的路由功能

这些功能现有代码已实现，但都会改写请求体或响应体。按 R10 它们**默认全部关闭**，由路由显式开启；开启后只在该路由生效。配置位置统一到 `routes[].features`（见 [03 第 4 节](03-领域模型与配置分层.md#4-路由-route)）。

| 功能 | 现有位置 | 改写内容 | 默认 |
|---|---|---|---|
| `missingMaxTokens` | `request_entry.rs:609-655`、`config.rs:461` | 请求没带 `max_tokens` 时按模型目录补默认值；不开启时让上游自己报错 | off |
| `thinkingModelName` | `handlers.rs:15102-15158` | 请求 `-thinking` 后缀模型时去后缀并注入 thinking 控制 | off |
| `thinkingTrigger` | `handlers.rs:15160-15199` | always / real_request / off | off |
| `reasoningCompat` | `request_entry.rs:81-161`、`config.rs:394` | reasoning 别名归一、budget 与 max_tokens 冲突修复 | off |
| `historySanitize` | `request_entry.rs:230`、`transcript_sanitizer.rs` | 清洗助手历史中的工具转录污染，流式响应侧同样清洗 | off |
| `payloadGuard` | `payload_guard.rs`（byte 口径部分） | 超过字节上限或收到 prompt too long 时裁剪历史并重试 | off |
| `payloadShaping` | `config.rs:602`、`handlers.rs:1239` | 历史 tool_result 截断、工具定义压缩、webfetch 结果裁剪 | off，见 [10 Q3](10-待确认事项.md) |
| `imageProcessing` | `config.rs:99-130`、`body_processing.rs`、`image_resize.rs` | 文件/URL 图片物化为 base64、media type 修正、压缩；随功能一起生效的还有两条本地前置守卫：单请求远程图片/文档源上限 20 个、当前轮内联图片 >5MB 时拒绝（开启 `resizeEnabled` 则改为压缩后放行）。功能关闭时这些检查都不做，原样透传由上游判定 | off |
| `promptInjection` | `prompt_injection.rs`、`model/prompt_injection/` | 保留 4 项：`taskQuality`、`languageConstraint`、`custom`、`identityPrompt`；其余 10 项随 Kiro 删除 | 各项 off |
| `integerOutput` | `integer_output.rs` | 当前随 Kiro 补偿层删除；若后续需要作为路由功能可再加回 | 删 |

每个功能对应一个 `BodyPatch` 生成器，输入是 `(&Value, &RouteContext)`，输出是 patch 列表；这样第 5 步只在有功能开启时解析 JSON 一次。

## 5. 错误出口

| 情况 | 响应 |
|---|---|
| 鉴权失败 | 401 `authentication_error` |
| 准入拒绝 | 429 `rate_limit_error`，带 `retry-after` |
| 密钥额度耗尽 | 429 `rate_limit_error`，带 `retry-after`（有重置时间时） |
| 路由不存在或禁用 | 404 `not_found_error` |
| 请求模型不被任何可用账号接受 | 404 `not_found_error`，文案与官方"model not found"一致 |
| 没有任何可调度账号且排队超时 | 529 `overloaded_error`（现为 503，改为与 Anthropic 一致） |
| 所有尝试都失败 | 按 [11 第 3.10 节](11-实施说明与关键逻辑契约.md#310-错误分类与对外映射) 的固定公开文案映射（429 / 400 / 529 / 502），上游原始错误只进日志与 usage 记录 |

所有 4xx 带 `x-should-retry: false`（现有 `mark_non_retryable_client_errors` 中间件保留）。
