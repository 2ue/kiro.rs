# 00 需求与范围

本章把用户在 2026-11-16 提出的需求逐条编号，后续每一章和最终验收都对照这里的编号。"来源"一列里 U 表示用户明确提出，C 表示沿用旧项目长期约定的硬约束，D 表示本方案推导出的必要结论。

## 1. 一句话定义

把当前 `kiro-rs` 改造成一个**纯 Claude Code 协议（Anthropic Messages）账号的调度网关**：账号以 `baseUrl + key` 接入，网关按路由做调度、模型限制、模型映射、优先级管理，并对返回给下游的 usage 做整形。所有 Kiro 相关能力全部删除。

## 3. 沿用的硬约束

| 编号 | 约束 | 影响章节 |
|---|---|---|
| C1 | usage 形态优先于不亏损：上下限是最终硬约束，补成本只在范围内进行 | [05](05-usage整形与缓存策略.md) |
| C2 | usage 整形只由路由挂载的策略决定，不按路径名写死；内置兜底默认值允许存在 | [05](05-usage整形与缓存策略.md) |

## 4. 推导出的结论

| 编号 | 结论 | 理由 |
|---|---|---|
| D1 | "外部池"这个词在新系统里没有对立面，统一改叫**账号（account）**；"路由（route）"沿用 | 没有本地账号后，"外部"失去含义；用户原话也把它定义为"claude code 协议的账号" |
| D2 | 只做 Anthropic Messages 入口，删除 OpenAI 兼容入口（`/v1/chat/completions`、`/v1/responses`） | 这两条入口本质是协议转换，和 R10 的透传原则冲突；见 [10 待确认 Q2](10-待确认事项.md) |
| D3 | 运行时配置的持有者必须先从 Kiro 凭据管理器中剥离出来 | 当前配置读写、热更新、外部池入口判断全部挂在 `MultiTokenManager` / `KiroProvider` 上（`src/kiro/token_manager/manager.rs:3341`、`src/anthropic/handlers.rs:1705`） |
| D4 | 不新建数据库兼容层，新分支使用全新 schema；现网外部池账号与配置通过导出/导入迁移 | 旧表里 Kiro 字段占多数，兼容成本高于重建；符合 C11 |
| D5 | 请求体默认按原始字节透传；只有路由开启了会改写请求体的功能时，才在 `serde_json::Value` 层做定点修改，不再经过类型化 `MessagesRequest` 重新序列化 | R10；旧 `normalized` 模式会丢失或重排字段（`src/external_pool/body_pipeline.rs:201-257`） |

## 5. 非目标

- 不做任何非 Anthropic 协议的上游。
- 不做上游账号的 OAuth 登录、token 刷新、额度查询（这些都是 Kiro 的概念）。
- 不做本地工具执行（代码执行、联网搜索代理执行）；服务端工具原样透传给上游。
- 不做出口代理池管理；账号可选一个出口代理字段（见 [10 Q6](10-待确认事项.md)）。
- 不重写 usage 整形算法；只做去 Kiro 命名和输入类型替换，算法与现有测试保持一致。

## 6. 与独立项目 ccgate 的关系

同级目录 `../ccgate` 是 2026-11-11 立项的 Go 重写版本，产品目标与本方案高度重合（见其 `docs/design/00-requirements.md`）。本方案是另一条路线：**保留 Rust 代码库，原地删除 Kiro**。两者的差异：

| 维度 | 本方案（claude-main） | ccgate |
|---|---|---|
| 代码基线 | 现有 Rust 代码，删除约 60% | Go 从零实现 |
| usage 整形算法 | 原样保留，测试原样保留 | 重新实现，需等价证明 |
| 多实例 | 保留 Redis 协调 | 单实例 |
| 风险 | 删除过程中的耦合破坏 | 行为等价证明 |

2026-11-17 用户确认：ccgate 原本就是按同一方向立项，但实现过程中偏离了目标；本方案（Rust 原地去 Kiro）是主线，ccgate 不再推进。ccgate 的设计文档（`../ccgate/docs/design/`）仍可作为需求对照参考，特别是 `00-requirements.md` 里用户确认过的 R 与 C 条目。
