## 2. 判定口径

全部来自脚本，本轮没有为任何用例放宽阈值。

闭环场景（`scheduler-scenarios.mjs`，每阶段独立判定）：

- 正常阶段 ok 率 ≥ 99%；名字含 `recover`/`after` 的恢复阶段 ≥ 90%；故障阶段按场景声明的 `allowed_errors` 只允许 `api_error` / `overloaded_error` / `rate_limit_error`。
- `/readyz` 的 `dispatch.progressing=false` 的秒数 ≤ 2（有排队却 5 秒无 dispatch 才算 stall）。
- 流式请求必须以 `message_stop` 收尾；上游中途断流必须变成 `event: error`，不允许 `stream_cut`（连接被掐断且无终止事件）。
- 不允许客户端传输层失败（连接错误、读错误、未声明的 `client_timeout`）。
- `burst_errors_never_recover`：全程只能是错误，p95 响应时间 < `dispatchMaxWaitSecs + 10s`，stall 为 0。
- 浸泡类场景（`long_stream_sessions`、`mixed_chaos_soak`、`everything_at_once`、`long_streams_hold_slots`、`heterogeneous_accounts`）：结束 RSS ≤ 峰值 × 0.8 或 ≤ 起始 + 150MB；服务进程存活；FD 按类别核对泄漏不变量，而不是比较总数：
  - 非套接字描述符（kqueue、unix、管道、文件）结束 ≤ 起始 + 10；
  - 下游客户端连接在脚本销毁自己的连接池后必须释放（结束 ≤ 起始 + 2）；
  - 上游连接数 ≤ 账号数 × 单账号并发（空闲池里的连接不可能多于曾经同时在飞的槽位）；
  - 数据库连接数 ≤ 配置的连接池容量（PG 主池 10 + usage 池 6 + Redis 8）。
  - 低于上限的空闲池连接是正常现象：reqwest 空闲池 90 秒、sqlx 空闲连接 10 分钟，都比 100 秒 settle 长。
- 服务进程存活由 `kill(pid, 0)` 判定。

开环用例（`overload-verdict.py`）：

- 不变量 A：有请求在排队或被拒的秒里，上游槽位使用率 ≥ 0.8（有容量就必须调度到）。
- 不变量 B：无 stall（排队中且 5 秒无上游完成且槽位 < 90%）、`/readyz` 不可用 ≤ 2 秒、drain 后队列清零、lease 回零（`accountsSummary.inFlightTotal=0`）。
- 任何账号的上游峰值在飞数不得超过它的 `maxConcurrentRequests`；无请求在 drain 后仍挂着。
- 上游整体故障的阶段（`storm_*` 的中段）不检查槽位使用率，只检查恢复。

## 4. 发现并修复的问题

### 4.1 调度缺陷：首输出后上游断流下游静默断流（`mid_stream_resets`）

现象：mock 在流输出到一半 `socket.destroy()`，53 次断流全部变成客户端侧 `stream_cut`：HTTP 200 已发出，下游收到部分 `content_block_delta` 后连接直接结束，既无 `message_stop` 也无 `event: error`。

根因：`src/account/mod.rs` 普通流路径的 unfold 里，首输出之后的 4 个不可恢复分支（上游读错误、idle 超时、lease 丢失、缓冲超限）向下游 body 流返回 `Err`，axum 据此直接关闭连接。设计契约（11 章 3.7）要求首输出后的错误"转发脱敏后的 error 事件并结束"。

修复（提交 `24933c23`，任务 `scripts/refactor/tasks/s10-mid-stream-terminal-error.md`）：4 个分支改为写一个脱敏 `event: error` 后正常结束流。读错误/超时/lease 丢失用 `overloaded_error`（Claude Code 会重试整个请求），缓冲超限用 `api_error`。usage 记录仍为 `StreamError`、不计费；首输出前的换号路径不变。3 个回归单测。

### 4.2 调度缺陷：协调器信号量瞬时饱和越过账号并发上限（`queue_overflow`）

现象：到达率约 53/s 冲 40 槽加 sub2api 式重试风暴时，mock 观测到两个账号峰值在飞 7，账号上限 4。服务日志有 6 条"Redis lease 准入不可用，尝试进程内有界 lease"，但熔断器从未真正打开。

根因：`AccountCoordinatorBreaker::try_begin` 对"熔断打开"和"256 并发信号量瞬时打满"返回同一个错误类型，调用方一律按"协调器不可用"处理，降级到进程内信号量 lease。此时 Redis 完全健康、账号的 Redis lease 还在飞，进程内 lease 是另一本账，两本账叠加越过上限。

修复（提交 `d3577372`，任务 `s11-coordinator-saturation-not-degraded.md`）：错误类型增加 `kind`（`BreakerOpen` / `AdmissionSaturated`）。信号量饱和返回 `Full` + 100ms 短等重试，走现有排队路径；只有熔断真打开才降级到进程内有界 lease。`/readyz` 新增 `coordinatorAdmissionSaturated` 计数。3 个回归单测（饱和不降级且并发 ≤ 上限；真熔断仍降级到有界 lease；饱和不打开熔断）。

### 4.3 验收工具问题

- `burst_errors_never_recover` 误报"service process exited"：采样库把 `ps`/`lsof` 任一超时当作进程不存在。改为 `kill(pid, 0)` 判存活，`ps`/`lsof` 失败只把 RSS/FD 置空（提交 `62b88343`）。
- `mixed_chaos_soak` 误报"FD did not recover"：最终采样时服务进程的 TCP 里 31 条是场景脚本自己的 keep-alive 下游连接、29 条是 reqwest 默认 90 秒空闲池里的上游连接，都不是泄漏。改为最终采样前销毁脚本连接池，浸泡场景等 100 秒再采样（提交 `63bb9ab8`）。
- `heterogeneous_accounts` / `long_streams_hold_slots` 误报"FD did not recover"（defaults 模式第 1 轮）：两个场景各阶段 ok 率 100%、stall 0，按类别采样后结束时多出的 FD 全是上游 reqwest 空闲池连接（6 → 24，90 秒空闲超时且 hyper 按 90 秒节拍驱逐）和 sqlx 空闲 PG 连接（9 → 13，10 分钟空闲超时，`pg_stat_activity` 全部 idle，上限 16），下游连接已从 8 回到 1，kqueue/unix/文件描述符不变。"结束 FD ≤ 起始 + 10"把有上限的空闲池连接当成了泄漏，之前通过只是因为起始采样恰好落在池已预热的时刻。改为按类别核对上面的四条不变量（`scripts/loadtest/lib/process-sample.mjs` 的 `classifyLsof`/`fdLeakProblems`），上限由矩阵脚本按账号数 × 并发和配置池容量传入；没有缩短生产连接池超时，也没有延长 settle。
- `mixed_chaos_soak` 的 `chaos_5`（5% 挂起流）出现 37 次 `client_timeout`：mock 挂起流只发 `message_start`，服务端首输出超时默认 120 秒与客户端 120 秒超时同刻到期，换号从未触发。隔离实例调度设置增加 `streamFirstOutputTimeoutSecs=30`（同一提交）。修正后 full 第 2 轮该阶段 940 个 200 + 1 个 502，服务端首输出超时换号 53 次。这是验收环境参数而不是代码改动，生产配置应按真实上游首字延迟设置该值。

## 4.4 发布前 CI 等价验证发现的问题（2026-11-17）

之前各阶段验收都未设置存储集成测试变量，接真实 PostgreSQL/Redis 的用例按约定自动跳过。发布前按 CI 原样（`CLAUDE_POOL_TEST_*` + `CLAUDE_POOL_REQUIRE_STORAGE_TESTS=1`，Rust 1.92.0）复跑，暴露以下问题，均已修复：

- **真缺陷**：管理端用量拆分接口（`/api/admin/usage-dashboard/breakdown`）的 SQL 在 `total_original_cost_usd,` 后直接接 `FROM`，语法错误，现网该接口必坏。
- **真缺陷（升级兼容）**：改造时删掉了 `usage_records` 的 `ADD COLUMN IF NOT EXISTS` 补列迁移块，从旧库升级时缺列不会被补上。已按当前列集合补回。
- 过时断言两处：`dispatchMaxWaitSecs=0` 的兜底值按设计是 60（原 5）；账号池总开关 `accounts.enabled` 默认开启（原外部池默认关闭）。
- 行为随设计变更的测试两处：>5MB 内联图片本地拒绝、单请求远程源上限 20 个，这两条前置守卫在阶段 3 随 `imageProcessing` 一起降为默认关闭的路由功能；测试改为显式开启该功能后再断言，另加"功能关闭时原样透传"的断言。
- Rust 1.92.0 clippy 基线超出 15 条（5 处可折叠 if、1 处默认值字段重赋值、9 处去 Kiro 化后残留的 dead code）：已改写或删除，`clippy-baseline.json` 未放宽。

- `admin::service::tests::usage_cleanup_lease_renewal_recovers_from_transient_row_lock_for_three_rounds` 在本地全量（1151 用例并行）中偶发失败（2026-11-18，发布 1.0.1 前）。用例给心跳重试 40ms 的尝试超时，在 80ms 释放行锁，等于只给第 2 次尝试留 15ms 完成一次 Postgres 往返；而且连接池只有 2 条连接：1 条被阻塞事务占着，另 1 条在第 1 次尝试超时后仍挂着未完成的 UPDATE，sqlx 归还它前要先把这条语句读完（它本身也在等锁）、再跑 `after_release` 探针和 ping，于是第 2 次尝试要先排队等这条连接可用。插桩时间线证实：加 24 个忙等进程后，解锁到第 2 次尝试返回之间最长 450ms，200ms 超时仍 8 次失败 5 次。修复：连接池给 3 条，尝试超时 1 秒、释放在 1.1 秒（与生产策略 2 秒同量级），上界断言改为"3 次尝试 + 全部退避 + 500ms"；修复后在负载均值 141 到 400 的机器上连续 10 次通过。生产心跳策略（2 秒 / 3 次 / 100ms）未改。
- 排查过程中一度把 24 个忙等进程留在后台跑验证，机器负载冲到 400、空闲内存只剩 100MB；以后注入负载只在前台单条命令内做并保证命令结束就回收。

## 4.6 高并发默认值（2026-11-17）

## 4.7 非核心逻辑不得阻断调度：请求路径审计（2026-11-18）

用户原则：统计、日志、审计等非核心逻辑失败或变慢，都不能阻断正常调度，也不能持续增压把账号调度拖垮。按这个口径把请求与调度路径上的每个“副作用”逐一核对：

| 副作用 | 进入方式 | 队列/并发上限 | 满载或后端慢时 |
|---|---|---|---|
| usage 写 PostgreSQL | `try_send` 入队，不等待 | 4096 条队列，批 64 条、5 秒超时、最多 3 次指数退避重试 | 队列满直接丢弃并计数（`droppedPersistRecords`，用量页显示“未保存记录”）；过载期对调度拒绝类记录每秒只留 1 条 |
| usage 写 Redis 摘要 | 同上 | 4096 条队列 | 同上，`droppedRedisRecords` |
| usage 内存环 | 同步，`parking_lot` 锁内只做 push | `usageRecordLimit` 条 | 满了淘汰最旧 |
| 密钥额度累计 | `tokio::spawn`，每周期一次 Redis 调用 | 每次调用 500ms 超时 | 超时只记 warn |
| 账号质量样本 / 降级标记 | `tokio::spawn` | 信号量 32 个并发任务，Redis 500ms 超时 | 拿不到许可直接丢样本 |
| 成功后重置失败计数 | `tokio::spawn`，同账号 coalesce 窗口 | Redis 500ms 超时 | 只记 warn |
| 软失败计数（换号排序信号） | 请求路径 `await` | Redis 500ms 超时 ×2 次调用 | 超时跳过，继续换号 |
| 自动禁用 | 请求路径 `await` | Redis claim 500ms、PG 条件更新 500ms | 超时跳过，不改状态 |
| 账号异动审计日志 | 后台存储执行器 best-effort 车道 | 2048 条队列、8 个 worker、单任务 5 秒 | 队列满丢弃并计数 |
| 跨实例失效通知（PUBLISH） | `tokio::spawn` | 无超时 | 只影响其他实例缓存刷新时机，不在请求路径 |
| 槽位释放回 Redis | 可靠释放调度器 + critical 车道 | 256 条队列、2 个 worker，每次 2 秒超时、重试 2 次 | 车道满走异步兜底任务；本地槽位先释放，Redis 释放失败由 lease TTL 兜底 |
| 诊断抓包 | 同步，`active` 为 false 时直接返回 | 默认关闭 | 不涉及 |
| tracing 日志 | 同步写 stdout | 由容器 json-file 驱动接管（100MB × 5 轮转） | stdout 被阻塞时 tracing 会阻塞调用线程；容器日志驱动本地落盘，实际不会阻塞 |

**发现并修复一处**：账号冷却标记（`mark_pool_cooldown` 与模型级 `mark_pool_model_cooldowns`）在故障转移路径上直接 `await` Redis，没有超时。Redis 卡住时，一次失败换号要先等这次写入返回，连接层没有响应超时就意味着无限等待。改为 500 毫秒超时；模型级多条写入共用一个截止时间，超时即跳过剩余模型继续换号。新增测试 `cooldown_markers_give_up_on_a_stalled_redis_instead_of_holding_the_failover`：用一个可随时停止转发的 TCP 中继接到真实测试 Redis 前面，握手完成后让中继吞掉所有命令，断言两个标记函数都在约 500ms 内返回而不是挂起。

**未改但记录**：
- 请求路径上同步等待 Redis 的还有软失败计数与自动禁用两处，各自已有 500ms 超时，一次失败换号最坏多花约 1.5 秒（软失败 2 次 + 自动禁用 claim 1 次），不会无限期阻塞；若要进一步压缩，可把这两处也改成后台任务，但会失去“本次换号立即看到降权”的即时性，暂不改。
- tracing 当前直接写 stdout。容器环境由 Docker 日志驱动落盘，不会反压；若将来改为直接写文件，应换成 `tracing-appender` 的非阻塞 writer。
