# 01 现状盘点与去留清单

本章回答"现在的代码里什么是 Kiro 的、什么是通用的、什么是外部池的"，并给出逐项去留结论。所有位置均为 `main`（`8946fe38`）上的 `src/` 相对路径。规模：Rust 源码 179 个文件、约 33 万行，其中 `src/kiro/` 约 10.4 万行，`src/external_pool*` 约 4.1 万行（含 2.2 万行测试）。

标记：**删** = 整体删除；**留** = 原样保留（允许改名）；**改** = 保留但要去耦合；**并** = 并入其他模块后删除原位置。

## 1. 三个决定方案走向的事实

1. **外部池已经自带一整套独立调度器**。`ExternalPoolManager`（`external_pool.rs:3461`）自己实现了候选过滤、优先级与质量评分、Redis Lua 原子 lease、心跳续期、排队等待、冷却、瞬态失败罚分、自动禁用、两个进程内熔断器和 Redis 降级时的进程内信号量。它与 Kiro 的 `MultiTokenManager` 真正共享的只有三样：Redis 并发槽的 `InFlightKeys` 结构与 Lua 脚本（`storage/redis_cache.rs:7716-7795`）、存储任务执行器 `storage_task::spawn_critical_storage_task`（`external_pool.rs:73`）、`common/capacity_signal.rs`。因此**不需要**把 Kiro 的 token_manager 改造成通用调度器，直接删掉即可。
2. **运行时配置的持有者是 Kiro 组件**。配置读取走 `KiroProvider::runtime_config_snapshot`（`kiro/provider.rs:11171`），写入和热加载在 `MultiTokenManager`（`kiro/token_manager/manager.rs:3341`、`3378`），handler 侧 `live_runtime_config` 和外部池入口都以 `state.kiro_provider.as_ref()` 为前提（`anthropic/handlers.rs:1705`、`1764`、`2070`、`7891`、`8226-8244`）。没有 provider 时外部池路径根本不会触发。这是去 Kiro 的第一刀。
3. **外部池的 usage 整形链路已经是完整且独立的**。`external_pool/usage_projection.rs` 加 `external_pool.rs:15818-16445` 已经把"真实上游 usage → 证据 → 本地模拟 → reportedUsage 字段整形 → 最终上限 → 放大 → 成本下限 → bounded 收口 → TTL 拆分 → 原地改写 JSON"全部实现，依赖的算法模块（`anthropic/cache.rs`、`prompt_cache.rs`、`prompt_cache_creation_control.rs`、`bounded_shaping.rs`、`kiro_plus_shaping.rs`）都是协议无关的纯逻辑。`handlers.rs` 里另一套本地 Kiro 的整形代码（`:3537-4126`、`:4542-5645`）可以整体删除。
