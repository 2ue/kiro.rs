# 15. 缺陷盘点与改造计划

2026-11-18 对 claude-pool 控制台与后端做的一次全面审计（不考虑多实例）。本章只记录**仍未修复**的缺陷与改造顺序；已修复项从这里删除并在第 14 章发布记录里体现。

审计范围：ui/src/features 下 13 个页面、src/admin、src/account、src/storage、src/anthropic/usage。对照基准是 main 分支（`../2ue_kiro.rs`）同名页面与接口。

## 5. 实现缺陷

### 5.1 调度与存储

- `account/mod.rs:5763-5808`：协调 epoch 路径上 Redis `INFO` 与 guard 查询无超时，且持本地锁 `coordinator_reconcile_lock` 时执行。
- `account/mod.rs:5828-5907`：reconcile 的 PG advisory lock 非取消安全；外层超时后锁跟连接泄漏回池，后续 reconcile 最长卡 10 到 30 分钟。**唯一一处会卡死调度的点。**
- `account/mod.rs:9810`：自动禁用后的 `publish_account_data_changed().await` 无超时，在请求失败路径上。
- `admin/management.rs:498-503`：总览接口每 30 秒在主业务连接池跑最长 90 天 JSONB 聚合，无缓存、无超时、无并发闸门，与调度路径抢连接。
- `main.rs:443-451`：usage 明细无自动保留任务，表只增不减；"清空"默认软删不释放磁盘；rollup 与 conversation 维度不裁剪。
- `admin/service.rs:1682`：管理端审计写入是不限数量、无超时的 spawn，是唯一不符合"有界队列 + 超时"约定的旁路写入。

### 5.2 审计与校验

- 未写审计：明文采集 start/stop/download（`capture_handlers.rs:52,64,81`）、带密钥导出（`config_transfer.rs:462`）、`promote_account_models`；失败的变更一律不留痕；管理端认证失败不记录不限速（`middleware.rs:81`）。
- `GET /config/runtime` 明文返回全局 `proxyPassword`（账号级代理是打码的）。
- 后端不校验：`usageProjection*` 百分比与阈值可为负（`service.rs:4037`）；新建账号 apiKey 可为空，落库后被静默跳过，UI 显示启用实际永不调度（`postgres.rs:1714`、`1562`）；`maxConcurrentRequests` 无上限，`u32 as i32` 溢出成负数；全局代理格式不校验。
- 删路由不检查请求 Key 的 `allowedRoutes` 引用（`management.rs:295`）；路由场景应用绕过 `normalize_routes` 的模型通配符检查（`service.rs:4007`）。

### 5.3 配置热更新

- `usageRecordLimit` 改后只是显示变了，实际不生效（`main.rs:328` 启动时固定）。
- `tlsBackend` 只在启动时读且账号转发根本不用；"生效参数"抽屉仍把它当生效项。
- 模型发现与账号测试不走代理、不用 Header/TLS profile，测试结果与真实转发不一致（`service.rs:1133`、`1302`）。

### 5.4 错误出口

- 过载三种表示并存：529 overloaded、503 overloaded、503 api_error。
- `body_processing.rs:285,452,670,773` 的 reqwest 错误（含 URL、DNS）原样以 400 返回下游。
- `account/mod.rs:13020`：透传上游 `anthropic-ratelimit-*` 响应头，暴露上游配额。
- `request_admission.rs:1160,1178`、`request_body.rs:22`：嵌套路由里用 `request.uri().path()`，前缀被 nest 剥掉，拒绝记录的 endpoint 全变成 `/messages`。

### 5.5 测试覆盖

管理端 HTTP 处理器几乎无直接测试；路由场景、明文采集、配置导入导出处理器层、`usage_projection.rs` 整个模块、`forward_with_failover`、决定对外状态码的分类函数（`is_rate_limit` 等）均无测试引用。

### 5.6 流式结束归因：下游"读完即关"被记成 client_dropped

现象（2026-11-18，17-us-debain 上 sub2api laoban → claude-pool c1）：在 sub2api 控制台对账号做"测试"，claude-pool 用量记录为 `client_dropped`、`outputTokens=0`，但上游 200、`externalAttempts[0].action=success`、首输出已到达。两条记录：`req_01Uk4evDRAGLaDraZxDyiHCA`（08:18:09）、`req_015Qym6wPHMGgpvrCrwNxWRS`（08:36:10）。

根因：
- sub2api `backend/internal/service/account_test_service.go` 的 `processClaudeStream` 读到 `message_stop` 事件即 `return`，`defer resp.Body.Close()` 在未读到 EOF 时让 Go 直接关闭 TCP 连接。
- claude-pool `src/account/mod.rs` 的 `ExternalStreamUsageGuard` 只在上游 body 读到 EOF 时 `record_success`（unfold 外层 `None` 分支）；下游在 `message_stop` 之后、上游 EOF 之前断开，就走 `Drop → record_client_dropped`，usage 一并丢失。`event_passthrough` 模式把上游 `message_stop` 原样转发，这个时间窗由下游控制。
- main 的原生 Kiro 路径是先写 success 再本地生成并发出 `message_stop`，所以同一测试打 main 的 Kiro 凭据不会出现；但 main 的外部池路径（`src/external_pool.rs:9977-10020`）与 claude-pool 逐行相同，现网 59138 库 30 天内 `external stream body dropped before completion` 有 1830 条。

修法（批次 B）：守卫记录"已向下游转发终止事件"（`message_stop` / 带 `stop_reason` 的 `message_delta` / `[DONE]`），`Drop` 时若已见终止事件则按 success 落账并保留 usage；或内层流在转发 `message_stop` 后置 `finished`，让外层 `None` 与最后一个 chunk 同轮到达。同一补丁应同步给 main 的外部池路径。sub2api 侧读到 EOF 再返回只是缓解，不作为主修复。
