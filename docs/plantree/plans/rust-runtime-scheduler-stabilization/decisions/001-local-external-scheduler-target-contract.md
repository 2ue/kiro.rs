## 1. 决策目的

为本地账号、外部池、fallback、rescue、重试、冷却、容量和排队建立一套可以被代码、配置、usage 明细和持续调度测试共同验证的目标契约。

这份记录只冻结行为边界，不冻结具体 Rust 类型、函数名或数据库表名。实现细节可以变化，但不能违反本文件中的硬约束。

## 2. 已明确的硬约束

### 2.1 策略来自配置，不来自入口路径

- `/v1`、`/cc`、`/ha`、`/na` 和自定义入口都只是入口。
- “外部池是否启用”“外部池直连策略”“本地池预检”“本地容量耗尽时 fallback”等页面配置决定行为。
- 代码不得把某个入口名称当作本地优先、外部直连、缓存策略或模型策略的隐含开关。
- 同一套配置复制到不同入口时，调度决策必须一致；只有协议注册、安全边界和明确的入口规则可以识别入口。

### 2.2 外部直连就是外部直连

当“外部池直连策略”和入口/模型规则命中时：

- 不调度本地账号。
- 外部失败不隐式 fallback 到本地账号。
- 只允许外部池内部的同池重试、换外部池、外部池临时不可调度和最终错误。
- 失败后不能因为本地账号后来变为可用而在同一请求中回本地。

### 2.3 本地优先才允许本地到外部

非直连请求先按照配置选择本地账号。只有下列条件满足时，才允许本地到外部：

- 本地状态和错误分类命中配置允许的 fallback 原因；
- 外部池对请求入口和模型有可用候选；
- 共享尝试预算和总 deadline 仍有余额；
- 当前请求尚未提交禁止重放的下游语义响应。

本地一个账号的偶发错误优先由本地同请求换号和账号冷却处理，不能因为一次错误就整体切到外部。

### 2.4 外部失败后的本地 rescue 必须有来源边界

仅当请求最初是“本地优先”，并且确实已经因为本地条件进入外部 fallback 时，才允许一次有界的本地 rescue。rescue 还必须满足：

- “外部池本地 rescue”及对应错误类型开关已启用；
- 重新读取到新鲜本地状态为 `Ready`，且有可调度容量；
- 共享尝试预算和总 deadline 仍有余额；
- 当前请求尚未提交禁止重放的下游语义响应。

以下情况禁止 rescue 到本地：

- 外部池直连；
- 原始请求没有本地账号、账号全部禁用、模型不支持、Redis 调度降级或风险熔断；
- 本地状态仍不可调度；
- 已经执行过一次 local rescue；
- 已经进入其他 fallback/rescue 回边。

### 2.5 失败账号和池不能在同一请求内反复命中

- 本地账号和外部池都必须维护请求级排除集合。
- 租约竞争失败、认证/配额/渠道禁用、明确的模型不支持和已确认的瞬态失败都要按错误类别加入排除集合。
- 跨账号/跨池后不得回到本请求已经排除的候选，除非获得新的权威运行态并明确记录重新纳入原因。

### 2.6 重试有层级、有界且共享预算

目标顺序：

1. 发送前准备失败：修正请求或直接结束，不伪造上游发送。
2. 同账号/同池：仅对配置允许且具备重试价值的瞬态错误做有限重试。
3. 换本地账号/外部池：当前候选排除后重新选择。
4. 本地到外部 fallback 或一次本地 rescue：仅按路线来源和配置允许。
5. 达到总预算或 deadline 后结束。

“推理上游最大尝试次数”必须覆盖本地发送、外部发送、外部内部 failover 和 local rescue；“辅助上游最大尝试次数”单独限制 WebSearch/MCP、Token refresh 等辅助调用，但辅助调用不能绕过请求总 deadline。

同池重试次数和外部池最多尝试不能相乘成无界发送。流式响应提交语义字节后不允许重放整个请求。

### 2.7 冷却是临时不可调度，不是永久禁用

- 冷却中的账号/池在有效期内不得被选择。
- 冷却必须记录原因、作用域（账号/池/模型）、失败次数、开始时间和剩余时间。
- 冷却期间必须正常选择其他可调度候选，而不是因为静态优先级仍然较低就反复命中坏候选。
- `401`、`402`、`403`、`429`、`5xx`、网络错误、协议错误、容量错误、认证/额度/渠道类错误默认都视为临时抖动信号；可以按权重影响短期健康分，但不能默认当成永久故障。
- 普通单次错误不得直接进入长时间池级冷却；只有重复失败证据达到严格阈值、管理员显式禁用、发送前本地配置自校验失败等少数情况，才允许写入临时不可调度。
- 管理面必须支持查看和手动清除冷却；清除后要立即使权威运行态和本地快照失效。

### 2.8 优先级是倾向，不是健康屏障

选择顺序必须先排除：

- 未启用、自动禁用、冷却中、模型不支持、容量不可用、租约协调无效的候选。

在健康候选中才使用“优先级”作为倾向。一个低数字但近期错误率持续升高的池不能长期垄断流量；健康的高数字池应能在配置允许的健康溢出条件下承接流量。

这一条是目标硬约束，但“连续失败阈值、窗口、健康溢出比例和恢复速度”仍需在验证后确定默认参数。

### 2.9 一条请求只有一个共享等待预算

请求 API Key 准入、本地账号等待、外部池等待、同池重试间隔和 local rescue 等待必须共享总 deadline。进入新的资源域时只能使用剩余时间，不能重新获得一套完整等待时间。

目标不是消灭所有队列，而是禁止多个队列无边界串联导致尾延迟和内部发送次数放大。

### 2.10 观测和业务执行隔离

- usage、dashboard、统计、配置快照和诊断写入不得阻断上游发送、流式输出、租约释放或最终响应。
- 调度轨迹可以作为 usage 明细中的独立诊断区域，用于展示请求模型、解析模型、实际上游模型、路线、候选排除、尝试账本和最终错误来源，但不能作为最终 usage 的计算输入。
- 最终 usage 必须继续按照 usage 配置、真实上游 usage，或明确的本地估算 fallback 独立计算；调度重试、换池、冷却、排队和 fallback 次数不得改变最终 usage 字段、整形规则、原始成本来源或下游标准字段。
- 建议追加运行时配置版本/规则命中摘要到调度诊断区域；在未实现前，不得把“路由轨迹”解释成完整配置快照。

## 3. 首版默认参数（验证后可调整）

以下参数用于第一版实现和隔离测试。它们不是永久锁死的产品限制；如果真实 fake-upstream 或生产观察证明不合适，按证据调整。

| 参数 | 建议起点 | 原因 |
| --- | ---: | --- |
| “同池重试次数” | 1 | 避免坏池连续占用请求；只给一次短暂恢复机会 |
| “外部池最多尝试” | 3 | 支持主池 + 两个备用池，仍有明确上限 |
| “同池重试间隔” | 100–500ms 指数退避 | 避免同步重打，控制尾延迟 |
| 普通错误短期软降权 | 10–60s 评分窗口 | 让健康池承接，但不把池硬踢出调度 |
| 临时不可调度 | 仅严格阈值命中后短期避让 | 避免持续打明显抖动候选，同时允许自动恢复 |
| 连续失败窗口 | 30–60s | 以滑动窗口区分偶发错误和故障波；同一并发波不能无限放大计数 |
| 健康溢出 | 低健康池达到阈值后允许高优先级数字池承接 10%–25% | 保护可用性，避免全量切换抖动 |
| local rescue | 最多 1 次本地发送 | 防止本地→外部→本地→外部回环 |

这些参数必须通过持续调度和错误波测试后再决定是否继续作为默认值。

## 4. 不属于本决策的内容

- 具体 UI 排版、字段内部命名和数据库迁移实现。
- 是否继续保留历史字段。
- 真实上游供应商的具体模型能力。
- 生产环境直接压测。

## 5. 已确认执行口径

用户已确认本轮核心目标，不再把实现阻塞在产品确认问题上。执行口径如下：

1. 健康的优先级 `10/20` 外部池必须能在优先级 `1` 池抖动时承接流量。
2. 所有上游错误默认都是临时抖动信号；状态码只影响权重和动作，不直接决定永久不可用。
3. 冷却/临时不可调度是严格阈值后的短期避让，不是日常错误处理的第一动作。
4. 外部直连失败不回本地；local-first 只在来源和 fresh 本地容量条件满足时允许一次本地救援。
5. 调度诊断可以记录配置版本、规则命中和尝试账本，但最终 usage 计算必须独立。
6. WebSearch/MCP 辅助失败仍保持辅助调用边界，不因本轮外部池调度改造扩大路线切换范围。
7. “外部池最多尝试 = 0”沿用现有兼容语义：按符合配置、模型、容量和健康条件的候选池自动尝试一轮，而不是固定只发一次。

## 6. 通过标准

本决策已经进入 `Accepted`，但发版仍必须满足：

- 当前符合度矩阵中的“不符合”项有实施方案；
- 持续调度验证通过正常、故障波、恢复、双实例和旁路故障场景；
- 目标行为与页面配置字段逐项对齐；
- 代码、问题文档、状态索引、plan-tree 和验证证据同步更新。
