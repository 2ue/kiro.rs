## 1. 核心目标

目标不是给每个错误码补一条规则，而是让外部池在真实抖动下尽可能可用。

已确认的执行口径：

1. 所有上游错误默认都是临时抖动信号，包括 `401`、`402`、`403`、`429`、任意 `5xx`、网络错误、协议错误、超时、容量不足、错误信封和短暂认证/额度异常。
2. 错误可以有轻重权重，但不能默认归类为永久问题。
3. 同一请求内先做有界同池重试或换外部池，不能反复打已经失败的同一个候选。
4. 优先级只影响健康候选里的倾向。优先级 `1` 的池抖动时，优先级 `10/20` 的健康池必须能接管。
5. 冷却或临时不可调度必须严格、短期、可自动恢复；不能一次普通错误就把池打入长冷却。
6. 外部直连失败只在外部池内部重试或换池，不回本地凭证。
7. 本地优先请求只有在配置允许、本地不可用、外部可用、且请求仍可安全重放时才 fallback 到外部；只有这种来源才允许一次有界回本地救援。
8. 调度和 usage 是两件事。调度重试、换池、降权、冷却、恢复不能改变最终 usage 的真实上游 usage、估算 fallback、整形字段和计费口径。

## 2. 不做的事

本轮不做这些方向：

- 不把 `401/402/403` 等 `4xx` 当成永久故障；
- 不假设上游一定会返回等待时间，也不把等待时间作为策略前提；
- 不因为某个状态码列表不完整就继续补洞；
- 不按 `/cc`、`/v1`、`/ha`、`/na` 等入口名称写死策略；
- 不把 usage 明细当作调度依据；
- 不通过强行放大重试来掩盖所有池都不可用的事实；
- 不对生产机器做压测或破坏性验证。

## 3. 参考项目学习点

### sub2api

学习目标：

- 请求内维护失败候选集合，当前请求失败后换账号/换池；
- 同账号重试和换账号次数分开；
- 临时不可调度是运行态健康信号，不是所有错误都立刻写入；
- 调度评分要考虑错误率、负载、首字延迟和优先级，而不是只按静态优先级；
- 恢复后要能重新参与调度。

不照搬：

- sub2api 的账号和协议模型不同；kiro.rs 仍必须保留外部直连、本地优先、本地到外部 fallback、一次本地救援和 usage 独立边界。

### CLIProxyAPI

学习目标：

- 请求级重试预算和换凭证预算分离；
- 短期避让用于让流量换到健康凭证；
- 避让到期后自动回到 ready；
- 按模型或候选维度隔离，不把一个模型的问题扩大成整个池不可用。

不照搬：

- CLIProxyAPI 的 key 调度和 kiro.rs 的外部池、Redis 容量、PgSQL 配置、usage 记录结构不同；只能借鉴调度思想。

## 4. 复现定义

复现不以“失败一次”为准，而以连续流量中的分布和恢复为准。

`失败 1 次`、`失败 2 次` 这类 case 只保留为基础分支 sanity control，不能作为验收标准。真正要复现的是持续累积后才暴露的问题：错误波把池全部打入不可调度、重试放大、队列堆积、租约残留、优先级坏池反复抢占、恢复后不能回流，以及多实例把同一波错误重复计数。

验收样本必须按时间窗口和流量分布判断，不按某一两个请求的结果判断。每个高可用结论至少要能说明：在故障窗口内每个池实际承接了多少业务请求、错误池的占比是否下降、健康池是否真实接管、重试放大倍数是否有界、故障停止后低并发请求是否快速恢复、RSS/FD/连接/队列是否回落。单次或双次失败测试只能证明分支没有死代码，不能证明调度策略满足目标。

### 4.1 外部池拓扑

至少准备以下 fake upstream：

| 池 | 优先级 | 基础行为 |
| --- | ---: | --- |
| A | 1 | 高优先级主池，可配置健康、连续失败、随机失败、恢复 |
| B | 10 | 备用池，可配置健康、限流、慢首字 |
| C | 20 | 备用池，可配置健康、随机失败、容量不足 |
| D/E | 可选 | 用于 5 池以上和同优先级场景 |

每个 fake upstream 必须记录请求次数、请求顺序、状态码、是否 stream、首字延迟、是否已经输出语义内容、请求模型、实际发送模型和响应 usage。

### 4.2 抖动模式

每种错误都要能按以下模式注入：

- 单次失败后恢复，仅作 sanity control；
- 连续失败 20、50、100、500 次后恢复；
- 随机失败率 10%、30%、50%、80%；
- 持续失败 5 秒、30 秒、2 分钟、5 分钟；
- 持续失败期间并发从低到高突增；
- 持续失败期间客户端对错误响应立即重试；
- 多池同时抖动，其中至少一个池健康；
- 全部池短时抖动后恢复；
- 全部池持续失败，系统有界返回错误；
- 慢首字但最终成功；
- 首语义字节前失败；
- 首语义字节后失败；
- 客户端收到错误后立即重试 2-3 次。

错误类别使用宽口径覆盖：

- `408/425/429`；
- `401/402/403`；
- `400` 中明确请求非法的情况；
- `500/502/503/504/523/529` 和其他未知 `5xx`；
- 网络连接失败、DNS 失败、请求超时、响应读取超时；
- 成功状态码但错误信封、HTML 响应、SSE/JSON 协议错配；
- 模型不支持、模型映射未命中；
- 容量不足、租约竞争失败；
- 客户端断开。

其中请求体非法、工具 schema 非法、输入过长这类确定是下游请求本身的问题，不污染池健康，也不盲目换池。

### 4.3 并发模式

必须同时覆盖：

- 闭环并发：`1 -> 5 -> 20 -> 50 -> 100`；
- 开环到达率：固定 QPS，不因服务变慢自动降速；
- 突增：`1 -> 5`、`5 -> 50`、`50 -> 500` 或按路由容量倍数放大；
- 健康流量和失败流量混合；
- 高并发故障后立刻降回低并发，验证恢复请求不被残留队列拖住；
- 至少一轮 5-10 分钟持续调度，一轮 15-30 分钟 soak。

高并发和持续报错下必须专门观察这些累积挑战：

| 挑战 | 风险 | 验证重点 |
| --- | --- | --- |
| 同步错误波 | 同一时间大量请求命中坏池，把一波失败放大成全局冷却 | 失败信号去抖，健康池承接，不出现全池黑屏 |
| 重试风暴 | 服务端同池重试、跨池重试和客户端重试相乘 | 真实发送放大倍数受预算限制，不能线性或乘法增长 |
| 队列堆积 | 坏池排队、健康池排队和 local rescue 串联 | 总等待有界，故障结束后低并发请求能快速恢复 |
| 租约残留 | 超时、客户端断开、流式中断后租约不释放 | 停止流量后租约、队列、连接、FD 回落 |
| 优先级抢占 | 优先级 `1` 池恢复或短暂可用后立刻重新垄断 | 恢复先探测和逐步回流，不能瞬时打满 |
| 多实例放大 | 多实例同时写失败状态，把同一故障波算成多轮独立失败 | 窗口内重复失败合并或降权，不能把所有池打入长冷却 |
| 全池抖动 | 所有外部池都短暂失败 | 有界返回错误，避免资源爆炸；恢复后自动成功 |
| 慢成功 | 首字慢或长流成功被误判失败 | 慢成功只影响延迟健康分，不触发错误冷却 |

## 5. 目标调度模型

### 5.1 当前请求先消化错误

失败发生后，先处理当前请求：

1. 当前候选加入本请求排除集合；
2. 如果同池重试还有预算，允许短间隔原地重试；
3. 如果跨池尝试还有预算，选择其他健康候选；
4. 如果是外部直连，最终仍只在外部池范围内结束；
5. 如果是本地优先 fallback 到外部，且本地 fresh 状态恢复为可调度，最多允许一次回本地救援；
6. 如果流式已经输出语义内容，不重放完整请求。

### 5.2 运行态健康分和临时不可调度分离

普通错误默认只做：

- 本请求排除；
- 短期软降权；
- 健康池接管；
- 成功后衰减或清除失败信号。

临时不可调度只在严格条件下发生：

- 滑动窗口内多轮独立失败证据足够；
- 管理员显式禁用；
- 发送前本地配置自校验失败；
- 模型级问题只影响对应模型或当前请求。

临时不可调度必须自动恢复，恢复后先少量探测，再逐步回流。

### 5.3 优先级是健康倾向

全部健康时，优先级 `1` 可以明显优先。优先级 `1` 抖动后，健康分必须能把流量转给优先级 `10/20`。优先级 `1` 恢复后，不需要人工清除，也不能瞬间重新打满导致再次抖动。

### 5.4 usage 独立

测试和实现都必须同时证明：

- 调度尝试次数只进入调度诊断；
- 最终成功请求只使用最终成功上游的 usage；
- 外部池上游返回真实 usage 时，原始成本按真实 usage；
- 没有真实 usage 时才使用本地估算 fallback；
- 本地整形 usage 按 usage 配置执行，不受调度路线影响；
- usage writer、Dashboard 或统计旁路失败不影响主请求调度。

## 6. 修复动作顺序

### P0：先修 132 高可用回归

目标：

- 普通上游错误不再默认写入长池级冷却；
- 失败池在当前请求内排除，允许换其他外部池；
- 短期健康分参与候选排序，让健康池接管；
- 成功后清理或衰减失败健康信号；
- 外部直连失败不回本地；
- local-first 的回本地救援继续受来源和 fresh 本地容量约束；
- 不改 usage 计算链路。

### P1：补恢复与观测

目标：

- 增加恢复探测和逐步回流；
- 补候选排除原因和尝试账本；
- 页面请求明细能解释“为什么选了这个池、为什么跳过那个池”；
- 手动清除仍可用，但不作为日常恢复依赖。

### P2：并发和多实例增强

目标：

- 并发错误波不把同一波错误无限放大成多个独立失败；
- 两实例共享运行态下不超卖、不互相回打坏池；
- Redis/PgSQL 短暂故障时主请求有界失败或切换；
- 高并发错误停止后资源回落。

## 7. 测试计划

### 第一层：本地 fake upstream 真实 HTTP

启动本地临时 kiro.rs 服务、隔离 PostgreSQL、隔离 Redis、fake 本地上游和 3-5 个 fake 外部池。

必须通过：

- A 优先级 1 健康时主要承接；
- A 在连续失败 20/50/100/500 次、随机失败和持续时间窗口内，B/C 能接管；
- A 恢复后自动回流；
- A/B 同时抖动、C 健康时 C 有真实流量；
- A/B/C 全部短时抖动后自动恢复；
- 所有池持续失败时有界报错，不队列爆炸；
- 401/402/403/429/任意 5xx 都按临时抖动和阈值处理，不默认永久；
- 外部直连本地发送数为 0；
- usage 计算不因重试或换池改变。

### 第二层：并发与持续运行

必须覆盖：

- 闭环并发阶梯；
- 开环到达率；
- 突然高并发；
- 客户端重试叠加；
- 慢首字和长流；
- 故障恢复后低并发请求快速恢复；
- 5-10 分钟持续调度；
- 15-30 分钟 soak。

本层不以“某几次请求成功”为通过标准，而以连续时间窗口内的分布和资源状态为准：

- 高优先级故障池的流量占比应下降；
- 健康备用池必须有真实承接流量；
- 错误池恢复后应逐步回流；
- 全部池不可用时返回错误必须有界；
- 请求停止后资源必须回落。

### 第三层：资源健康

测试期间和结束后记录：

- 请求成功率和错误分类；
- 每个池真实发送占比；
- 同池重试数、换池数、最终失败数；
- 真实发送放大倍数；
- 冷却/临时不可调度进入次数和恢复时间；
- p50/p95/p99 首字和总延迟；
- RSS、FD、连接数、队列深度；
- 测试进程、端口、Redis key、PgSQL 临时库清理结果。

## 8. 发版条件

满足以下条件才允许进入发版：

1. 文档、issue 索引、plan-tree 状态已同步；
2. P0 修复完成；
3. fake upstream 真实 HTTP 场景通过；
4. 重复失败、随机失败、持续失败、恢复、并发突增均通过；
5. 外部直连、本地优先、local-first fallback、本地救援边界通过；
6. usage 独立性通过；
7. 资源健康和临时产物清理通过；
8. scoped Cargo、feature docs、diff/fmt、build artifact inventory 等门禁通过。

如果任一场景失败，先记录失败证据和原因，再判断是测试假设问题、配置问题还是代码实现问题；不能用缩窄 case 的方式绕过失败。
