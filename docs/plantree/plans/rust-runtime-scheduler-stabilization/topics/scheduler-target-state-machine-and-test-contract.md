## 1. 这份文档解决什么问题

这份文档不是实现说明，也不是单个错误码的修复记录。它先把用户要求转换成一份可以被：

- 页面配置解释；
- Rust 调度代码实现；
- usage 明细展示；
- 假上游真实 HTTP 请求；
- 双实例和持续流量验证；

共同检查的目标契约。

在这份契约被确认、实现并通过真实持续调度验证之前，不能把“优先级故障池会自动让路”“外部直连绝不回本地”“本地故障会平滑切外部”等目标写成已经完成。

## 2. 目标审视结论

用户提出的总体思路是合理的，核心目标可以归纳为：

1. **本地优先是默认路线**：有可调度本地账号时先用本地；单账号失败先换本地账号。
2. **外部直连是独立路线**：启用“外部直连策略”后，只调度外部池；外部失败不能隐式回本地。
3. **本地到外部必须有条件**：只有本地路线确实不可用、配置允许、外部有实时可调度候选且请求仍可安全重放时，才转外部。
4. **错误应在内部消化，但必须有界**：同账号重试、换本地账号、同池重试、换外部池、跨本地/外部切换，都要受同一个请求级尝试预算和总截止时间约束。
5. **冷却是临时不可调度**：冷却中的账号或外部池必须从候选集中移除，其他健康候选可以接管；恢复后再按受控速度恢复流量。
6. **优先级是健康候选中的倾向，不是故障屏障**：数字越小只表示健康时更优先，不能让持续失败的优先级 1 池无限垄断。
7. **调度与 usage 计算分离**：调度只决定资源选择和允许的重试/切换；最终 usage 必须继续按照 usage 配置、真实上游 usage 或明确的本地估算 fallback 计算。调度路线和尝试只能作为独立诊断元数据，不能改变最终 usage 字段、整形规则或原始计费口径。

### 2.1 当前实现不是完全没有这些能力

源码中已经存在若干局部边界：

- 外部直连路线已经有单独的路线类型，当前代码显式禁止直连失败后本地救援。
- 本地失败到外部已经有按“容量不足、调度 Redis 降级、无可用凭据、瞬态错误、模型不支持”等原因的配置分类。
- 外部池已经有同池重试、跨池尝试、`Retry-After`、池/模型冷却、请求级排除集合。
- 外部失败回本地已经限制为来源明确的本地优先请求，并要求重新读取本地状态；救援入口不再回到外部 fallback 上下文。
- 本地账号已经有并发、RPM、sticky、排队、冷却和 Redis 租约处理。

### 2.2 当前明确不满足目标的结构

以下不是“感觉问题”，而是源码级已经能确认的缺口：

1. **外部池排序仍是优先级硬排序**：当前候选先按“优先级数字 → 负载 → 池编号”排序。只要故障池尚未进入冷却或请求级排除，健康的较高数字池不会主动溢出接管。
2. **没有统一的端到端等待账本**：请求准入、本地排队、外部池排队、同池重试间隔和本地救援各自有等待上限，但进入下一层时还没有统一的“剩余截止时间”。
3. **调度诊断账本还不完整**：本地发送、外部发送、外部内部换池和本地救援虽然部分共享推理尝试预算，但当前诊断元数据还不能完整解释每次候选排除、真实发送和转换原因。这个账本只能服务于排障和统计，不能参与最终 usage 的 token 整形或成本计算。
4. **配置是局部开关集合**：页面已经有“本地容量预检”“容量不足 fallback”“调度 Redis 降级 fallback”“外部池最多尝试”“同池重试次数”“启用回本地”等开关，但它们之间的优先关系、总预算关系和故障恢复语义没有被一个统一的路线计划表达。
5. **持续故障波尚未通过真实请求证明**：已有 focused 测试不能替代优先级 `1/10/20` 三池连续故障、恢复、双实例冷却传播和 15–30 分钟稳定性验证。

因此当前结论是：

> 目标设计方向正确；现有代码只能被称为“局部符合”，不能直接宣布满足高可用调度目标。先确认下面的契约，再按不符合项分阶段实现。

## 3. 当前真实请求链路

当前请求的大致顺序如下，名称是为了说明职责，不代表目标实现必须保留这些函数：

```text
请求入口
  -> 请求 API Key 准入
  -> 请求体/模型/缓存/提示词/工具处理
  -> 外部直连策略判断
  -> 本地账号状态预检
  -> 本地账号获取/排队/租约
  -> 本地上游发送
  -> 本地错误分类
  -> 本地到外部 fallback
  -> 外部池权威快照/容量租约/发送
  -> 外部池同池重试或换池
  -> 外部最终错误分类
  -> 有条件的一次本地救援
  -> 流式提交或非流式响应
  -> usage/统计/汇总旁路写入
```

### 3.1 当前链路中的关键含义

| 阶段 | 当前事实 | 目标约束 |
| --- | --- | --- |
| 请求 API Key 准入 | 有单独的入口限流/准入 | 只能扣除总等待和准入预算，不能给后续队列重新发一套完整等待时间 |
| 外部直连判断 | 命中“外部直连策略”时直接进入外部池 | 不得调度本地；失败不得隐式本地救援 |
| 本地状态预检 | 依据本地状态和 fallback 配置判断是否可直接外部 | 只能作为路线规划输入，不能替代本地最终账号租约 |
| 本地账号获取 | 过滤禁用、冷却、模型不兼容、并发/RPM 和 sticky 绑定 | 同一请求失败账号必须排除；本地健康时不应被外部池配置拖慢 |
| 本地错误分类 | 根据错误文本、错误类型和尝试记录判断 fallback 原因 | 请求本身错误不能被错误地转成跨池重试 |
| 外部池选择 | 读取权威池快照和运行态后选择候选 | 先过滤不可用，再在健康候选中使用优先级倾向 |
| 外部池发送 | 获取容量租约后发送，可同池重试或换池 | 所有真实发送扣同一总尝试预算；流式已提交后不能重放 |
| 外部最终错误 | 交给调用方或尝试本地救援 | 只有原始 local-first 且本地重新 Ready 时才允许一次救援 |
| usage/统计 | 在请求完成后记录最终 usage，并可附带独立的调度诊断元数据 | usage 计算必须按照 usage 配置和上游 usage 独立完成；旁路写入不能阻断发送、流式输出或租约释放 |

## 4. 目标路线模式

路线模式必须由运行配置、路由规则、模型规则和实时资源状态共同决定；不能根据 `/v1`、`/cc`、`/ha`、`/na` 这些入口名字写死。

### 4.1 模式矩阵

| 模式 | 进入条件 | 首选资源 | 允许的转换 | 明确禁止 |
| --- | --- | --- | --- | --- |
| 本地优先 | 外部池关闭，或外部池开启但未命中“外部直连策略” | 本地账号 | 本地换账号；按配置本地到外部；满足来源边界时一次本地救援 | 外部池配置改变本地健康请求的等待语义 |
| 本地优先 + 外部备用 | 外部池开启、未命中直连、本地存在或可能存在账号 | 本地账号 | 本地同请求换账号；本地故障后外部池；外部失败后最多一次本地救援 | 因外部池静态存在就跳过本地健康容量 |
| 外部直连 | “外部直连策略”命中 | 外部池 | 同池重试；换外部账号/换外部池；最终外部错误 | 调度本地；本地救援；改成标准处理后偷偷走另一条路线 |
| 无本地账号临时外部 | 外部池开启、非直连、本地明确无账号且配置允许 | 外部池 | 外部内部重试；本地账号新增后下一请求快速回到本地优先 | 把外部错误伪装成本地账号错误 |
| 仅本地 | 外部池关闭或路由规则禁止外部池 | 本地账号 | 本地换账号、有限本地重试、排队 | 读取外部池并影响本地主路径 |

### 4.2 同一请求的路线来源必须不可变

请求开始后应创建一份不可变的“路线计划”，至少包含：

- 首选资源：本地账号 / 外部池；
- 是否允许本地到外部；
- 是否允许外部到本地救援；
- 同账号/同池重试上限；
- 换账号/换池上限；
- 总真实上游发送预算；
- 总截止时间；
- 流式是否已经提交下游语义字节；
- 当前已排除账号、外部池和模型候选；
- 当前配置版本和规则命中摘要。

后续执行器只能在这份路线计划允许的转换内行动，不能在 handler、账号管理器和外部池管理器中各自重新决定一遍完整路由。

## 5. 目标有限状态机

### 5.1 状态

```text
准入
  -> 规划完成
  -> 选择本地候选
  -> 等待本地容量
  -> 本地发送
  -> 选择外部候选
  -> 等待外部容量
  -> 外部发送
  -> 同资源重试
  -> 排除当前候选并切换
  -> 本地到外部 fallback
  -> 外部到本地救援
  -> 成功提交
  -> 最终错误
```

### 5.2 允许转换

| 当前状态 | 失败/事件 | 下一步 |
| --- | --- | --- |
| 选择本地候选 | 某账号已冷却、禁用、容量租约竞争失败 | 排除该账号，选择其他本地账号 |
| 本地发送 | 可重试的瞬态错误且同账号重试预算有余 | 同一账号有限重试 |
| 本地发送 | 同账号预算耗尽或错误明确属于账号不可用 | 冷却/排除当前账号，切换其他本地账号 |
| 本地发送/本地等待 | 本地路线分类命中、外部启用、外部有实时可调度候选、总预算未耗尽 | 本地到外部 fallback |
| 选择外部候选 | 池冷却、禁用、模型不支持、租约拒绝 | 排除该池，选择其他外部池 |
| 外部发送 | 配置允许的瞬态错误且同池预算有余 | 同一外部池重试 |
| 外部发送 | 跨池可重试错误 | 冷却/排除当前池，选择其他外部池 |
| 外部最终错误 | 原始 local-first、未执行救援、本地新鲜状态 Ready 且有容量 | 一次本地救援 |
| 外部最终错误 | 外部直连、无本地账号、全部本地禁用、模型不兼容、Redis 降级或本地风险熔断 | 直接返回外部最终错误 |
| 冷却到期 | 健康探测成功或冷却自然结束 | 进入候选，但按恢复观察权重逐步恢复 |

### 5.3 明确禁止转换

```text
外部直连 -> 本地救援
本地救援 -> 外部 fallback
外部 fallback -> 本地救援 -> 外部 fallback
同一请求重新命中已排除账号/池
流式已提交语义字节后重放完整请求
进入新队列时重新获得完整等待时间
因优先级较高而跳过健康备用池
usage/Dashboard 写入失败 -> 主请求失败
调度重试/换池次数 -> 改写最终 usage token 或 usage 整形规则
调度候选数量/冷却状态 -> 改写原始计费口径
```

## 6. 错误分类与动作

错误分类必须优先使用结构化状态码、错误类型、上游响应阶段和流式提交状态，错误文本只作为兼容补充。

| 错误类别 | 同资源重试 | 换资源 | 冷却/临时不可调度 | 跨本地/外部 | 说明 |
| --- | --- | --- | --- | --- | --- |
| 请求体非法、工具 schema 非法、模型字段非法、输入过长 | 否 | 否 | 否 | 否 | 这是请求错误，不能把同一错误复制给其他账号 |
| 认证失败、额度耗尽、渠道禁用 | 否或仅按协议完成一次刷新 | 是 | 长冷却或自动禁用 | 仅按路线配置 | 当前候选应立即排除，不能反复打 |
| 429/限流 | 通常最多一次短重试 | 是 | 使用 `Retry-After` 或退避 | local-first 可按配置切换；直连不回本地 | 不应让同一池连续占用请求 |
| 408/5xx/网络超时 | 有限同资源重试 | 是 | 短冷却并按连续失败上浮 | 按路线配置 | 连续失败时健康备用池应接管 |
| 成功状态码但协议污染/错误信封 | 默认不在同池重复 | 是，须开启“协议错误跨池重试” | 短冷却或按协议错误策略 | 不能把客户端请求错误当协议错误 | 记录真实上游响应摘要 |
| 模型不支持/模型映射失败 | 否 | 仅切换明确支持该模型的候选 | 模型级或请求级排除 | 不应盲目回本地 | 先修正模型映射或透传语义 |
| 外部容量满/租约竞争失败 | 不发送同一池请求 | 是 | 临时不可调度 | local-first 可按“容量不足 fallback”策略决定 | 健康备用池必须能承接 |
| 本地账号队列满/RPM 满/全部冷却 | 不重复打已排除账号 | 换本地账号或按配置转外部 | 本地账号冷却 | 只在 local-first 允许转外部 | 不应因为外部池静态存在而改变本地健康排队 |
| Redis 调度降级 | 不重复无效租约 | 可按配置转外部或保持本地 | 记录故障域和短暂降级 | 直连不回本地 | 外部池 Redis 故障不能拖慢本地 Ready |
| 流式首语义字节前错误 | 可按预算重试/切换 | 是 | 按错误类别 | 可按路线规则 | 尚未向下游提交语义，可安全重放 |
| 流式首语义字节后错误 | 不重放完整请求 | 只允许协议明确的流内处理 | 记录中断 | 不切换整条请求 | 防止重复文本/工具调用 |
| 客户端主动断开 | 否 | 否 | 释放租约/取消任务 | 否 | 不能因为客户端断开触发池冷却 |

## 7. 优先级、健康和冷却目标

### 7.1 选择顺序

候选选择必须分两层：

**第一层：硬过滤**

- 未启用；
- 手动禁用；
- 自动禁用；
- 池/账号冷却中；
- 当前模型不支持；
- 当前请求已排除；
- 当前容量不可租约；
- 调度协调不可用且没有安全降级；
- 配置明显无效。

**第二层：健康候选排序**

- 健康状态；
- 连续失败数和失败率窗口；
- 最近成功时间；
- 当前负载；
- 配置优先级；
- 稳定的随机扰动或轮转。

“优先级”只在第二层使用。优先级 `1/10/20` 的目标行为是：

- A（优先级 1）健康时明显更常被选；
- A 偶发错误时先做有限同池重试或短冷却；
- A 连续失败达到阈值后，B/C 必须承接真实流量；
- A 恢复后先进入观察窗口，再逐步恢复主流量；
- A 不得因为静态优先级最小而永久压制 B/C。

### 7.2 冷却语义

冷却不是永久禁用，至少要记录：

- 作用域：账号、外部池、模型；
- 原因：限流、服务繁忙、网络、协议、认证、额度、模型不可用；
- 首次失败时间；
- 连续失败次数；
- 冷却截止时间；
- `Retry-After` 来源；
- 是否自动禁用；
- 是否允许手动清除。

冷却期间：

- 候选选择必须跳过该账号/池；
- 其他健康候选可以承接；
- 不能因为“优先级更高”重新打冷却候选；
- 冷却清除后要让本地和跨实例快照立即失效；
- 自然恢复后要有短暂观察/降权，避免恢复瞬间再次打满。

## 8. 尝试预算、排队与总截止时间

### 8.1 预算拆分

页面上的“外部池最多尝试”和“同池重试次数”必须保持不同含义：

- **外部池最多尝试**：同一请求最多真实尝试多少个外部池/外部发送机会；
- **同池重试次数**：同一外部池在瞬态错误后原地重试多少次；
- **本地账号切换次数**：同一请求最多更换多少个本地账号；
- **本地救援次数**：目标固定最多一次；
- **辅助调用尝试次数**：WebSearch、MCP、刷新等辅助请求单独计数；
- **总真实上游发送预算**：跨本地、外部、救援和内部换池的最终硬上限。

这些预算不能相乘成无界发送。每次真实发送前都必须扣除总预算，扣除失败直接结束或进入允许的最终错误。

### 8.2 共享总截止时间

请求需要在“请求 API Key 准入”完成后建立一个总截止时间。后续所有等待都只使用剩余时间：

```text
总截止时间
  - 请求 API Key 准入等待
  - 本地账号排队等待
  - 外部池容量等待
  - 同池重试间隔
  - 本地救援等待
  = 剩余可用时间
```

不能每进入一个队列就重新获取完整的“最大等待秒数”。否则一个请求可能在多个资源域各等待一遍，最终产生高尾延迟和发送放大。

### 8.3 排队规则

- 有健康候选但只是瞬时容量满：按该资源域配置短暂排队；
- 已确认候选不可用：立即排除并换候选，不在坏候选上排长队；
- 外部直连只有外部池队列；
- 本地优先只有在配置允许的本地容量溢出策略下才转外部；
- 本地和外部不能串联无限排队；
- 队列满、等待超时、租约丢失必须形成结构化错误并记录路线原因。

## 9. 页面配置的目标语义重组

下面使用页面上的中文字段，不把内部变量名当作产品语义。

### 9.1 路线策略

| 页面字段 | 目标作用 | 不应控制 |
| --- | --- | --- |
| 外部池启用 | 是否允许该配置使用外部池 | 不应单独决定本地账号是否排队 |
| 启用显式直连 | 命中时只走外部池 | 不应自动回本地 |
| 本地容量预检 | 是否在发送前读取本地状态并规划转移 | 不应替代本地最终租约 |
| 容量不足 fallback | 本地容量满时是否允许转外部 | 不应让单账号一次失败直接全局转外部 |
| 调度 Redis 降级 fallback | 本地调度 Redis 降级时是否允许转外部 | 不应让外部 Redis 故障拖慢本地 Ready |
| 无可用凭据 fallback | 本地明确无可用账号时是否允许转外部 | 不应把外部错误伪装成本地错误 |
| 瞬态错误耗尽 fallback | 本地账号连续瞬态失败后是否允许转外部 | 必须受失败窗口、排除集合和总预算约束 |
| 模型不支持 fallback | 本地模型不支持时是否允许转外部 | 不能绕过模型支持校验 |

### 9.2 外部池尝试与重试

| 页面字段 | 目标作用 |
| --- | --- |
| 外部池最多尝试 | 限制同一请求的外部发送机会；`0` 的现有语义“按候选池自动尝试一轮”需要保留并在页面明确 |
| 网络错误跨池重试 | 无 HTTP 状态码的连接、DNS、超时是否允许换池 |
| 协议错误跨池重试 | 成功状态码但协议内容错误是否允许换池 |
| 跨池重试状态码 | 哪些 HTTP 状态码允许换池 |
| 同池重试次数 | 同一池原地重试次数，不与外部池最多尝试相乘失控 |
| 同池重试状态码 | 哪些状态码先在同池原地重试 |
| 同池重试间隔 | 原地重试的等待，必须消耗共享总截止时间 |

### 9.3 冷却与恢复

现有本地账号的“限流后暂停”“服务繁忙后暂停”“网络错误基础冷却”“流式中断后暂停”“格式异常后暂停”“授权异常后暂停”“最大冷却时长”等字段，应与外部池冷却采用同一语义模型：

- 错误类型；
- 作用域；
- 初始时长；
- 连续失败退避；
- 抖动；
- 最大时长；
- 是否自动禁用；
- 是否手动清除；
- 恢复观察窗口。

### 9.4 回本地

| 页面字段 | 目标作用 |
| --- | --- |
| 启用回本地 | 只对原始 local-first 且确实进入外部 fallback 的请求生效 |
| 429 时回本地 | 外部最终限流且本地新鲜 Ready 时允许一次救援 |
| 超时时回本地 | 外部最终超时且本地新鲜 Ready 时允许一次救援 |
| 容量失败回本地 | 外部最终容量失败且本地新鲜 Ready 时允许一次救援 |
| 回本地最多等待 | 使用共享剩余截止时间，不能重新获得完整等待预算 |

## 10. usage 独立边界与调度观测目标

### 10.1 硬边界：调度不能参与最终 usage 计算

调度域和 usage 域必须是两个独立的阶段：

```text
调度域：
  路线规划 -> 账号/外部池选择 -> 排队 -> 重试/换候选 -> 最终响应来源

usage 域：
  成功响应 usage 捕获
    -> 按 usage 配置进行标准字段整形
    -> 原始 usage / 展示 usage / 最终上报 usage 分离
    -> 原始成本、展示计费、上报费用分别计算
    -> 旁路持久化和汇总
```

必须满足：

- 调度不读取或修改最终 usage 的 token 整形配置；
- 调度重试次数、换号次数、外部池优先级、冷却状态和排队等待时间，不得改变最终 usage 字段；
- 失败的本地/外部尝试不能和最终成功尝试的 usage 相加；
- 同一请求在不同调度路线下，只要最终上游返回相同 usage，最终下游 usage 必须一致；
- 外部上游返回真实 usage 时，原始 usage 以真实 usage 为准；
- 外部上游没有 usage 时，才按既有本地估算规则生成原始 usage fallback；
- 本地估算可以用于“缺少真实 usage 时的原始成本 fallback”和本地整形输入，但不能被调度逻辑替换或二次放大；
- usage 旁路写入、Dashboard 汇总和统计失败，不能触发重试、换号、冷却或 fallback。

调度可以把以下信息附加到 usage 明细的诊断区域，但这些信息不是 usage 计算输入：

- 首选路线；
- 实际路线；
- 同账号/同池重试次数；
- 换账号/换池次数；
- fallback/rescue 原因；
- 候选排除原因；
- 总等待和最终错误阶段。

### 10.2 调度诊断明细

每条请求明细的诊断区域至少需要能够回答：

1. 请求模型是什么；
2. 本地解析模型是什么；
3. 实际外部上游模型是什么；
4. 入口配置命中了什么路线规则；
5. 首选路线是本地还是外部；
6. 每个本地账号/外部池为什么被排除；
7. 真实发送了几次本地请求、几次外部请求；
8. 是否做了同账号/同池重试；
9. 是否发生了本地到外部 fallback；
10. 是否发生了一次本地救援；
11. 最终错误来自哪个上游、哪个池、哪个阶段；
12. 当时使用的调度配置版本或规则摘要是什么。

展示层仍应使用页面已有中文字段：

- 路由；
- 状态与路由；
- 模型（请求）；
- 模型（本地解析）；
- 模型（上游）；
- Fallback 原因；
- 直连原因；
- 错误阶段；
- 内部错误信息；
- 外部错误信息。

### 10.3 最终 usage 计算验收

最终 usage 必须单独校验以下字段和来源：

- 上游真实 usage；
- 本地估算 usage（仅在真实 usage 缺失时）；
- 本地整形后的 usage；
- 下游标准 usage；
- 上游原始成本；
- 展示计费；
- 上报费用；
- usage 是否为估算；
- usage 整形是否已应用。

调度诊断字段可以说明“这次请求经过了几次尝试”，但不能把这些尝试的输入输出 token 累加到最终成功请求的 usage 中。

usage、Dashboard 汇总和统计写入必须是旁路操作。写入失败、延迟或队列满时，最多影响观测完整性，不得阻断上游发送、流式输出、租约释放、最终响应或最终 usage 的既定计算。

## 11. 分阶段改造方案

### 阶段 A：先补“观测合同”，不改变路线行为

目标：

- 增加请求级路线计划摘要；
- 增加本地账号/外部池候选排除原因；
- 增加独立于 usage 计算的真实发送尝试账本；
- 区分“预检未发送”“同资源重试”“换资源发送”“本地到外部”“本地救援”；
- usage 明细的诊断区域记录调度配置版本/规则命中摘要；不把它们作为 usage 计算输入。

验收：

- 不改变现有成功/错误路线；
- 通过 fake upstream 日志能和 usage 账本逐请求对齐；
- 旁路写入故障不影响主请求。

### 阶段 B：统一路线计划、尝试预算和总截止时间

目标：

- 在执行前生成不可变路线计划；
- 本地和外部调度器只接受候选集和剩余预算；
- 所有真实发送共享总尝试预算；
- 所有等待共享总截止时间；
- 禁止 rescue 回到外部 fallback。

验收：

- 表驱动状态机覆盖所有允许/禁止转换；
- 真实上游发送次数始终不超过预算；
- 多队列串联不会重新获得完整等待时间。

### 阶段 C：健康感知优先级和临时不可调度

目标：

- 先硬过滤冷却/禁用/不支持/已排除候选；
- 对健康候选使用优先级倾向；
- 连续失败窗口触发健康降权或临时不可调度；
- 健康的较高数字池能够承接；
- 恢复池先观察再逐步回切。

验收：

- 真实配置 A/B/C=`1/10/20` 下，A 连续故障时 B/C 有实际流量；
- A 恢复后不会瞬时垄断；
- B/C 不会因为优先级较高而永远无流量。

### 阶段 D：双实例和故障域隔离

目标：

- 冷却、租约、快照、手动清除在两个实例间一致；
- 外部池 Redis/PgSQL 故障不拖慢本地 Ready；
- usage/Dashboard 延迟不阻断主业务；
- 重启后租约、队列和冷却最终收敛。

验收：

- 双实例同时发送不超卖；
- 一个实例写入冷却后另一实例不继续回打；
- 清除冷却后两实例都能按恢复规则调度；
- 旁路故障下主业务持续成功。

## 12. 真实持续调度验证方案

不能只跑单元测试。必须启动隔离服务，使用真实 HTTP 调用和可记录请求顺序的假上游。

### 12.1 隔离拓扑

```text
测试客户端
  -> kiro.rs 实例 A（临时端口）
  -> kiro.rs 实例 B（可选，共享隔离 PostgreSQL/Redis）
       -> 假本地上游
       -> 外部池 A（优先级 1）
       -> 外部池 B（优先级 10）
       -> 外部池 C（优先级 20）
```

每个假上游必须记录：

- 请求顺序；
- 请求模型；
- 实际外发模型；
- `anthropic-version`；
- 是否流式；
- 是否已经发送首个语义事件；
- 返回状态、错误类别和延迟；
- 请求 ID 与场景编号。

### 12.2 并发模型与流量波定义

并发不能只用一个“并发 20–50”概括。测试必须同时使用两种流量模型：

- **闭环并发**：固定数量的客户端请求，上一请求结束后才发下一请求，用来观察账号/池容量、排队和恢复；
- **开环到达率**：按照固定到达速率发请求，不因为服务变慢而自动降低到达率，用来暴露队列堆积、重试放大和反馈回路。

设：

- `C_local` = 本地所有可调度账号的总并发容量；
- `C_external` = 当前模型可用外部池的总并发容量；
- `C_route` = 当前路线实际可用容量，取决于路线模式和实时健康候选；
- `A` = 单位时间下游到达请求数；
- `S` = 单位时间真实上游发送数；
- `R = S / A` = 真实发送放大倍数。

并发测试至少覆盖以下突发形态：

| 场景 | 流量变化 | 故障变化 | 必须观察 |
| --- | --- | --- | --- |
| 小并发突增 | 闭环 `1 → 5 → 20`；开环 `A=1x → 5x C_route`，突增窗口 1–2 秒 | 全部健康 | 本地/外部切换、队列峰值、首字延迟、是否误触发 fallback |
| 中并发突增 | `5 → 50` 或 `0.25C_route → 2C_route` | 全部健康 | 是否有界排队、是否超卖租约、是否出现容量错误 |
| 大并发突增 | `50 → 500` 或 `C_route → 5C_route`，至少持续 30–120 秒 | 全部健康 | admission、队列上限、拒绝比例、RSS/FD/任务数、恢复时间 |
| 小并发全错 | `A` 维持 1–5 请求/秒 | 当前池 100% 5xx/网络错误 | 是否重复打坏池、冷却生效时间、备用池接管 |
| 大并发全错 | `0.5C_route → 5C_route` | 优先级 1 池在同一时间窗口全部报错 | 错误波是否形成重试风暴、B/C 是否承接、健康状态传播延迟 |
| 大并发部分错 | `C_route → 3C_route` | A 失败率 5%、50%、100% 分档 | 失败阈值、优先级溢出、错误池流量占比、恢复回切 |
| 错误后恢复 | 保持高并发，故障池从错误恢复 | A 返回 200，B 或本地短暂受限 | 恢复观察窗口、回切速度、是否瞬时再次打满 |
| 客户端重试叠加 | 下游收到 429/5xx 后立即重试 2–3 次 | 上游同时出现 5xx/429 | 服务端内部重试与客户端重试是否相乘 |
| 长流并发 | 10/50/100 个并行流式请求 | 首语义字节前失败、首语义字节后失败分档 | 是否错误重放、租约是否释放、流结束后资源是否回落 |

并发场景的通过条件不是“最终有一次成功”，而是同时满足：

- 真实发送放大倍数 `R` 不超过路线总预算允许的上界；
- 已排除的账号/外部池不会在同一请求内被重打；
- 队列、任务、连接和租约有明确上限；
- 故障池不会因为请求同时到达而被所有实例重复探测；
- 高并发错误波后，低并发正常请求能在规定恢复窗口内恢复；
- 流量停止后队列、任务、RSS、FD 和连接数回到基线附近。

### 12.3 第一组：路线边界

每个场景至少重复 stream 和 non-stream，各 5 轮：

1. 只有健康本地账号；
2. 本地优先 + 外部启用 + 本地 Ready；
3. 外部直连 + 外部成功；
4. 外部直连 + 外部 429/5xx/网络错误；
5. 本地单账号错误，另一本地账号健康；
6. 本地全部冷却；
7. 本地全部禁用；
8. 本地无账号；
9. 本地 fallback 到外部，外部成功；
10. 本地 fallback 到外部，外部失败后本地恢复 Ready；
11. 外部失败但本地仍不可调度；
12. Raw 透传和标准处理的模型映射、请求头和正文处理。

验收重点：

- 外部直连本地真实发送数为 0；
- 本地 Ready 时外部真实发送数为 0；
- 本地救援最多一次且不回外部；
- 同一请求不再次命中已排除账号/池；
- 流式提交后不重放。

### 12.4 第二组：优先级故障波

配置外部池 A/B/C 的优先级为 `1/10/20`：

```text
0–60 秒    A/B/C 全部健康
60–120 秒  A 连续 5xx/网络错误
120–180 秒 A 恢复，B 返回 429 + Retry-After
180–240 秒 本地账号部分冷却
240–300 秒 Redis 调度短暂延迟或断开
300–360 秒 全部恢复
```

并发建议从 10、25、50 分档，每档至少持续 5 分钟；先单实例，再双实例。

验收重点：

- A 故障后 B/C 在有限时间内获得真实流量；
- 不重复打冷却中的 A；
- B 的 `Retry-After` 影响 B，不冻结整个池；
- A 恢复后逐步回切；
- 总真实发送次数不超过预算；
- 错误波后成功率、队列、连接数、RSS 和文件描述符回落。

### 12.5 第三组：本地/外部切换

覆盖：

- 本地部分账号连续失败；
- 本地全部账号容量满；
- 本地全部账号 RPM 满；
- 本地 Redis 降级；
- 外部池部分可用；
- 外部池全部冷却；
- 外部池全部容量满；
- 外部池最终失败但本地恢复；
- 外部池最终失败且本地仍不可调度；
- 直连模式下本地后来恢复。

验收重点：

- 只有 local-first 才能发生本地到外部；
- 只有 local-first 且 fresh 本地 Ready 才能本地救援；
- 直连模式失败不回本地；
- 无本地账号不能伪装成本地错误；
- 不出现本地 → 外部 → 本地 → 外部回环。

### 12.6 第四组：双实例、排队和旁路故障

覆盖：

- 两实例同时竞争同一外部池容量；
- 一个实例写入冷却，另一个实例继续请求；
- 两实例同时清除冷却；
- 本地排队和外部排队同时出现；
- usage writer 延迟、Dashboard 查询慢；
- PostgreSQL 慢查询；
- Redis 短断和恢复；
- 服务重启后继续流量。

验收重点：

- 不超卖并发容量；
- 权威冷却最终在两个实例生效；
- 清除冷却后状态最终收敛；
- 旁路故障不影响主请求；
- 队列和租约在停止流量后释放。

### 12.7 第五组：15–30 分钟持续运行

至少运行三种工作负载：

1. 健康基线；
2. 低比例随机 429/5xx/网络错误；
3. 故障波、恢复和 usage/Dashboard 延迟同时存在。

必须记录：

- 下游请求数；
- 请求 API Key 准入数；
- 本地账号选择次数；
- 本地真实发送数；
- 外部真实发送数；
- 同账号/同池重试数；
- 换账号/换池次数；
- fallback/rescue 次数；
- 最终错误按类别分布；
- 首语义字节和总延迟的 p50/p95/p99；
- 冷却进入、持续和恢复时间；
- 每个账号/池的成功率、错误率和流量占比；
- Redis/PostgreSQL 延迟；
- RSS、文件描述符、连接数和队列深度。

### 12.8 usage 独立性与调度交叉验证

这组验证必须把“调度是否正确”和“最终 usage 是否按配置计算”拆成两个断言集合。

固定同一份请求体、同一份 usage 配置，并让假本地上游和假外部上游返回完全相同的真实 usage，分别执行：

1. 本地直接成功；
2. 外部直连成功；
3. 本地第一次失败后切换外部成功；
4. 外部第一次失败后换外部池成功；
5. 本地到外部失败，再本地救援成功；
6. 先发生一次同池重试，再成功；
7. 高并发下多个失败尝试后成功；
8. 同一请求最终失败，没有成功 usage。

必须同时验证：

- 调度诊断中的尝试次数、候选排除、路线和错误阶段正确；
- 最终成功请求的下游标准 usage 与无重试基线一致；
- 失败尝试的输入/输出 token 不被累加到最终成功 usage；
- 上游有真实 usage 时，“是否为估算”保持为否，原始 usage 取真实上游值；
- 上游没有 usage 时，才使用同一套本地估算 fallback，不因调度尝试次数增加而放大；
- usage 配置关闭/开启、缓存整形、最终上限和原始成本计算结果与调度路线无关；
- 最终失败请求不把请求估算错误写入正常成功 usage 字段，诊断估算必须留在诊断区域；
- usage writer、Dashboard 汇总或统计失败时，调度结果和最终 usage 计算不改变。

这组测试的核心判定是：

```text
相同请求 + 相同最终上游 usage + 相同 usage 配置
  => 不同调度路线只能改变调度诊断字段
  => 不能改变最终 usage、整形结果和原始计费来源
```

## 13. 不通过条件

出现以下任一情况，就不能进入发版：

- 有健康可调度账号/池却返回容量不可用；
- 外部直连出现本地真实发送；
- 优先级 1 的持续故障池长期垄断，健康备用池没有实际流量；
- 同一请求反复命中已经排除的账号/池；
- 实际发送次数超过总预算；
- 流式已经提交语义字节后重放完整请求；
- Redis/PostgreSQL/usage/Dashboard 延迟明显阻塞主请求；
- 故障波后无法恢复；
- 停止流量后 RSS、文件描述符、连接或队列不回落；
- 在任何并发档位下，真实发送放大倍数超过预算、重试风暴使队列持续增长，或小并发恢复请求仍被高并发故障波拖住；
- 相同请求和相同最终上游 usage 因调度路线不同而产生不同的最终 usage，或失败尝试 token 被累加到成功 usage；
- usage 配置未改变但调度重试、换池、冷却或排队改变了最终 usage 整形、原始成本来源或下游标准字段；
- 测试留下临时服务、端口、租约或后台进程。

## 14. 需要用户确认的产品决定

下面这些是实现前必须确认的产品参数，不应由代码作者自行猜测：

1. 是否接受“健康的优先级 10/20 外部池可以在优先级 1 池连续失败时溢出承接流量”？
2. 是否接受“连续失败窗口 + 临时不可调度 + 恢复观察窗口”作为默认机制？
3. “外部池最多尝试”为 `0` 时，是否继续表示“按候选池自动尝试一轮”？
4. 外部池普通 5xx/网络错误的默认策略，是否采用“同池最多 1 次、然后换池，单池短冷却”？
5. 外部池认证/额度/渠道禁用是否默认进入更长冷却或自动禁用，而不是反复重试？
6. WebSearch/MCP 辅助失败是否只重试辅助调用，不把整个请求隐式切到另一条路线？
7. 是否要求在 usage 明细中增加独立的“调度诊断附属区域”，用于记录配置版本/规则命中摘要/候选排除原因/统一尝试账本，但明确不参与最终 usage 计算？
8. 是否接受所有队列和重试共享一个请求总截止时间？
