## 1. 验证原则

这不是单次请求 smoke test。验证必须观察一段时间内的：

- 路由选择分布；
- 实际上游发送次数；
- 闭环并发、开环到达率、突增倍数和故障波下的并发峰值；
- 同账号/同池重试次数；
- 冷却、临时不可调度和恢复时间；
- 队列等待、总 deadline 和最终错误；
- 多实例 Redis 租约与快照传播；
- usage/统计旁路变慢时的主业务表现；
- 调度诊断与最终 usage 计算是否保持独立；
- RSS、文件描述符、连接数和队列在流量停止后的回落。

不得把现网 `9022` 作为负载目标。所有运行使用临时端口、隔离 PostgreSQL 数据库、隔离 Redis DB/前缀、临时 fake upstream 和冻结候选二进制。测试结束必须停止所有自有进程并清理临时资源。

## 2. 测试拓扑

```text
load generator(s)
        |
        v
  kiro.rs instance A ----\
                           +---- isolated PostgreSQL
  kiro.rs instance B ----/      isolated Redis scheduler
        |
        +---- fake local upstream
        +---- fake external pool A (优先级 1)
        +---- fake external pool B (优先级 10)
        +---- fake external pool C (优先级 20)
```

fake upstream 必须能够按请求序号或测试控制端点返回：

- 200 stream / non-stream；
- 429 + `Retry-After`；
- 408、500、502、503；
- 网络断开、连接超时、首字慢、长流；
- `anthropic-version` 缺失协议错误；
- 认证/配额/渠道禁用；
- 模型不支持；
- 输入过长；
- 流式首语义字节前失败；
- 首语义字节后失败。

每个 fake upstream 记录脱敏的：

- 请求次数和顺序；
- 请求模型、实际发送模型；
- 是否收到 `anthropic-version`；
- 请求是否 stream；
- 请求是否已经发送语义响应；
- 成功响应中的真实 usage 字段，以及是否触发本地估算 fallback；
- 响应状态和延迟。

## 3. 分层执行顺序

### L0：静态与合同检查

先执行：

- 文档链接检查；
- `cargo fmt --check`；
- 相关 source-contract / Node contract；
- 配置字段默认值和边界检查；
- `git diff --check`。

L0 失败时不启动服务。

### L1：单进程、单池确定性矩阵

每个 case 至少重复 5 轮，每轮包含 stream 和 non-stream：

1. 只有本地账号且容量足够。
2. 本地优先 + 外部池启用 + 本地 Ready。
3. 外部直连 + 外部成功。
4. 外部直连 + 外部 429/5xx/网络错误，确认本地发送数为 0。
5. 本地一个账号 429/5xx/网络错误，确认同请求换本地账号。
6. 本地全部冷却、全部禁用、无账号、模型不支持、Redis degraded。
7. 本地 fallback 到外部，外部成功。
8. 本地 fallback 到外部，外部失败后本地恢复 Ready，最多一次 rescue。
9. 外部失败但本地仍不可调度，不回本地。
10. Raw 透传和标准处理分别验证模型映射、正文模式和请求头。

验收：

- 每个 case 的本地/外部真实发送计数符合路线契约；
- 同一请求不重打已排除账号/池；
- stream 首语义字节后不重放；
- 调度诊断轨迹与 fake upstream 记录一致；
- 在假上游返回相同真实 usage 时，不同调度路线的最终 usage 按相同 usage 配置得到相同结果。

### L2：多账号、多池和容量竞争

配置：

- 本地账号至少 6 个，包含不同“账号最大并发”“账号 RPM”“账号错误冷却”；
- 外部池 A/B/C 优先级 `1/10/20`；
- A 偶发 5xx，B 健康，C 429；
- sticky 会话至少 20 个；
- 并发 20–50，连续 5–10 分钟。

观察：

- A 失败期间 B 是否能承接；
- C 是否只对受影响模型冷却；
- sticky 是否在冷却/容量满时逃逸；
- 低健康 A 恢复后是否重新接管过量流量；
- 真实上游发送数是否受“外部池最多尝试”和总预算限制。

L2 必须同时执行并发阶梯，而不能只跑固定并发：

```text
基线：1、5、10
小并发突增：1 -> 5 -> 20
中并发突增：5 -> 50
大并发突增：50 -> 500，或 0.25C_route -> 2C_route
超载保持：C_route -> 5C_route，保持 30–120 秒
```

每个并发档位都要分别使用：

- 闭环固定并发；
- 开环固定到达率；
- 下游客户端收到 429/5xx 后立即重试 2–3 次；
- 不自动降低到达率的过载流量。

额外验收：

- 队列峰值、任务数、连接数和租约数有硬上限；
- 重试不会随着并发线性或乘法放大；
- 高并发故障期间发起的低并发恢复请求不会长期被拖住；
- 小并发突增时不因短暂容量竞争误触发全局 fallback；
- 大并发超载时必须按准入/队列/路线策略明确拒绝或切换，不能无限堆积。

### L3：故障波与恢复

对同一配置按时间段切换：

```text
0–60s   全部健康
60–120s 池 A 连续 5xx / 网络错误
120–180s 池 A 恢复，池 B 429
180–240s 本地账号部分冷却
240–300s Redis scheduler 延迟或短暂断连
300–360s 全部恢复
```

每个阶段保持连续请求，不重启服务，不清空运行态。

L3 至少重复以下并发/错误组合：

| 组合 | 并发变化 | 故障变化 |
| --- | --- | --- |
| C01 | `1 -> 20` | 优先级 1 池 100% 5xx |
| C02 | `10 -> 100` | 优先级 1 池 50% 5xx，其他池健康 |
| C03 | `50 -> 500` | 优先级 1 池 100% 网络断开，B 返回 429 |
| C04 | 保持 `2C_route` | A 恢复、B 继续限流、本地部分冷却 |
| C05 | 高并发降到 `1` | 所有池恢复，检查恢复和资源回落 |

必须记录每个时间片的到达请求数、实际发送数、重试数、候选切换数、队列深度和冷却状态，不能只记录最终错误比例。

验收：

- 故障池进入临时不可调度，其他健康候选有流量；
- 故障解除后在合理窗口恢复，不出现永久饿死；
- 错误波不会导致本地/外部发送次数乘法放大；
- 高并发故障期间的小并发恢复请求不会长期被残留队列或冷却阻塞；
- 队列、连接、RSS、FD 在恢复阶段回落。

### L4：双实例、租约和冷却竞态

启动两个隔离实例，共享同一 PostgreSQL 和 Redis 调度命名空间：

1. 两实例同时抢同一个外部池租约；
2. A 写入冷却，B 在 100–500ms 内继续选择；
3. A/B 同时清除冷却；
4. 一个实例 Redis 延迟，另一个实例正常；
5. 一个实例重启，另一个实例持续承载请求；
6. 本地和外部池同时容量竞争。

验收：

- 不超卖“账号最大并发”和外部池容量；
- 权威冷却生效后不继续回打坏池；
- Redis degraded 不造成无限等待或错误 fallback 回环；
- 实例退出后租约和队列最终释放。

### L5：15–30 分钟 soak

至少运行三组：

1. 健康基线；
2. 低比例随机 429/5xx/网络错误；
3. 故障波 + 恢复 + 旁路 usage/dashboard 延迟。

推荐并发从 1、10、25、50 分档，再加入 `0.5C_route`、`C_route` 和 `2C_route`
三个相对容量档；每档至少 5 分钟，再进入 15–30 分钟持续运行。至少有一轮在高并发错误波
结束后降回并发 1，验证低并发恢复请求不被残留队列或冷却状态阻塞。

## 4. 必采指标

每个请求和每个阶段都要采集：

- 下游接收请求数；
- 请求 API Key 准入数/拒绝数；
- 本地账号选择尝试数；
- 本地实际上游发送数；
- 外部池实际上游发送数；
- 下游到达率、并发峰值、开环目标到达率与实际到达率；
- 同账号/同池重试数；
- 跨账号/跨池切换数；
- fallback/rescue 次数；
- 真实发送放大倍数 `实际发送数 / 下游接收请求数`；
- 429、4xx、5xx、网络、协议、容量、队列超时数量；
- p50/p95/p99 首语义字节时间；
- p50/p95/p99 总延迟；
- 冷却进入次数、平均/最大持续时间、恢复时间；
- 每个账号/池的成功率、错误率、发送占比；
- Redis/PgSQL round-trip 延迟；
- RSS、文件描述符、连接池占用和队列深度。
- 最终 usage 的真实上游 usage、估算标记、整形结果和下游标准字段；
- 调度诊断中的尝试次数与最终 usage 是否互相独立。

如果实现尚未提供统一“尝试账本”，测试脚本必须从 fake upstream 请求日志和独立调度诊断记录交叉计算，并把“无法直接观测”标成缺口，而不是猜测。最终 usage 只用于单独验证 usage 配置、真实上游 usage 和本地估算 fallback，不作为调度发送次数的推导来源。

## 5. 失败判定

任一条件出现即判定该层不通过：

- 存在可调度账号/池却返回容量不可用；
- 外部直连产生本地发送；
- 低健康池持续垄断流量且健康备用池长期无流量；
- 同一请求反复命中已排除账号/池；
- 总实际发送次数超过预算；
- stream 已提交语义字节后重放；
- Redis/PgSQL/usage/dashboard 慢导致主请求明显阻塞；
- 故障波后无法恢复或恢复期间错误持续放大；
- 高并发故障波下真实发送放大倍数超过总预算，或小并发恢复请求仍被高并发残留队列拖住；
- 相同请求、相同最终上游 usage 和相同 usage 配置因为调度路线不同而产生不同最终 usage；
- RSS/FD/连接数在停止流量后不回落；
- 自有测试进程、端口、队列或租约未清理。

## 6. 证据与状态更新

每轮验证至少保留一份脱敏摘要，包含：

- 代码提交和冻结二进制哈希；
- 配置摘要（不含密钥）；
- 场景、持续时间、并发和故障时间线；
- 指标摘要；
- 失败请求 ID 和 fake upstream 证据索引；
- 资源采样；
- 清理结果。

验证完成后必须同步：

1. 对应 `feature/issues/*.md`；
2. `feature/issues/current-issue-status-index-20260731.md`；
3. `docs/plantree/plans/rust-runtime-scheduler-stabilization/roadmap.md`；
4. `implementation-status.md`；
5. `history/evidence-index.md` 或新的 `feature/evidence/*.md`。

在完整 L1–L5 通过前，不能把目标矩阵标为“已修复”，也不能发版。
