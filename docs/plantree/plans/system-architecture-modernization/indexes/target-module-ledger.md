## Ledger Rules

1. A `MOD-*` ID identifies one technical authority boundary, not a person, file, directory, trait, task, or product phase.
2. Every target production path belongs to exactly one module ID. Shared protocol and kernel paths use their own IDs rather than being anonymously imported by every module.
3. A legacy file can contain responsibilities mapped to several target modules. Exact symbol/responsibility mapping is the first implementation task for each affected module and every symbol resolves to one technical authority.
4. `Dependency group` is construction order inside one implementation program. It is not a separate release, production activation, acceptance phase, or personnel assignment.
5. Allowed dependencies name public contracts only. They do not permit importing another module's private domain, adapters, persistence records, workers, queues, or state handles.
6. `Not Started`, `Implementing`, `Integrated`, and `Verified In Candidate` are development states. None means independently released or production-authoritative.
7. A module reaches `Verified In Candidate` only after focused gates, target integration, legacy-symbol deletion, and post-deletion checks pass. Final `Complete` is reserved for the whole system after decision 009 completion criteria pass.
8. Target runtime code cannot import a legacy implementation. Test-only characterization adapters and fakes are excluded from release features and deleted before the final candidate freezes.

## Dependency Vocabulary

- `KERNEL` means only `MOD-KERNEL` primitives.
- `PROTO-*` means the named protocol module's public wire/codec contract.
- `PUBLIC(MOD-X)` means only that module's public application/query/event contract.
- `OWNED-PORTS` means ports declared and owned by the same module.
- `OBS` means bounded typed observability events through `MOD-OBSERVABILITY`.
- Bootstrap may construct concrete implementations. This exception does not authorize business decisions in bootstrap.
