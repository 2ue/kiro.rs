## Scope And Interpretation

This document separates three kinds of fact:

1. **Hard implementation bounds** reject, evict, time out, or cap work in the current code.
2. **Defaults** apply only when configuration does not override them; a default of `0` can mean unbounded.
3. **Dated observations** describe one measured workload and are not current SLOs, guarantees, or maximum capacity.

The product is single-user and single-operator. Concurrency is generated by that operator's clients, Claude Code subagents/tools, retries, replicas, and background work. It is not per-user concurrency and has no tenant quota dimension.

## Dated Production Observation

The following evidence was captured on 2026-07-06 and analyzed in `docs/analysis/prod-slow-first-token-root-cause-20260706.md`. It is retained to describe a real workload shape, not to promise that every deployment or revision sustains it.

| Observation | Recorded value |
| --- | ---: |
| Successful streams in one hour | `3438+` |
| Time to first byte, p50 | `11.45s` |
| Time to first byte, p95 | `63.2s` |
| Requests with first byte later than 30 seconds | `578` |
| In-flight requests, approximate p95 | `50` |
| In-flight requests, observed peak | `55` |
| One high-volume minute | about `73` successful streams |
| Reported tokens in that minute | about `31.7M` |
| Payload-guard latency for payloads at least 1 MiB, p95 | about `108ms` |
| Largest observed request class | exceeded `20 MiB` |

Heavy requests commonly contained tens of tool definitions and hundreds of thousands of input or cache tokens. The dominant slow interval was usually upstream connection/header wait or header-to-first-chunk wait. Local SSE conversion was not the main contributor in that observation.

Consequences for interpreting tests:

- a 30- or 60-second first byte is a real operating condition, not automatically a dead request;
- total execution beyond 180 seconds is plausible when upstream behavior and configured timeouts permit it;
- a fast mock alone does not exercise retained-request memory, lease lifetime, slow-client backpressure, keepalive, or shutdown behavior;
- the observation proves neither a safe maximum nor a current regression gate.

Evidence: `docs/analysis/prod-slow-first-token-root-cause-20260706.md:7-19,88-203`.

As of the 2026-07-16 dirty-tree containment fix, remote sources are still fetched serially and materialized base64 remains in the request, but source count, aggregate download/base64, HTTP attempts, workflow time and concurrent workflows are bounded. The transport resolver filters the addresses used for each actual connection and the materialization client does not inherit system proxies. Final release-candidate handler/load/RSS evidence remains open in [the active issue](../../../feature/issues/remote-multimodal-resource-and-ssrf-bounds.md).

Base64 expands binary input by approximately one third before JSON/string overhead. A file or remote object can coexist temporarily as stored/downloaded bytes, an encoded string, parsed JSON, a rewritten request, and an upstream envelope. Therefore the 50 MiB HTTP limit and 256 MiB Files-store limit are not process memory ceilings.

| Usage writer batch size | 64 records | Coalesces input, but PgSQL persistence still performs multiple per-record/upsert operations |

## Configured Concurrency Semantics

The current local scheduler supports both request-count capacity and weighted capacity. However, the default local/global concurrency and queue-limiting values are `0`, meaning disabled/unbounded for those controls. Weighted capacity tiers exist but weighted admission is disabled by default.

An operator can therefore run with explicit bounds, but an untouched configuration does not establish a finite process-wide request concurrency budget. The HTTP server, parsed request bodies, remote content, upstream requests, streams, and terminal work can grow with offered concurrency until some downstream pool, queue, OS, allocator, or dependency becomes the effective limit.

External pools have their own concurrency, queue, priority, cooldown, and timeout configuration. Their limits do not create a global bound covering local work, request preprocessing, Files, remote downloads, background storage, and all external pools together.

Evidence: `src/kiro/token_manager/capacity.rs:16-67,118-160`, `src/model/config.rs:3050-3110,3625-3690`, `src/external_pool.rs:2124-2207`.

## Local Credential Scheduling

The local scheduler is stateful and coordinates process-local and Redis-backed facts. Current selection follows this functional sequence:

1. filter credentials by enabled state, endpoint/proxy viability, and resolved-model support;
2. exclude credentials already failed by the current request attempt loop;
3. apply cooldown, probation, RPM, request-count concurrency, and optional weighted-capacity eligibility;
4. prefer a valid sticky-session binding when possible;
5. otherwise score/select by configured priority, balanced, or health/pressure behavior;
6. acquire local and, where configured, Redis in-flight capacity;
7. wait on scheduler wakeups up to the dispatch deadline when capacity is temporarily unavailable;
8. refresh or prepare authentication and execute the upstream attempt;
9. on retryable failure, update cooldown/health state and retry with the failed credential excluded;
10. on success, error, timeout, cancellation, or client drop, release the completion guard/lease and update runtime state.

Sticky selection improves conversational affinity but is not an ownership boundary. A binding can fall back after soft failures, expiry, disablement, model incompatibility, or capacity pressure.

The implementation uses broad shared credential vectors and state maps. Selection scans these structures and coordinates scheduling decisions with Redis/PgSQL/refresh work through `MultiTokenManager`; pure selection and I/O ownership are not isolated into separate runtime components.

Evidence: `src/kiro/token_manager/strategy.rs:33-59,147-300`, `src/kiro/token_manager/manager.rs:3414-3603`, `src/kiro/token_manager/sticky.rs`, `src/kiro/token_manager/capacity.rs`.

## External Pool Scheduling

External pools are filtered by enabled/auto-disable state, route role, model support, body compatibility, cooldown, and capacity. Eligible pools are ordered by priority and then by normalized current load. Local and Redis-backed leases coordinate capacity across replicas, and a bounded dispatch queue can wait for release notifications.

On retryable external failure, the manager records cooldown/auto-disable evidence and can try another eligible pool or return to the configured local/external rescue path. Lease ownership is guarded so stream completion, explicit failure, timeout, and response drop can release capacity.

External scheduling does not eliminate duplicate-execution risk when an upstream accepted work but the gateway lost the response before determining whether execution occurred. Retry policy classifies transport/status errors, but no universal idempotency key makes all model execution retries cost-free.

Evidence: `src/external_pool.rs:2124-2207,3329-3377`, `src/external_pool/retry_pipeline.rs`.

## Current High-Cost And Blocking Paths

The following are confirmed implementation properties relevant to memory, latency, and event-loop health:

- remote image/document sources are fetched serially, accumulated, base64-encoded, and retained without an aggregate request or process-wide download budget;
- DNS/IP safety is checked before the reqwest connection, but the validated resolution is not pinned to the actual connection, leaving a DNS-rebinding/time-of-check gap;
- PDF parsing runs synchronously in the async request flow and uses one global standard `Mutex` around parser work;
- remote token counting uses `block_in_place`, clones the payload, constructs a client per call, and allows a 300-second client timeout;
- Files content response clones the stored byte container for response construction, while file-to-request materialization creates a separate base64 allocation;
- the default diagnostic path captures bounded request-body samples but retains an unbounded set of rolled files;
- scheduler selection scans shared credential collections and combines decision, mutable coordination, refresh, and persistence concerns;
- normal success, runtime mutation, usage saturation fallback, and lease release can synchronously touch PgSQL or Redis;
- usage batches reduce channel overhead but still issue multiple SQL inserts/upserts per record or rollup class;
- no benchmark or performance-regression gate currently blocks a release.

Evidence: `src/anthropic/body_processing.rs:139-160,255-279,300-429`, `src/anthropic/converter/content.rs:263-328`, `src/token.rs:107-185`, `src/anthropic/files.rs:255-341`, `src/anthropic/tool_format_debug.rs:369-493`, `src/anthropic/usage.rs:1398-1483`, `src/kiro/token_manager/manager.rs:3414-3603`.

## Test And Capacity Interpretation

A valid resource test needs separate profiles because one aggregate requests-per-second number hides the dominant risks:

| Profile | What the current system must be observed for |
| --- | --- |
| Fast upstream burst | scheduler contention, queue admission, response conversion, storage pressure |
| 30/60+ second first byte | retained request memory, leases, keepalive, disconnect cleanup |
| 180+ second execution | idle versus total timeout semantics, shutdown and stale-lease behavior |
| Large tools/schema body | parse/copy/payload-guard CPU and peak RSS |
| Many remote sources | aggregate bytes, SSRF behavior, download concurrency, base64 expansion |
| PDF and tokenizer load | blocking-pool/event-loop delay and memory copies |
| Upstream mass failure | retry amplification, cooldown convergence, queue wakeups, duplicate-cost risk |
| Slow downstream client | SSE backpressure, buffer limits, lease release on disconnect |
| PgSQL/Redis latency or outage | request-path fallback, queue saturation, readiness, state convergence |
| Restart during load | accepted-work drain, abandoned writes, lease recovery, process-local state loss |

This table explains coverage dimensions only. It does not assert that the current implementation passes a threshold that has not been measured and versioned.

## 未实现要求

The following required outcomes are not current baseline behavior. Detailed target budgets, authorities, measurements and gates belong to the [Greenfield AI Gateway plan](../plans/greenfield-ai-gateway/README.md):

- define finite whole-request and process-wide budgets for remote-source count, downloaded bytes, materialized bytes, download concurrency, PDF work, and tokenizer work;
- make PDF parsing and remote tokenization asynchronous or isolated behind explicitly bounded blocking workers, queues, cancellation, and time budgets;
- ship production defaults with explicit global/local concurrency, queue, weighted-capacity, and overload-shedding budgets instead of unbounded `0` settings;
- bound diagnostics and normal logs by directory bytes, file count, age, permissions, redaction, and cleanup ownership;
- remove synchronous PgSQL/Redis work from latency-sensitive completion paths or give it an explicit durable/replayable contract;
- guarantee lease, memory, queue-slot, file-descriptor, and background-task recovery for success, error, timeout, cancellation, disconnect, retry, and shutdown;
- add repeatable performance and resource-regression gates covering fast, slow, large-body, sudden-concurrency, mass-failure, dependency-failure, and restart profiles without exhausting the developer machine;
- record peak RSS, allocator behavior, open file descriptors, task/connection counts, queue age/depth, event-loop delay, and filesystem residue as first-class test evidence.
