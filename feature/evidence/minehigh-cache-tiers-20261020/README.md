# minehigh 缓存策略档位测试（2026-10-20）

Role: 为新路由 `/dfcache/minehigh` 选择缓存策略档位，记录各档配置、真实账号多样化测试结果和结论

Status: `local-validated / 2026-10-20 已写入现网 59137 与 sub2api`

## 结论

推荐 minehigh 使用 **mh-c10**（[configs/mh-c10.json](configs/mh-c10.json)）：

- sub2api 口径汇总命中率 **94.3%**，单请求命中率 p10 为 91.2%（不含冷请求）；
- 积分转换率 **$0.262/积分**，落在 0.25 左右；
- 计费比 1.14，下发计费高于原始计费，不亏损；
- input 全部压在上限内：最大 3292，p90 2564。

其他选择：

- 要转换率尽量高：**mh-c15**，$0.413/积分，命中率 95.6%，计费比 1.69。
- 要中性档位：**mh-c08**，$0.244/积分，命中率 93.4%，计费比 1.00。
- 0.2 以下的档位：mh-c00 / mh-c03 / mh-c05，$0.19~0.20/积分。这三档计费比都低于 1，相对原始计费是亏的，不推荐。
- 照搬线上 `/ha`（ha-clone）：汇总命中率只有 83.4%，单请求 p10 只有 50.9%，**达不到 90% 以上的要求**。

口径：

- 汇总命中率 = Σcache_read ÷ Σ(input + cache_read + cache_creation)，和 sub2api `TokenUsageTrend.vue` 的公式一致，包含冷请求。
- 单请求命中分位数只统计有读取的请求。冷请求是每条对话的首轮，没有可复用前缀，读取为 0。
- 积分转换率 = 下发 usage 的估算费用（美元）÷ Kiro 实际消耗积分（meteringEvent），和管理后台概览页的"积分转换率"口径一致。
- 原始转换率 = 原始 usage 的费用 ÷ 积分；计费比 = 估算费用 ÷ 原始费用。

## 策略配置

每个档位的完整路由配置在 [configs/](configs/) 目录，测试实例写入的 runtime 片段在 [configs/runtime-config-snippet.json](configs/runtime-config-snippet.json)。

所有 mh 档位共用的参数：

- 策略 `bounded_high_cache`，路由独立缓存空间（`routeNamespace: true`），只走本地账号、不进外部池。
- 模拟：`tokenScale 2.05`、`targetReadRatio 0.98`、`maxSimulatedInputTokens 300000`。
- 写入频次控制：单次写入上限 30000，300 秒窗口上限 120000，最小写入间隔 6 秒。
- input：`sample-max`，上限 3300。最终上限再向下浮动最多 15%，所以 input 始终 ≤ 3300，只压在上限内，不保证集中在 3k 附近。
- output：超过 2000 放大 70%（`outputUpliftMinTokens 2000`，`outputUpliftPercent 70`）。
- 命中率整形：目标 0.90、浮动 0.05，最小写入比例 0，读写最小值 1024。

各档只有两项不同：`hitShaping.minCostRatio`（计费下限）和 `hitShaping.maxReadMultiplier`（读取上限倍数），对应上表第二列。

## 测试方法

- 版本：本地 `main` 的 `0.0.201`（`c89217a`）release 构建，独立测试库 `kiro_minehigh_20261020` 和 Redis 前缀 `kiro_rs:minehigh_20261020`，端口 19191。
- 账号：导入项目根目录账号文件 235 个，成功 233 个（2 个 refresh 返回 40x）。额度全部为 KIRO FREE，每个剩余 36~50 积分。模型探测结果为 social / idc 可用 claude-sonnet-4.5、claude-haiku-4.5 等；15 个 api_key 账号拉模型失败，已禁用。
- 驱动脚本：[scripts/drive_diverse.py](scripts/drive_diverse.py)。每个档位每轮 10 条对话，两轮共 140 条对话：
  - 话题从 20 类中选取（Rust、TS、SQL、Python、运维、算法、写作、数据、安全），首问附仓库里随机截取的真实代码；
  - 每条对话 8~16 轮追问，追问从通用和分话题追问池随机选取，30% 附加新的代码片段；
  - 系统提示词分无 / 小 / 中 / 大四档；45% 带工具定义，模型调用工具时用真实文件内容回填 tool_result；
  - 模型 sonnet-4.5 1210 次、haiku-4.5 442 次；流式 1345 次、非流式 307 次；轮间随机间隔 1.5~9 秒，并发 14。
- 统计脚本：[scripts/analyze.py](scripts/analyze.py)，直接查询测试库的 `usage_records`，只统计成功请求。

## 已知限制

- **请求失败**：共发送 1652 次请求，成功 1359 次。第二轮有 290 次 429，其中 206 次是本地准入退避（`admission_local_temporary_backoff`），84 次是本地调度暂时没有可用账号（单账号 RPM 100）；上游没有返回 429。另有 3 次上游 502。失败请求不计入统计，每档成功请求仍有 185~220 次。
- **模型覆盖**：免费账号只能用 sonnet-4.5 和 haiku-4.5。现网主要跑 opus 系列，积分消耗和单价都不同，上线后需要按真实流量复核转换率。
- **output 分布**：output 放大门槛设在 2000，所以下发的 output 不会落在 (2000, 3400] 区间，两轮数据中这一区间的计数为 0。
- **input 分布**：input 采样约 70% 落在上限的 2%~25%，中位数约 0.8k，p90 约 2.2k~2.9k，最大值不超过 3300。
- **原始数据**：测试结束后已按资源约定删除测试库、Redis 前缀和逐请求 JSONL。本文数据来自删除前对测试库的查询，脚本已保存，可以重跑复现。
- **积分消耗**：两轮共消耗 531 积分，账号池总额度约 1.1 万。
