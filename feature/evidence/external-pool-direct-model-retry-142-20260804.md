## 根因确认

### 1. 不是外部直连错误地回到了本地凭证

当前“外部直连策略”开启时，外部池最终错误不会走本地救援。142 的
`yuenan` 502 记录也显示本地尝试为 0。现场出现的本地错误主要来自
`/dfcache/onlylocal`，该入口被“外部池路由模式/外部池路由规则”明确排除，
只能走本地凭证。

### 2. `yuenan` 失败后没有选到后两个池，是当前实现把“请求正文模式”放进候选筛选

外部池选取先按“请求正文模式”过滤，再按可用性、冷却、容量和优先级选池：

- Raw 透传请求只会选择 Raw 透传池；
- 标准处理请求只会选择标准处理池。

因此当前配置下，`yuenan` 是唯一 Raw 透传池。它返回 502 后，本次请求会排除
`yuenan`，但 `kkkkyue` 和 `jinnyapi` 因为是标准处理，不属于当前实现生成的
同一候选集合，最终形成“外部池不可用”。这不是“优先级 1 永久锁死 10/20”，而是
当前实现的候选集合先被正文模式裁掉：

```text
请求正文模式过滤
  -> Raw 候选只有 yuenan
  -> yuenan 502 后排除当前池
  -> 没有同模式后备池
  -> external_pool_unavailable
```

这只解释现场，不代表目标产品语义。用户已确认目标语义是：外部池先按路由配置、
启用状态、优先级/容量/冷却和模型支持选池；Raw 透传或标准处理是选中池之后的
请求体处理方式，不应作为选池前置条件。后续修复应围绕“选池与 body 处理解耦”
设计，而不是要求同一个 Raw 请求必须只有 Raw 池后备。

### 3. 优先级 1、10、20 是严格优先级，不是权重分流

数字越小越优先；只有更高优先级池不可用、被排除、冷却或容量不足时才会
考虑下一优先级。`jinnyapi` 在窗口内 0 次尝试与此语义一致：标准处理候选中
`kkkkyue` 可用并成功，所以不会继续选优先级 20。

### 4. 502 已进入重试逻辑，但“重试次数”受候选池数量约束

服务器错误会被标记为可重试并写入池级冷却；请求内排除当前池后继续选下一个。
“外部池最大重试次数=3”不是强制发送三次，也不会凭空把不符合“请求正文模式”
的池加入候选。当前 Raw 候选只有一个，所以实际只发生一次外部尝试。

### 5. 模型映射在 `yuenan` 已经真实回写；其他池的配置并不相同

142 数据库中 `yuenan` 包含用户列出的带日期映射，并且 Raw 顶层模型重写已经
在“外部尝试”的“模型（上游）”中生效。

`kkkkyue` 和 `jinnyapi` 实际缺少：

- `claude-haiku-4-5-20251001`
- `claude-opus-4-5-20251101`
- `claude-sonnet-4-5-20250929`

两池“必须命中映射”均关闭，因此映射未命中时按“透传优先映射”的定义保留
原模型。页面出现带日期模型不是本地别名解析异常，而是该池没有对应映射时的
预期透传。

### 6. “模型（本地解析）”与外部池“模型（上游）”是不同阶段

- 模型（请求）：客户端原始值；
- 模型（本地解析）：本地凭证兼容层的别名或规范化值；
- 模型（上游）：实际发给所选外部池的值；
- 模型解析说明：本地解析阶段的说明。

`claude-opus-4-7 -> claude-opus-4.7` 出现在仅本地入口时，只能说明本地解析层
选择了别名，不代表外部池会使用该别名。Raw 外部池优先使用原始模型做池级映射，
命中后回写到实际请求体。

### 7. 入口路径不是本次调度差异的根因

`/v1`、`/cc`、`/ha`、`/na` 和 `/dfcache/*` 的运行时外部池准入均通过
“外部池开关”“外部池路由模式”“外部池路由规则”判断；本次现场中多个入口
都出现同样的 `external_direct_policy`，说明差异来自“请求正文模式”和池配置，
不是针对某一个内置路径写死了重试策略。

代码中保留的内置路径判断属于 Axum 路由注册、默认配置和测试 fixture；它们定义
入口存在，不定义外部池的直连、fallback、模型映射或冷却策略。策略仍由请求
入口解析出的运行配置决定。

## 修复方向

本证据文件只记录生产只读事实，没有直接修改运行时逻辑。后续修复方向如下：

1. P0：将外部池候选选择与“请求正文模式”解耦。Raw 入口选中标准处理池时，
   需要从已保留的原始 body 延迟解析出 `MessagesRequest`，然后走标准处理、
   payload guard、模型映射、usage/cache 和流式兼容链路。
2. P0：外部池运行时请求在客户端未提供时默认补
   `anthropic-version: 2023-06-01`，与 `../sub2api` 的 Anthropic API Key
   兼容行为对齐。
3. P1：若希望持续失败的高优先级池自动退出，应增加失败阈值、窗口、池级/模型级
   冷却和手动恢复，而不是把 10 秒冷却误当成自动禁用。
4. P1：参考 `../sub2api` 的账号池模式，增加可配置重试次数、可重试状态码/错误类、
   同池账号重试或跨池重试策略。默认只覆盖首输出前的 429、网络错误、超时和 5xx；
   普通 400 不默认重试。
5. P2：若希望三个池共同分流，应使用相同优先级或明确的权重策略；不能把
   `1/10/20` 当作均衡权重。
6. 应把三池的模型映射配置补齐作为配置修复；代码不应为缺失映射自动猜测目标。
7. 请求明细可增加“候选池筛选原因”，明确显示“请求正文模式不匹配”“冷却”
   “容量不足”“优先级未到”，减少把配置语义误判成 fallback bug。
