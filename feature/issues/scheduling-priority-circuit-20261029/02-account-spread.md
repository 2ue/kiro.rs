# 并发集中在少数账号；同会话并发；会话迁移与缓存

## 现象

现网约 64 个启用账号，总并发 30 多时只占用约 20 个账号，其余账号空闲。

## 同一会话会不会产生多个并发

会。

- 会话 id 取自请求体 `conversationState.conversationId`（`provider.rs:12259`），由 converter 生成（`converter.rs:324-397`）：优先用 `metadata.user_id` 里的 session；没有时，用 system、tools 和第一条 user 消息算哈希，派生出固定 UUID。都拿不到时随机生成，相当于没有粘性。
- 主对话、并行的 subagent 和 websearch 内部调用，只要带同一个 metadata session，就是同一个会话 id。Claude Code 的 subagent 是否都带同一个 session，需要抓包确认。
- 同一会话的请求先叠在绑定的账号上（并发 3 以内）。第 4 个并发时，只要还有可调度账号，就临时借号（`manager.rs:7019-7031`，标记 `fallbackFromSticky`），不改绑（7289-7306）。
- 没有"单账号绑定会话数上限"，也没有按负载调整的绑定。

## 原因（按可能性排序）

1. **占用的账号数约等于活跃会话数。** 绑定不看负载，没有上限，6 小时滑动续期，一个会话的请求都留在绑定的账号上。按现在的设计，活跃会话约 20 个时就会占约 20 个账号。
2. **优先级 10 的 20 个账号在优先级 0 没满时应当空着。** 这是优先级模式的预期行为。
3. **同档排序的平局键用的是终身累计成功数。** `priority_selection_key`（`strategy.rs:289-301`）为 `(priority, 在途, 10s 选中, 60s 选中, success_count, total_selection_count, id)`。`success_count` 是终身值（manager.rs:11138 累加，9390 从 PG 取最大值）。空闲账号之间总是确定性地挑历史成功数最少的，老账号会一直闲着。成功数排在选中数前面，失败多的账号在平局时反而更容易被选中。
4. **模型目录筛选相当于隐藏一层优先级。** `prefer_catalog_listed`（5783-5790）：只要有一个可调度账号的目录里明确列出了该模型，目录为空的账号就全部出局。
5. 多实例快照滞后（Redis 状态约 1 秒同步一次）只会造成撞号和重选，不会让账号长期空闲。

每号并发上限是 3，20 个号可承载 60 并发，所以"30 并发占 20 号"在现有设计下不算异常。问题在目标：如果目标是把单号负载和风控暴露摊薄，现在的排序和绑定方式就不合适。

## 解决方案

已实现，提交和验收见 [07-implementation.md](07-implementation.md)。

- 同档排序改为依次比较：在途负载占比、近 10 分钟活跃绑定会话数、60 秒选中数、最久未被选中。去掉终身成功数。新会话会落到会话最少的账号上，各账号的会话数会逐步拉平。
- 同会话并发默认仍叠在一个账号上（对上游真实缓存最友好）。新增"单会话在单账号的最大并发"配置，默认等于账号上限（不改变现状），调成 1 或 2 会更分散。
- 模型目录：现网 497 个凭据都没有 `supportedModels`，目录优先从不生效，不是账号空闲的原因。发现流程只对 API Key 凭据运行，OAuth 凭据目录为空表示不限制。目录优先只是在有目录的账号可调度时把空目录账号排后，有目录的账号满了以后空目录账号照常接流量。

现网数据（2026-10-30 0:55，只读）：优先级 0 的 41 个账号绑定会话 293–1072 个，近 1 小时请求 130–362 个，没有空闲账号；优先级 10 的 24 个账号有 23 个空闲。这与原因 1、2 一致：账号数随活跃会话数增长，低档在高档没满时空着。

## 会话迁移时缓存会不会丢

用户判断基本正确。本地模拟缓存的键是 `(conversation_id, route_namespace)`，不含账号（`prompt_cache.rs:28-32`），有测试覆盖"同会话跨账号命中"（`prompt_cache.rs:2380-2396`）。默认配置下，改绑后对外 usage 的 `cache_read_input_tokens` 和 `cache_creation_input_tokens` 保持连续。

需要补充：

1. 创建频次控制配成 `credential_conversation_model` 时，换号后 `cache_creation` 会再出现一次（`prompt_cache_creation_control.rs:364`）。默认的 `conversation_model` 不受影响。
2. 上游 metadata 带回非零缓存字段时直接透传（`handlers.rs:4427`）。上游真实缓存很可能按账号隔离（代码无法证实，`config.rs:1342` 的注释是作者的假设）。如果是这样，换号后上游第一轮不命中，真实成本会高一次，对外 usage 也可能跟着变。
3. 本地缓存只在进程内存里：重启就丢，多实例之间不共享。这与换号无关。
4. `promptCacheMaxEntriesPerAccount` 实际按会话计数（`prompt_cache.rs:246-270`），名字和注释已经过时。`handlers.rs:6230` 的注释也过时了。
