# 极端场景梳理与覆盖

两条底线：

- **A**：只要有账号的并发和 RPM 都没满（并且可用于该模型、路由，未禁用、未冷却，代理可用），请求就必须能调度到它。
- **B**：在非恶意流量下服务不能挂；负载退去后自动恢复，不需要重启。

梳理方式：4 路只读代码分析（有容量却不调度、服务挂掉或无法恢复、上游与客户端行为、本次改动审查），加上 mock 场景实测。

测试环境：10 个账号，每号并发 4，共 40 个槽；到达率按容量比例从现网 228 个槽折算；客户端连接上限 300；每个用例前后检查 TIME_WAIT。

## 场景清单与结果

"处理"一列写的是本分支的修复。"实测"一列写的是修复后 mock 的结果。

### 上游故障

| 场景 | 风险 | 处理 | 实测 |
| --- | --- | --- | --- |
| 全部账号 5xx 持续 30 秒 | 全池被冷却，恢复后仍不可用 | 成片故障不冷却（已有） | storm_5xx：故障期间返回 502，恢复后立即恢复，没有残留冷却 |
| 全部账号 429 持续 30 秒，带 Retry-After 1 | 冷却期间不调度 | 冷却按 Retry-After，1 秒 | storm_429：故障期间排队，恢复后槽位利用率 99% |
| 全部 429 且不带 Retry-After | 冷却 30 秒起翻倍，恢复后要空等 | 大部分账号已在冷却时，后续冷却封顶 5 秒，并写入 Redis | storm_429_noretry：修复前恢复阶段槽位利用率 61%，修复后 91% |
| 首字节前断流（reset） | 误判为账号问题 | – | storm_reset：返回 502，恢复后立即恢复 |
| 一半流中途断开 | – | 已输出则以 error 事件结束 | storm_midstream：中途断开的流以 error 事件结束，恢复后正常 |
| 过载叠加 30% 5xx | 错误放大 | – | spike_with_errors：没有停摆，租约归零 |
| 上游整体变慢 20–40 秒 | 槽被占满，排队超时 | – | slow_wave：槽位利用率 99%，排队正常推进，恢复后正常 |
| 三成账号变慢 | 慢账号拖累整体 | – | slow_accounts_spike：其余账号承接，槽位利用率 99% |
| 专属代理账号成片超时（现网 216 个账号都用代理资源） | 超时直接冷却，全池被冷掉 | 只有故障集中在少数账号时才冷却 | 单元测试 `dedicated_proxy_timeouts_shared_by_the_active_pool_are_not_concentrated` |
| 403 风控、402 额度同时出现在多个账号 | 账号被永久禁用，不会自动恢复 | 不改：属于策略问题，需要用户决定 | – |

### 运维事件

| 场景 | 风险 | 处理 | 实测 |
| --- | --- | --- | --- |
| 过载中发布（SIGTERM） | 修复前退出 26–34 秒被强杀，usage 丢失 | 排队请求立即返回；HTTP 排空时长可配置（`KIRO_RS_HTTP_DRAIN_SECS`，默认 5 秒），后台阶段 4 秒；Redis 恢复等待会响应停止 | 矩阵内所有用例退出 0.7–0.8 秒 |
| SIGKILL 后新实例接管 | 租约 30 秒、排队名额最长 120 秒才回收 | 不改：心跳回收已有；排队名额问题见下方遗留 | – |
| Redis 卡住不返回 | 豁免让 breaker 永远打不开 | 连续 20 次豁免且中间没有成功后，超时照常计数 | 单元测试 `excused_timeouts_stop_being_excused_without_any_success` |
| PG 或 Redis 半开 | `/readyz` 挂住，被误判为宕机 | readyz 依赖检查各限时 500ms | – |
| 自愈进行中、PG 变慢 | 每个请求在路由预检里 `block_in_place` 最长 30 秒，拖垮运行时 | 只有本地池全部不可用时才等；容量满时不等 | – |

## 本轮新增修复（在 05 的基础上）

| # | 改动 | 对应风险 |
| --- | --- | --- |
| G1 | tombstone 改为按时间排序的队列，只弹出过期项，不再每次释放都全表扫描；超过上限时只丢最旧的，不再整表清空 | B：大量释放时 O(n) 锁内扫描；清空后旧快照把已释放租约算回来 |
| G2 | 会话绑定修剪改为每 60 秒一次，或超过上限时才执行 | B：每个带会话的请求都在锁内遍历 1 万条 |
| G3 | 路由预检的自愈等待只在全部不可用时发生 | B：`block_in_place` 30 秒 |
| G4 | `/readyz` 依赖检查各限时 500ms | B |
| G5 | 成片故障判断只统计近期被调度过的账号；专属代理账号的超时和读失败只在故障集中时才冷却 | A：分档或专属代理时上游成片故障把全池冷掉 |
| G6 | Redis 判满标记只在"该账号已满"时设置；全局满、调度阻断、已释放租约不再误标 | A |
| G7 | 本实例的释放写入 Redis 后立即清除判满标记并唤醒等待者 | A：等待者原来只能等 1 秒兜底 |
| G8 | breaker 豁免加安全阀 | B：Redis 真故障时 breaker 永远打不开 |
| G9 | 配置代数改为进程级递增，请求配置缓存不会串用 | 正确性 |
| G10 | 释放分发器"只超时"的判断排除单条 intent 的错误 | 正确性 |
| G11 | HTTP 排空时长可配置，部署 compose 默认 45 秒；Redis 恢复等待响应停止 | 发布时长流被截断 |
| G12 | 运行时延迟探针把"当前还没醒的睡眠"也算进去 | 停摆期间探针本身看不到延迟 |
| G13 | 大部分账号已在冷却且上游没给 Retry-After 时，后续冷却封顶 5 秒；封顶值同时写入 Redis | A：全池 429 后恢复要空等 30 秒以上 |
| G14 | 调度路径上的本地过期租约扫描按"最早可能过期时刻"节流，最长 1 秒一次；定时清理和显式清理不节流 | B：每次调度都全表扫描租约 |
| G15 | 释放容量时，如果读到的唤醒额度已经多于等待者，直接返回，不再计算 `target - current` | B：main 上已有的问题。等待者在两次读取之间注册并拿到额度时，这个减法会下溢。debug 构建会 panic；release 构建会得到一个接近 2^64 的数，之后循环调用 `notify_one`，把一个运行时线程卡死。高并发调度测试偶发复现，已补单元测试 |

## 回归

- mock 矩阵 24/24 通过（判定见 [06-test-plan.md](06-test-plan.md)）。
- 默认特性全量测试：2839 通过，0 失败。
- 无默认特性全量测试：每次失败的都是不同的时序类测试，单独复跑均通过。其中 `redis_backed_session_binding_and_cooldown_are_shared_between_managers` 依赖每次 Redis 亲和操作在 75ms 内完成，超时后回退为本地计数，断言就会失败；把时限改成 1µs 可以稳定复现。这个测试已标为 timing-sensitive，由单线程的时序测试任务运行。

## 遗留（需要用户决定，或影响较小）

| 项 | 说明 |
| --- | --- |
| 风控 403、额度 402 不自动恢复 | 现有策略。如果是代理或上游误报，只能人工启用。是否自动恢复需要用户决定 |
| Redis 不可用时没有纯本地调度降级 | Redis 整体不可用时调度会停。实现本地降级需要处理多实例超卖，范围较大 |
| SIGKILL 后排队名额最长 120 秒回收 | 排队名额不按实例回收。只在排队满时被强杀才会出现，影响新实例约 2 分钟 |
| 调度排队不是先进先出 | 有槽释放时所有等待者竞争，过载回落阶段少数请求会排满 60 秒后超时，同时其他请求正常调度。槽位利用率不受影响，属于公平性问题 |
| 请求体内存没有全局上限 | 单个请求最大 50MB。几千个 MB 级请求同时进来可能 OOM，属于接近恶意的流量 |
