# 10-31 19:23 59137 过载停摆：现象与证据

时间为北京时间。数据来自现网只读查询：59137 的 PG（`usage_records`）、Redis、容器日志、dockerd 日志，以及同机 sub2api 的日志和 `usage_logs`。查询期间没有改现网配置，也没有重启服务。

## 现象

- 19:23 起，59137 的账号并发全部占满，但几乎不再调度新请求，RPM 接近 0。
- 用户 19:30 重建应用容器，恢复约 1 分钟后又卡住；19:34 第二次重建后恢复。
- 机器本身不忙：8 核，可用内存 11G，load 4–7。Redis 实测延迟 0.16ms，slowlog 为空，服务端一小时只用了 57 秒 CPU。PG 没有长事务。

## 关键证据

### 1. 卡住的是 kiro-rs 进程，不是 PG、Redis 或上游

- usage 写库。平时延迟 0 秒。卡住时每批 64 条要 10–60 秒，最长延迟 396 秒。19:34:38 停止接新请求后，1,472 条两秒内写完。PG 本身不慢。
- Redis。服务端延迟 0.16ms，slowlog 为空，6 个连接。kiro-rs 日志里的 Redis 操作却频繁超过共享期限（75ms、250ms、500ms），breaker 反复打开。
- 上游。恢复后同一批账号、同样的大上下文请求，每分钟能完成 300 多个。卡住时在途请求几乎都完成不了，说明不是上游变慢。
- 拒绝本身也变慢。"Redis 调度协调状态不可用"的 429，处理耗时中位 3.8 秒、P95 9 秒、最长 12 秒；队列满的 429 中位 37ms。sub2api 记录的 429 往返耗时中位 54 秒、P90 76 秒，原因是 sub2api 的重试也算在内。

结论：负载上来以后，kiro-rs 进程里所有异步任务（Redis 操作、usage 写入、请求处理）一起变慢；负载一停，马上恢复。

### 2. Redis 命令量和请求量不成比例

0.0.227 的 Redis 运行 3,854 秒，共处理 1,904 万条命令，平均每秒约 4,900 条。当时负载约每秒 5 个请求，折算每个请求约 800 条 Redis 命令。

| 命令 | 调用次数 |
| --- | --- |
| GET | 987 万 |
| ZCOUNT | 275 万 |
| HGETALL | 269 万 |
| ZRANGE | 179 万 |
| ZADD | 29 万 |
| ZRANGEBYSCORE | 27 万 |
| EXPIRE | 21 万 |
| EVAL | 18.6 万（平均 170us） |

Redis 里还有约 2.8 万个会话绑定键（`scheduler:session:*`）。

### 3. 重试放大

- sub2api 收到 429 后，先在同一账号上隔 500ms 重试 3 次，再换号，最多换 10 次。20 个账号都指向 59137，换号还是打到 59137。
- 故障期间，sub2api 每分钟对 59137 发起约 2,500 次尝试，正常时 150–200 次，放大 10 倍以上。
- 第一批"Redis 调度协调状态不可用"的 retry_after 是 1 秒，sub2api 的重试间隔又固定 500ms，不会真正退避。

### 4. 重建为什么要两次

- 第一次重建后，sub2api 积压的重试马上涌进来（19:31 一分钟 1,952 个），新进程又被压垮。
- 两次停止都在 10 秒内没退出，被强杀，内存里还没写进库的 usage 全部丢失。compose 没设 `stop_grace_period`，用的是默认 10 秒。
- 第二次重建后能恢复，可能有两个原因：sub2api 把 9 个账号暂停到 19:44，下游积压也已耗尽，进入的负载降下来了。这一点是推断，没有直接证据。

### 5. 当前 0.0.227 仍有隐患

- 重启后正常负载下，1 小时内 breaker 打开 169 次，"Redis 调度协调状态不可用"的 429 有 192 个。
- 排队会周期性冲到 80–120，再回落。

### 6. 不是第一次

10-29 20:02（0.0.224）出过同样的事：队列满 319 个，写库延迟 611 秒，20:12 重启后才恢复。分析见 `../scheduling-priority-circuit-20261029/04-incident-2002-queue-lease.md`。当时修了 Retry-After、早拒绝、唤醒和租约回收，但"负载下进程整体变慢"这一层没有找到原因。
