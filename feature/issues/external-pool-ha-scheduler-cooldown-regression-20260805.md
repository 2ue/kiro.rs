## 用户核心目标

外部池调度的核心目标是高可用，不是把每个错误都快速变成冷却。

用户已明确纠正：不要把 `401`、`402`、`403`、`429`、`5xx`、网络错误或协议错误预设为“永久问题”。这些错误默认都只是上游临时抖动信号，可以按影响程度赋予不同权重，但不能因为单次或短波错误就把外部池长期踢出调度。

目标行为：

1. 多个外部池同时存在时，优先级只是健康候选里的倾向；优先级低数字的池出错时，健康的高数字池必须能及时接管。
2. 外部池出现短暂抖动、间歇抖动、持续几秒、持续几分钟、部分池坏、全部池短时间坏等场景时，当前请求应优先原地有限重试或换外部池消化错误。
3. 冷却或临时不可调度可以存在，但必须非常严格，不能一次普通错误就把整个池长期踢出调度，导致外部池整体黑屏。
4. 故障池恢复后必须自动回到调度，不需要人工清除；但恢复应有观察/降权，避免刚恢复就重新打满。
5. 外部直连就是外部直连，外部池失败不能隐式回本地凭证。
6. 只有原始路线是本地优先，并且按配置从本地 fallback 到外部池的请求，才允许在外部失败后根据新鲜本地容量做一次回本地救援。
7. 调度和 usage 完全独立；调度重试、换池、冷却、恢复不能改变最终 usage 的真实上游 usage、估算 fallback、整形和计费规则。

## 用户可见问题

现网从 `v0.0.131` 升级到 `v0.0.132` 后，外部池出现大量冷却，页面/日志可见：

- 外部池容易全部进入冷却；
- 随后出现“外部池队列满”“外部池协调不可用”等二次症状；
- 高优先级外部池异常时，业务请求没有自然打到后续健康外部池；
- 即使池后续会恢复，也会因为长冷却和反复再冷却造成服务不可用窗口；
- 用户需要手动禁用或清除，不符合“多个外部池用于自动容灾”的使用目标。

这些二次症状不是根因。根因是调度策略把普通外部上游错误过早扩大成池级硬冷却，使后续流量没有足够机会被健康池接管。

## 当前源码根因

当前 `v0.0.132` 代码具备“当前请求换池”的基础能力，但冷却语义过重：

1. 外部池发送失败后，当前请求会按“跨池重试状态码”“网络错误跨池重试”“协议错误跨池重试”等配置决定是否换池。
2. 同时，很多错误会立即写入池级冷却，包括限流、数据库忙、服务错误、网络错误、协议污染、认证、额度、渠道禁用等。
3. 普通服务错误、网络错误和协议错误的基础冷却默认是 10 秒；限流和配额相关默认是 30 秒。
4. 连续瞬态失败窗口为 5 分钟，冷却可上浮到 300 秒。
5. 并发错误波里，同一个池可能被很多请求几乎同时打到；如果这些错误都写入长冷却，会快速造成多个池同时不可调度。
6. 冷却过期后，高优先级池又会因为静态优先级重新赢得流量；如果它还在抖动，会再次失败、再次冷却，形成反复黑屏。

因此 `v0.0.132` 的核心问题不是“没有冷却”，也不是“没有重试”，而是：

> 单次或短波普通错误被提升成池级硬冷却；硬冷却又参与候选硬过滤，导致外部池容灾被冷却机制反向破坏。

## 复现

复现不能用“某池失败一次或两次”作为最终标准。最小 sanity control 可以证明当前请求排除和换池分支存在，但高可用回归必须用持续流量复现：

1. 配置 3 个或更多外部池，优先级分别为 `1/10/20`，让优先级 `1` 的池在持续时间窗口内返回 `401/402/403/429/5xx/网络/协议` 任一类错误，让优先级 `10/20` 保持健康。
2. 使用闭环并发和开环到达率同时压测，覆盖低并发、高并发突增、客户端收到错误后立即重试、持续 30 秒/2 分钟/5 分钟错误波。
3. 观察真实 fake upstream 发送分布：健康备用池是否承接，坏池是否因静态优先级反复抢占，是否出现所有池长时间不可调度。
4. 错误停止后继续请求，观察坏池是否自动恢复、是否逐步回流、是否需要人工清除冷却。
5. 停止流量后检查队列、租约、连接、RSS、FD 是否回落。

通过标准不是“有一条请求成功”，而是时间窗口内调度分布、发送放大倍数、恢复时间和资源健康都符合 [外部池高可用调度执行计划](../../docs/plantree/plans/rust-runtime-scheduler-stabilization/topics/external-pool-ha-scheduler-execution-plan-20260805.md)。

## 参考项目结论

### sub2api

可借鉴点：

- 当前请求维护已失败账号集合，失败后切换账号，不在同一请求内反复命中坏候选。
- 同账号重试有明确次数，用尽后才切账号。
- 临时不可调度记录原因、错误码、命中规则、解除时间，但不是所有错误都会写入。
- 调度先过滤不可调度候选，再在可用候选里按负载、优先级、错误率、首字延迟等打分。
- 失败结果会更新运行态健康分，不等同于立即永久禁用。

不能照抄点：

- sub2api 面向不同协议和账号模型，kiro.rs 仍要保留外部直连、本地优先、本地到外部 fallback、一次本地救援的边界。

### CLIProxyAPI

可借鉴点：

- 请求重试次数和换凭证次数分开。
- 短冷却用于让调度切换凭证，不把所有瞬态错误都做成长时间全局黑屏。
- 过期冷却会在 pick 前自动提升回 ready。
- 可以按模型维度冷却，避免一个模型错误影响整个账号。

不能照抄点：

- CLIProxyAPI 的外部 key/auth 调度与 kiro.rs 的外部池、Redis 全局容量和 usage 记录结构不同，不能直接搬状态类型。

## 目标策略

### 1. 当前请求动作优先于全局硬冷却

外部池失败后，先决定当前请求怎么继续：

- 可以同池重试：按“同池重试次数”“同池重试状态码”“同池重试间隔”做有限重试。
- 应该换池：当前请求排除失败池，按“外部池最多尝试”和跨池配置选择其他外部池。
- 不应重试：请求体非法、工具 schema 非法、输入过长等请求错误直接返回，不污染池健康。
- 流式已提交语义字节后：不重放整条请求，只记录中断。

当前请求的换池不依赖池是否已经进入全局冷却。失败池应先在本请求内排除。

### 2. 运行态记录分三层

| 层级 | 作用 | 触发条件 | 对调度影响 |
| --- | --- | --- | --- |
| 请求级排除 | 只影响当前请求 | 当前候选发送失败、租约竞争失败、模型不支持 | 当前请求不再打该池 |
| 软降权/健康分 | 影响短期排序 | 普通瞬态错误、间歇失败、慢首字、短容量失败 | 让健康池接管，但不硬过滤 |
| 严格短期避让/临时不可调度 | 硬过滤候选 | 多轮独立失败证据达到严格阈值、管理员显式禁用、发送前本地配置自校验失败等少数情况 | 避让期内不调度该作用域，到期或探测成功后自动恢复 |

### 3. 冷却必须非常严格

普通单次 5xx、网络错误、协议错误、429、401、403、402 都不能被简单理解成“永远不可调度”。

临时不可调度只能在以下条件成立时写入：

- 在滑动窗口内跨多个独立请求或独立时间片持续失败，达到配置阈值；
- 管理员显式禁用或自动禁用策略命中；
- 发送前即可确认的本地配置问题，例如 base URL 格式无效、必要配置缺失；
- 模型级问题只影响当前请求或模型作用域，不默认冷却整个池。

如果上游响应里带有等待提示，只能作为短期避让的一个输入信号；这不是用户提出的必要条件，也不能覆盖“普通错误默认临时抖动、自动恢复”的主策略。

并发同一波失败不能被当成多个独立失败波无限放大。相同池、相同原因、很短窗口内的重复错误应合并计数或只做软降权。

### 4. 恢复要自动发生

恢复目标：

- 软降权随成功逐步衰减；
- 硬冷却到期后允许少量半开放探测；
- 探测成功后清理失败 streak 或降低错误率；
- 探测失败后再进入更严格的短期隔离；
- 恢复池不能立刻拿回 100% 流量，避免反复抖动。

### 5. 优先级不能阻止故障转移

优先级 `1/10/20` 的含义：

- 全部健康时，优先级 1 的池明显更优先；
- 优先级 1 的池发生普通失败后，当前请求要能切到优先级 10/20；
- 优先级 1 的池连续失败或错误率升高时，后续请求应主要由健康池承接；
- 优先级 1 恢复后自动逐步回流；
- 不允许因为优先级 1 静态最小，就反复打它、冷却它、等待它，而让健康池没流量。

## 验证矩阵

测试不能只覆盖“各失败一次”“失败两次”这种窄 case。小次数失败只能作为 sanity control，用来确认基础分支没有断；不能作为高可用验收标准。真正的验收必须覆盖持续累积行为：高并发错误波、持续报错、间歇无规律报错、客户端重试放大、队列/租约/RSS/FD 积累，以及恢复后的自动回流。

以下矩阵必须覆盖 stream 和 non-stream，至少包含闭环并发、开环到达率、高并发突增和长时间持续运行。

### A. 单池行为

| 场景 | 预期 |
| --- | --- |
| 单池健康 | 全成功，无冷却 |
| 单池小次数失败 | 只作基础分支检查，不作为发版验收标准 |
| 单池连续失败 20、50、100、500 次后恢复 | 当前请求按预算结束；运行态不进入长时间全局黑屏；恢复后自动成功 |
| 单池持续失败 30 秒、2 分钟、5 分钟 | 有界失败，队列/RSS/FD 不增长；恢复后自动成功 |
| 单池慢首字但成功 | 不应被当作错误冷却；只进入健康分/延迟评分 |

说明：小次数失败只用于确认分支动作，不作为发版标准。发版判断以持续失败、随机失败、恢复和资源健康为准。

### B. 多池优先级

| 场景 | 预期 |
| --- | --- |
| A/B/C 优先级 `1/10/20` 全健康 | A 占主要流量 |
| A 第 1 次失败，B/C 健康 | 当前请求切到 B/C；A 不应长黑屏 |
| A 连续失败 20/50/100/500 次，B/C 健康 | 后续流量主要由 B/C 承接 |
| A 间歇性随机失败 10%、30%、50%，B/C 健康 | 错误率越高，A 流量越低；整体成功率保持高 |
| A 失败 2 分钟后恢复 | A 半开放探测成功后逐步恢复主流量 |
| A/B 同时抖动，C 健康 | C 必须承接，不能因为 A/B 优先级更低数字而一直打坏池 |
| A/B/C 全部短时抖动 5 秒 | 不应把三个池全部打入长冷却；恢复后自动正常 |
| A/B/C 全部持续失败 2 分钟 | 有界返回错误，不能队列爆炸；恢复后自动正常 |

### C. 错误类型

以下每类都要测试一次、连续多次、随机间歇和恢复：

- 408/425；
- 429，带等待提示和不带等待提示；
- 401/403，包括可恢复的临时锁定和真实认证失败；
- 402/额度不足，包括后续充值恢复；
- 500/502/503/504/529；
- 523 等非默认 5xx；
- 连接失败、DNS 失败、请求超时、响应体读取超时；
- 成功状态码但返回错误信封；
- HTML 响应、SSE/JSON content-type 错配；
- 模型不支持、模型映射未命中；
- 请求体非法、工具 schema 非法、输入过长；
- 客户端断开；
- 流式首语义字节前失败；
- 流式首语义字节后失败。

### D. 并发与故障波

| 场景 | 预期 |
| --- | --- |
| 低并发 1 -> 5 突增 | 不误判成全局故障 |
| 中并发 5 -> 50 突增 | 健康池承接，发送次数受预算限制 |
| 高并发 50 -> 500 突增 | 队列、租约、RSS、FD 有界；恢复请求不被残留队列长期拖住 |
| 客户端 429/5xx 后立即重试 | 服务端真实发送放大倍数受总预算限制 |
| 健康流量 + 失败流量混合 | 失败池被降权，健康流量不被坏池拖死 |
| 流量停止 60 秒 | 队列、连接、租约、RSS、FD 回落 |

### E. 持续累积风险

| 挑战 | 必须验证的问题 | 通过标准 |
| --- | --- | --- |
| 同步错误波 | 高并发请求同时命中同一个坏池，是否把同一波失败放大成大量冷却/降权写入 | 同一波错误不会导致全部池长时间不可调度；健康池仍接管 |
| 客户端重试放大 | 下游收到 429/5xx 后立刻重试，是否和服务端重试相乘 | 真实上游发送放大倍数受总预算限制，队列不持续增长 |
| 长时间持续报错 | 一个或多个池连续 2-5 分钟失败，是否导致所有池被锁死 | 可用池继续承接；全部失败时有界报错，恢复后自动成功 |
| 间歇无规律报错 | 失败率在 10%-80% 随机变化，是否让优先级 1 坏池反复抢占 | 错误率越高流量占比越低，恢复后逐步回流 |
| 半开放恢复 | 避让/降权到期后如何探测恢复，是否瞬间打满 | 少量探测成功后回流，失败则继续降权，不能全量抖动 |
| 多实例写入 | 多个实例同时记录失败，是否把同一故障波计成多轮独立失败 | 计数和避让有去抖/窗口约束，不造成冷却风暴 |
| 队列残留 | 高并发故障结束后，低并发正常请求是否被残留队列拖住 | 故障停止后恢复请求在目标窗口内成功，队列/RSS/FD 回落 |
| 长流和首字慢 | 慢首字或长流是否被误判为错误，流式首语义字节后是否重放 | 成功慢请求不冷却；首语义字节后不重放完整请求 |

### F. 路线边界

| 场景 | 预期 |
| --- | --- |
| 外部直连 + 外部失败 | 只在外部池内部重试/换池；本地发送数为 0 |
| 本地优先 + 本地 Ready | 不被外部池状态拖慢 |
| 本地优先 + 本地全不可用 + 外部可用 | 按配置进入外部 fallback |
| 本地 fallback 到外部 + 外部失败 + 本地恢复 Ready | 最多一次回本地救援 |
| 本地无凭证进入临时外部 | 外部失败不伪装成本地凭证错误 |
| usage 旁路慢或失败 | 不影响调度、不影响最终 usage 计算 |

## 发版标准

本问题不能只靠单元测试标记完成。发版前必须至少完成：

1. 源码修复：普通错误不再默认写入长池级冷却；请求级排除、软降权和严格临时不可调度分离。
2. 本地 fake upstream 真实 HTTP 场景：多池、不同优先级、连续失败、随机间歇失败、全池抖动、恢复回流。
3. 并发场景：闭环并发、开环到达率、突增、客户端重试放大。
4. 路线边界：外部直连不回本地；本地优先符合 fallback/rescue 条件才回本地。
5. usage 独立性：相同真实上游 usage 在不同调度路线下最终 usage 一致；失败尝试不累加进最终成功 usage。
6. 资源健康：测试停止后临时服务、端口、队列、租约、RSS、FD 回落，临时产物清理。
7. 文档更新：本 issue、当前问题索引、plan-tree 状态和 evidence 同步。

## 当前处理方案

本轮选定方案：

1. 保留“当前请求排除失败池并换外部池”的行为。
2. 保留“外部池最多尝试”“同池重试次数”“跨池重试状态码”“网络错误跨池重试”“协议错误跨池重试”等配置。
3. 把普通错误的默认池级冷却改为请求级排除和短期软降权，不直接写池级冷却。
4. 临时不可调度只用于严格场景：重复失败证据达到阈值、管理员显式禁用、发送前本地配置自校验失败，或模型作用域明确且只影响该模型的问题。
5. 选择候选时使用短期健康分进行临时降权，即使没有冷却，也让健康池能够承接。
6. 成功请求降低或清除软失败 streak，让恢复池自动回流。
7. 用多场景 fake upstream 和较长时间本地验证证明恢复，而不是只跑“各失败一次”。

## 残余风险

- 如果某外部池长时间返回 401/403/402/429/5xx 等错误，不默认长冷却会增加少量恢复探测；需要通过严格阈值、短期避让和自动恢复策略控制探测频率，而不是把任何 4xx/5xx 一律当永久故障。
- 如果所有池都持续失败，系统仍会返回错误；目标是有界失败和自动恢复，不是伪造成功。
- 如果外部池本身把不同供应商聚合在一个 base_url 后面，本地只能看到聚合后的错误；冷却粒度可能无法精确到聚合内部账号。
- 完整 RoutePlan/统一截止时间/完整调度诊断仍是更大架构项，本轮先修复 132 的高可用回归。

## 2026-08-05 修复结论

本轮实际确认并修复的 P0 根因不是优先级排序函数本身，而是外部池管理变更的
Redis 事件竞态：当前进程发布自己的变更事件后又消费该事件，把刚合并的本地权威
池快照当作远端变化清空，连续创建多个池时候选集合因此只剩最后一个池。修复为
每个进程携带 `origin` 实例标识；观察到自身事件时只推进已观察代际，不清空本地
快照；没有 `origin` 的旧事件仍按远端事件兼容处理。

修复后的最终候选已完成真实 HTTP 多池验证、256 并发与 1800 RPM/60 秒持续到达率
验证、外部直连不回本地验证、失败池恢复回流验证，以及隔离 PostgreSQL/Redis
存储回归。全量 Rust 门禁为主程序 `1896 passed / 0 failed / 6 ignored`，
`kiro_loadtest 31/31`，格式、差异和构建产物库存门禁均通过。详细命令、候选二进制
哈希和资源采样见[专项证据](../evidence/external-pool-ha-scheduler-validation-20260805.md)。

`production-rollout-pending` 仅表示尚未将该候选部署到三台现网机器并观察，不表示
本地实现或本地发布候选仍有验证阻塞。更大范围的统一 RoutePlan、候选拒绝可观测性
